# ADR-002 — DB-per-service + 폴링 Outbox 릴레이

| 항목 | 내용 |

## 맥락

목표 G4는 "어떤 컴포넌트를 죽여도 데이터가 유실되거나 중복 배송되지 않는다"이다. 이를 위해 반드시 원자적이어야 하는
지점이 하나 있다.

> **도메인 상태 변경(PostgreSQL)** 과 **그 사실을 알리는 이벤트 발행(Kafka)** 은 함께 일어나거나 함께 일어나지 않아야 한다.

예: `order-service` 가 주문을 `PLACED` 로 저장했는데 `order.placed` 가 발행되지 않으면, 그 주문은 영원히 웨이브에
편입되지 않는다. DB에는 주문이 있는데 배송은 되지 않는 상태 — 조용한 데이터 손실이며 운영 중 가장 찾기 어려운 종류다.

반대로 이벤트만 나가고 상태가 없으면 하류가 존재하지 않는 주문을 계획한다.

서비스는 각자 자기 PostgreSQL DB를 가지며(§3.3 규칙 3), 이 두 리소스(PG, Kafka)는 서로 다른 트랜잭션 도메인이다.

## 결정

1. **DB-per-service**: 서비스마다 별도 DB와 별도 DB 사용자. 다른 서비스 테이블에 대한 JOIN·FK를 금지한다.
   필요한 데이터는 이벤트 페이로드 스냅샷 또는 자기 DB 프로젝션으로 가진다.
2. **Transactional Outbox**: 도메인 상태 변경과 `outbox_events` INSERT를 **같은 DB 트랜잭션**에서 수행한다.
   유스케이스에서 `KafkaTemplate` 을 직접 호출하지 않는다(ArchUnit 규칙 6, ADR-015 이후 추가됨 — DESIGN.md §13).
3. **폴링 릴레이**: 별도 컴포넌트 `OutboxRelay`(`libs/messaging`)가 미발행 행을 폴링(100ms)해 배치(500건)로 Kafka에
   발행하고 `published_at` 을 기록한다. 다중 인스턴스 안전성은 `SELECT … FOR UPDATE SKIP LOCKED` 로 확보한다.
4. **관측**: `dawnline_outbox_lag_seconds`(가장 오래된 미발행 행의 나이)와 미발행 건수를 핵심 메트릭으로 노출한다.

## 근거

- **원자성을 단일 리소스로 환원한다.** 두 리소스에 걸친 원자성 문제를 "PostgreSQL 트랜잭션 하나"로 바꾼다.
  이것이 이 결정의 전부이며, 나머지(폴링 방식·배치 크기)는 구현 세부사항이다.
- **인프라 추가가 없다.** 릴레이는 서비스 프로세스 안의 스케줄러다. 로컬 Compose 스택에 컨테이너가 늘지 않는다.
- **테스트가 쉽다.** Phase 0 DoD가 그대로 통합 테스트가 된다: outbox INSERT → 릴레이 → Kafka 수신.
- **재발행이 자연스럽다.** DLQ 재처리·장애 복구 시 `published_at` 을 비우면 다시 나간다.
- **지연 예산이 충분하다.** SLO(§8.1)의 Outbox 지연 목표는 p95 ≤ 2초이고, 폴링 주기는 100ms다.
  지연의 지배 항은 폴링 주기가 아니라 Kafka 발행 왕복이다.

## 고려한 대안과 기각 이유

**(a) Debezium CDC (PostgreSQL logical decoding → Kafka Connect)**

- 장점: 애플리케이션이 폴링하지 않고, 지연이 낮으며, outbox 라우팅 SMT 로 토픽 분배까지 처리한다.
- 기각: 로컬 스택에 Kafka Connect 클러스터 + 커넥터 설정이 추가된다. `wal_level=logical` 과 리플리케이션 슬롯을
  운영해야 하고, **슬롯을 아무도 읽지 않으면 WAL이 무한히 쌓여 디스크가 찬다** — 데모 중 노트북에서 이 실패 모드가
  발생하면 프로젝트 전체의 신뢰도를 잃는다. 얻는 이점(수십 ms 지연 단축)이 SLO에 필요하지 않다.
  **확장 경로로만 문서화한다**(아래 "되돌리는 방법" 참조).

**(b) 2PC / XA 로 PG와 Kafka를 묶기**

- 기각: Kafka 클라이언트는 XA 리소스가 아니다. `kafka-clients` 4.2.1 jar 에 `XAResource` 구현이 없고,
  Producer API에는 prepare 단계가 존재하지 않는다(상세 실측 근거는 ADR-006 §근거 1–2).
  구현 가능성 자체가 없으므로 트레이드오프의 대상이 아니다.

**(c) 트랜잭션 커밋 후 발행 (`TransactionSynchronization#afterCommit`)**

- 장점: 코드가 가장 짧고 outbox 테이블이 없다.
- 기각: 커밋과 발행 사이에 프로세스가 죽으면 이벤트가 영구히 사라진다. 이 창은 좁지만 0이 아니고,
  피크 시 인스턴스 재시작·OOM이 실제로 발생하는 구간이다. G4를 정면으로 위반한다.

**(d) 공유 DB (서비스들이 같은 스키마 사용)**

- 기각: §3.3 규칙 3 위반. 스키마 변경이 전 서비스 배포를 묶고, "MSA"라는 주장이 무의미해진다.

**(e) `LISTEN/NOTIFY` 로 폴링 대체**

- 장점: 폴링 부하 제거, 지연 단축.
- 기각(현 시점): 알림은 전달 보장이 없으므로(리스너 미연결 시 유실) **폴백 폴링을 유지해야 한다.**
  결국 두 경로를 다 갖게 되어 복잡도만 늘어난다. 폴링 부하가 실측으로 문제가 되면 그때 "알림으로 폴링을 깨우는"
  최적화로 도입한다.

## 결과

**장점**

- 상태와 이벤트가 절대 어긋나지 않는다. 크래시 시점이 어디든 결과는 "아직 발행 안 됨"이거나 "발행됨"이다.
- 릴레이는 `SKIP LOCKED` 덕분에 인스턴스를 늘려도 안전하다(같은 행을 두 인스턴스가 잡지 않는다).
- outbox 테이블이 곧 **발행 감사 로그**다. "이 주문의 이벤트가 언제 나갔는가"를 SQL로 답할 수 있다.

**비용**

- **at-least-once 가 구조적으로 강제된다.** 릴레이가 Kafka 발행 성공 후 `published_at` 기록 전에 죽으면
  같은 이벤트가 다시 나간다. 이것을 없앨 방법은 없으므로 소비자를 멱등으로 만든다 → **ADR-006**.
- **폴링 지연**: 최선의 경우에도 평균 폴링 주기의 절반이 더해진다.
- **테이블 증가**: 발행 완료 행이 계속 쌓인다. 보존 기간 정책(주기적 삭제 또는 파티션 드롭)이 필요하다.
  미발행 행 조회는 부분 인덱스(`WHERE published_at IS NULL`)로 상수 시간에 가깝게 유지한다.
- **키별 순서**: 같은 파티션 키의 이벤트는 outbox `id`(UUIDv7, 시간순) 오름차순으로 발행해야 순서가 보존된다.
  배치 발행 시 이 정렬을 깨지 않는 것이 릴레이의 계약이다.
- **쓰기 증폭**: 모든 도메인 트랜잭션에 INSERT가 하나 더 붙는다(주문 API p99 예산 200ms 안에서 수용 가능).

**되돌리는 방법**

`outbox_events` 의 **테이블 형식을 유지한 채** 릴레이만 교체할 수 있다. Debezium 의 outbox 이벤트 라우터는
정확히 이 형태의 테이블을 입력으로 받으므로, 전환 시 애플리케이션 코드(유스케이스·`OutboxEvent` 기록)는 그대로 두고
릴레이 스케줄러를 끄고 커넥터를 붙이면 된다. 즉 이 결정은 **CDC로 가는 길을 막지 않는 방향으로** 내려졌다.
