# ADR-018 — 멱등 잠금은 Redis 가 잡고, DB 에는 완료만 기록한다

## 맥락

§5.1 은 `POST /api/v1/orders` 의 멱등 처리를 네 단계로 적어 두었다. 그 문장을 그대로 코드로 옮기려
하면 두 곳이 서로 맞지 않는다.

1. 1단계는 Redis `SET NX` 가 실패했을 때 DB 를 보고 **`IN_PROGRESS` 면 409** 라고 한다.
   즉 DB 행이 처리 <em>도중</em>에도 존재한다는 뜻이다.
2. 3단계는 트랜잭션 하나가 `idempotency_keys` 를 **`DONE` 으로 INSERT** 한다고 한다.
   그러면 처리 도중에는 DB 에 행이 없다.

둘 다 만족시키려면 처리 시작 시 `IN_PROGRESS` 행을 <em>별도 트랜잭션으로</em> 먼저 커밋해야 한다.
그 설계에는 되돌릴 수 없는 결함이 있다. **커밋된 `IN_PROGRESS` 행은 스스로 사라지지 않는다.**
3단계 도중에 프로세스가 죽으면(배포·OOM·노드 손실) 그 행이 남고, 같은 멱등 키로 오는 모든 재시도는
`expires_at` 까지 409 를 받는다. 클라이언트가 할 수 있는 일이 없다 — 멱등 키는 클라이언트가 만든
것이고, 그 키를 바꾸면 애초에 멱등이 아니다. 즉 **정상적인 프로세스 종료가 고객의 주문을 영구히
막는다.** 그리고 이 상황은 배포할 때마다 확률적으로 생기며, 트래픽이 많을수록 더 자주 생긴다.

## 결정

### 1. in-flight 표시는 Redis 키가 맡는다

`SET idem:order:{key} IN_PROGRESS NX PX 30000` — **PX 30000 이 이 결정의 핵심**이다.
프로세스가 죽어도 30초 뒤 잠금이 스스로 풀린다. 사람이 치우러 갈 것이 없다.

### 2. DB `idempotency_keys` 에는 완료된 결과만 기록한다

주문 트랜잭션 하나가 `orders` + `order_items` + `outbox_events` + `idempotency_keys(DONE)` 를
함께 커밋한다. 행이 있다는 것은 곧 "그 요청은 끝났고 응답은 이것" 이라는 뜻이다.

### 3. 정확성의 근거는 Redis 가 아니라 `idempotency_keys` 의 기본 키다

Redis 가 없어도 같은 키로 동시에 들어온 두 요청 중 하나만 성공한다. 완료 기록을 업서트로 쓰기 때문이다.

```sql
INSERT INTO idempotency_keys (...) VALUES (...)
ON CONFLICT (idem_key) DO UPDATE SET status = 'DONE', ...
 WHERE idempotency_keys.status = 'IN_PROGRESS'
```

두 번째 요청은 첫 번째가 커밋할 때까지 인덱스에서 대기하다가 `DONE` 행을 보고 **0행**을 갱신한다.
그 0행이 곧 "내가 졌다" 는 신호이고, 트랜잭션을 롤백한 뒤 409 를 준다. 클라이언트가 재시도하면
1단계에서 저장된 응답이 재생된다. 잃는 것은 진 쪽이 한 <em>일</em>뿐이고, 그 일은 통째로 롤백된다.

그래서 Redis 가 하는 일은 **정확성이 아니라 낭비 방지**다. 이것이 불변 규칙 7 이 요구하는 모습이다 —
키가 전부 사라져도 답은 같고 비용만 오른다.

### 4. DB 의 `IN_PROGRESS` 는 읽기 경로에만 남긴다

§5.1 DDL 의 `status` 는 `IN_PROGRESS | DONE` 그대로 두고, 읽기 경로도 `IN_PROGRESS` 를 만나면
409 로 처리한다. 다만 **order-service 는 그 값을 쓰지 않는다.** 지우지 않는 이유는 두 가지다.
DDL 은 설계서에 있는 것이고 컬럼 값 하나를 줄이자고 마이그레이션을 만들 이유가 없다. 그리고 언젠가
`IN_PROGRESS` 를 쓰는 경로(예: 결제처럼 되돌릴 수 없는 외부 호출을 끼는 요청)가 생기면 읽기 쪽이
이미 준비돼 있는 편이 낫다.

### 5. 지문은 원문 바이트가 아니라 요청의 표준형에서 만든다

§5.1 은 "본문 해시" 라고만 적었다. 원문 바이트를 해싱하면 공백·필드 순서·`null` 생략만 다른
재전송이 **422** 가 된다. 재시도는 보통 다른 HTTP 클라이언트나 다른 직렬화기를 거쳐 오므로 이것은
드문 일이 아니다. 명령 객체의 필드를 정해진 순서로 이어 붙인 표준형을 해싱하면, 의미가 같은 요청은
같은 지문을 갖는다.

대가: 명령에 필드를 더하면서 표준형에 넣는 것을 잊으면 **서로 다른 두 요청이 같은 지문을 갖는다** —
두 번째 요청이 첫 번째의 응답을 받는다. 이것은 조용한 오작동이라 리뷰로는 못 잡는다. 그래서
`PlaceOrderCommand` 의 레코드 컴포넌트를 리플렉션으로 훑어 표준형이 전부 포함하는지 확인하는
테스트를 둔다. 필드를 추가하면 그 테스트가 먼저 깨진다.

## 고려한 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| **DB 에 `IN_PROGRESS` 를 먼저 커밋**(§5.1 문장을 그대로 옮김) | 위의 맥락 그대로 — 프로세스가 죽으면 그 멱등 키가 `expires_at` 까지 막힌다. 배포마다 확률적으로 발생하고 고객이 회복할 방법이 없다 |
| **`IN_PROGRESS` 를 쓰되 짧은 `expires_at` 으로 스스로 풀리게** | 만료를 판정하려면 읽는 쪽이 매번 시각을 비교해야 하고, 만료된 행을 지우는 배치가 또 필요하다. Redis TTL 이 공짜로 해 주는 일을 DB 로 옮기는 것뿐이다 |
| **Redis 없이 DB 만으로**(PK 충돌만 사용) | 동작은 한다. 그러나 피크에 같은 키의 중복 요청이 몰리면 진 쪽이 주문 INSERT 까지 다 하고 롤백한다. Redis 한 번의 `SET NX` 로 막을 수 있는 낭비다 |
| **`SELECT ... FOR UPDATE` 로 멱등 키 행을 잠금** | 잠글 행이 아직 없다(첫 요청). 빈 행을 잠그려면 advisory lock 이 필요한데, 그것은 DB 커넥션을 요청 내내 붙잡는다 — 피크에 커넥션 풀(인스턴스당 10, §8.2)이 먼저 마른다 |
| **응답 본문 대신 `orderId` 만 저장하고 재생 시 주문을 다시 조회** | 조회가 한 번 더 늘고, 그 사이 상태가 바뀌면 <em>접수 시점의</em> 응답과 다른 것이 재생된다. 멱등 재생은 "그때 준 답" 을 돌려주는 것이다 |

## 결과

**좋아지는 것**

- 프로세스가 언제 죽어도 30초 뒤 그 멱등 키로 다시 주문할 수 있다. 운영자가 치울 것이 없다.
- Redis 가 통째로 죽어도 주문은 계속 받는다. 정확성은 `idempotency_keys` PK 가 지킨다 (불변 규칙 7).
- 정상 경로는 여전히 트랜잭션 하나다 (§5.1 "쓰기 경로를 최소화").

**비용**

- Redis 를 잃으면 같은 키의 동시 중복 요청이 헛일을 한 뒤 롤백된다. 정상 트래픽에서는 같은 키가
  동시에 두 번 오는 일이 드물어 실측 영향은 작지만, 클라이언트가 타임아웃 후 즉시 재시도하는
  패턴에서는 두 배의 쓰기가 잠깐 발생한다.
- `status` 컬럼에 이 서비스가 쓰지 않는 값(`IN_PROGRESS`)이 남는다. 읽기 경로만 보는 사람에게는
  "언제 생기는 값인가" 가 바로 보이지 않아, DDL 주석과 이 ADR 로 가리킨다.
- 지문이 표준형에 의존하므로 명령 필드를 늘릴 때 표준형도 함께 늘려야 한다. 리플렉션 가드 테스트가
  그것을 강제한다.
