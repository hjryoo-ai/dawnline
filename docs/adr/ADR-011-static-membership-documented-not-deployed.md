# ADR-011 — 롤링 배포의 소비자 static membership 은 문서로만 둔다

| 항목 | 내용 |
|---|---|
| 상태 | Accepted (2026-09-28) — **문서만.** k8s 매니페스트와 kind 스모크는 만들지 않는다(7-7 결정) |
| 결정일 | 2026-09-28 |
| 관련 문서 | `docs/DESIGN.md` §8.6(기동 · 종료) · §14(배포 전략 문서) · `docs/runbooks/RB-01-kafka-recovery.md` |
| 관련 ADR | [ADR-016](ADR-016-readiness-excludes-kafka.md) (레디니스에 Kafka 를 넣지 않는다) · [ADR-034](ADR-034-degrade-mode.md) (랙이 열화 입력이다) |

---

## 맥락

소비자 그룹은 서비스 이름이고(`group-id`), 리스너 동시성 3, 수동 커밋, 그레이스풀 셧다운 30초다. 인스턴스는 Compose 에서 하나씩 뜬다.
롤링 배포에서 파드가 하나씩 바뀌면 **파드마다 두 번**(떠날 때 · 올 때) 그룹 리밸런스가 돈다 — 그동안 파티션은 소비되지 않고, 랙은
「모름」(`LAG_UNKNOWN`)이 되고, 컷오프 직전이면 그 랙이 열화의 입력이다(ADR-034).

## 결정 — 배포할 때의 모양 (구현하지 않는다)

1. **파드마다 고정된 `group.instance.id`** — StatefulSet 의 서수(`<service>-0`, `-1`)에서. 같은 id 로 돌아온 소비자는 리밸런스 없이 자기 파티션을 되받는다.
2. **`session.timeout.ms` 는 파드 하나의 교체 시간보다 길게**(예: 45–60초). 짧으면 static membership 이 있어도 떠난 것으로 본다. 대가: 파드가 정말
   죽으면 그 파티션은 세션 만료까지 멈춘다 — 그 시간이 알림(`DawnlineConsumerLag`)의 `for` 보다 짧아야 한다.
3. **종료는 지금 그대로** — HTTP 드레인 30초 · 처리 중 레코드 커밋 뒤 종료(§8.6). static member 는 떠날 때 `LeaveGroup` 을 보내지 않으므로
   리밸런스 없이 멈춘다.
4. **레디니스는 여전히 DB 마이그레이션만**(ADR-016) — 소비 재개를 레디니스로 막지 않는다.

## 구현하지 않는 이유

이 포트폴리오의 실행 환경은 Compose 단일 인스턴스다 — 롤링 배포가 없다. 매니페스트를 만들면 검증할 수 없는 설정이 생기고, 검증되지
않은 설정은 문서보다 나쁘다(있다고 믿게 만든다). 설정 키 둘(`group.instance.id` · `session.timeout.ms`)은 Spring Boot 의 `spring.kafka.consumer.properties.*` 로 넣는다 — 인스턴스마다
다른 값이라 환경 변수에서 온다(코드 변경은 없다, 근거: 추정 — 넣고 재지 않았다).

## 대안

| 안 | 기각 사유 |
|---|---|
| 기본 리밸런스(동적 멤버십) | 파드마다 두 번의 정지 — 컷오프 창에서 열화를 부른다 |
| 협조적 리밸런스(`CooperativeStickyAssignor`)만 | 정지 범위를 줄이지만 없애지 않는다. static membership 과 함께 쓰는 것이 보통이고, 둘 다 배포가 있어야 잰다 |
| k8s 매니페스트 + kind 스모크 | 검증 가능한 것은 「뜬다」뿐이고 리밸런스의 부재는 부하와 함께 재야 한다 — 범위 밖(7-7 결정) |

## 재검토 지점 (포트폴리오 범위 밖 — 다시 여는 조건)

- **인스턴스가 둘 이상 뜨는 배포가 생길 때** — 롤링 배포 중 `LAG_UNKNOWN` 구간과 리밸런스 횟수를 재고, 이 ADR 의 네 줄을 설정으로 옮긴다.
