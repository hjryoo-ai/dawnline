# ADR-003 — JSON + JSON Schema 이벤트 계약

| 항목 | 내용 |

## 맥락

토픽 9개(+ DLQ)를 통해 서비스 5개가 통신한다(§4.1). 발행자 1개에 소비자 2~3개가 붙으므로, 페이로드 변경은
언제나 다자간 계약 변경이다. 계약이 깨지는 두 가지 방식을 모두 막아야 한다.

1. **발행자가 계약을 어긴다** — 필수 필드 누락, 타입 변경, enum 값 변경.
2. **소비자가 계약을 좁게 가정한다** — 알 수 없는 필드를 만나면 역직렬화 실패.

동시에 로컬 스택은 `make up` 한 명령으로 떠야 하며(§14), 컨테이너를 하나 늘릴 때마다 데모의 실패 확률이 올라간다.

또한 Spring Boot 4의 기본 JSON 매퍼는 **Jackson 3(`tools.jackson.*` 패키지)** 이다. 직렬화 스택 선택은
프레임워크가 이미 정해 놓았고, 우리 결정은 "그 위에 어떤 계약 검증을 얹는가"이다.

## 결정

- **직렬화는 JSON.** 이벤트 봉투(§4.2)는 `eventId / eventType / schemaVersion / occurredAt / producer /
  partitionKey / traceId / payload` 이며, Kafka 헤더에 `traceparent`, `eventType`, `schemaVersion` 을 중복 기록해
  페이로드를 열지 않고도 라우팅·필터링이 가능하게 한다.
- **계약은 JSON Schema 파일.** `contracts/events/<eventType>.v<major>.schema.json` 과
  `contracts/events/examples/<eventType>.v<major>.json`.
- **양방향 계약 테스트**(§13). 발행자 측: 생성한 페이로드가 스키마를 통과하는지 검증한다.
  소비자 측: `examples/*.json` 을 자기 DTO로 역직렬화해 필수 필드가 매핑되는지 검증한다.
- **진화 규칙**(§4.7): 같은 major 안에서는 **추가만** 허용(필드 추가, enum 값 추가).
  소비자는 `FAIL_ON_UNKNOWN_PROPERTIES=false` 로 알 수 없는 필드를 무시한다.
  삭제·의미 변경·타입 변경은 새 토픽 `…v2` 로 발행하고 이관 완료까지 v1·v2를 병행 발행한다.
- **계약 우선**: 새 이벤트/필드는 스키마와 예시를 **먼저** 갱신하고 계약 테스트를 추가한 뒤 코드를 바꾼다.

## 근거

- **레지스트리 없이 CI로 계약을 강제할 수 있다.** 우리가 필요한 것은 "호환되지 않는 변경이 머지되지 않는 것"이고,
  그것은 스키마 파일 + 테스트로 달성된다. 런타임 레지스트리는 배포 시점 강제를 추가로 줄 뿐이다.
- **디버깅 가능성.** 데모·장애 조사에서 `kafka-console-consumer` 로 메시지를 그대로 읽을 수 있다.
  바이너리 포맷이면 스키마 조회 도구가 있어야 한 줄을 읽는다. 관측성(§9)이 프로젝트의 핵심 어필인데,
  가장 기본적인 관측 수단을 포기할 이유가 없다.
- **계약이 문서다.** 리뷰어가 `contracts/events/` 만 열어도 이 시스템이 무엇을 말하는지 알 수 있다.
- **규모가 결정적이지 않다.** 로컬 데모의 피크는 15만 건/일(§8.2)이다. 이 규모에서 JSON의 크기·파싱 비용은
  병목이 아니며, 필요하면 토픽 압축(`compression.type`)으로 대부분 상쇄된다.

## 고려한 대안과 기각 이유

**(a) Avro / Protobuf + Confluent Schema Registry**

- 장점: 메시지 크기 축소, **레지스트리가 런타임에 호환성을 강제**(비호환 스키마는 등록 자체가 거부됨),
  스키마에서 타입 생성, 스키마 ID가 메시지에 실려 버전 추적이 정확하다. 대규모 조직에서는 사실상 표준이다.
- 기각: (1) 로컬 스택에 Schema Registry 컨테이너와 직렬화기 설정이 추가된다. 브로커는 `apache/kafka:4.3.1`
  순정 이미지를 쓰는데 여기에 Confluent 스택을 섞으면 로컬 기동 복잡도와 버전 조합 리스크가 커진다.
  (2) 우리가 이 도구에서 실제로 필요한 것(진화 규칙 강제)은 CI의 계약 테스트로 동등하게 얻는다.
  (3) 코드 생성은 Java `record`(§6.2 스타일)로 손으로 쓰는 편이 오히려 읽기 좋다.
- **확장 경로**: 봉투(§4.2)는 그대로 두고 `payload` 직렬화만 교체할 수 있게 설계했다.
  처리량이나 페이로드 크기가 실측으로 문제가 되면 그때 도입한다.

**(b) 스키마 없이 공유 DTO 라이브러리 (`libs/events` 에 record를 두고 모두가 컴파일 의존)**

- 장점: 모노레포에서 가장 쉽다. 타입 안전, 중복 없음.
- 기각: 발행자와 소비자가 **같은 클래스에 컴파일 의존**하게 되어 독립 배포가 불가능해진다.
  필드를 지우면 전 서비스가 동시에 재배포돼야 하고, "이벤트로 느슨하게 결합했다"는 설계 주장이 무너진다.
  모노레포에서 가장 빠지기 쉬운 함정이므로 명시적으로 금지한다.

**(c) CloudEvents 규격 채택**

- 장점: 표준 봉투, 생태계 도구 호환.
- 기각: 우리 봉투(§4.2)와 필드가 거의 1:1로 대응하는데(`id/type/time/source` ↔ `eventId/eventType/occurredAt/producer`)
  라이브러리 의존성이 하나 늘어난다. 필요해지면 필드 이름만 바꿔 이관할 수 있도록 **의미적으로 호환되게** 유지한다.

**(d) 계약 없이 관용적 소비 (스키마 파일 자체를 두지 않음)**

- 기각: 소비자가 무엇을 기대하는지가 코드에만 존재하면, 발행자는 자신이 무엇을 깨는지 알 수 없다.

## 결과

**장점**

- 인프라 추가 0. 계약 위반은 CI에서 잡힌다.
- 사람이 읽을 수 있는 메시지 → 장애 조사·데모·면접 설명이 모두 쉬워진다.
- 계약 변경이 모노레포 덕분에 한 커밋에 담긴다(ADR-001).

**비용**

- **런타임 강제가 없다.** 레지스트리라면 비호환 발행을 브로커 앞에서 막지만, 우리는 CI 게이트에 의존한다.
  CI를 우회해 배포하면 깨진 이벤트가 나갈 수 있다. → 발행 경로에서도 스키마 검증을 켤 수 있게
  `libs/messaging` 에 검증 유틸을 두고, 최소한 테스트·개발 프로파일에서는 항상 검증한다.
- **이중 관리**: 스키마 파일과 Java `record` 가 따로 존재한다. 어긋남은 계약 테스트로만 잡히므로,
  새 필드 추가 시 테스트 추가가 규율로 요구된다(`CLAUDE.md` 규칙 8).
- **메시지 크기**: Avro 대비 크다. 토픽 압축으로 완화하며, 실측이 필요해지면 벤치마크로 판단한다.
- **enum 확장의 함정**: 소비자가 모르는 enum 값을 만날 수 있다. 소비자는 미지의 값을 "무시 + 메트릭"으로
  처리해야 하며(§4.6의 `dawnline_event_rejected_total`), 예외를 던져 DLQ로 보내지 않는다.

**되돌리는 방법**

`schemaVersion` 이 봉투와 Kafka 헤더 양쪽에 있으므로, 소비자는 헤더만 보고 JSON/바이너리 분기를 할 수 있다.
포맷 전환은 토픽 단위로 점진 가능하며(v2 토픽 병행 발행), 저장소 차원의 일괄 변경이 필요하지 않다.
