# ADR-016 — 레디니스 프로브에서 Kafka 브로커 연결을 제외한다

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |
| 결정일 | 2026-09-01 |
| 관련 문서 | `docs/DESIGN.md` §8.4(장애 모드 표), §8.6(기동·종료), §4.4(Outbox) |
| 구현 위치 | `services/*/src/main/resources/application.yml` (`management.endpoint.health.group.readiness`) |

---

## 맥락

설계서 §8.6은 레디니스 조건을 "DB 마이그레이션 완료 + **Kafka 프로듀서 초기화** + (fulfillment) GEO 적재 완료"로
적었다. 그런데 같은 설계서 §8.4의 장애 모드 표는 정반대를 요구한다.

> | Kafka 브로커 다운 | outbox 미발행 누적 | 릴레이 재시도, **주문 API 정상** | RB-01 |

두 문장은 동시에 성립할 수 없다. 레디니스에 브로커 연결이 들어가면 브로커가 죽는 순간 5개 서비스의
레디니스가 전부 실패하고, 오케스트레이터가 트래픽을 끊는다. "주문 API 정상"은 불가능해진다.

Phase 0 구현은 Kafka를 레디니스 그룹에서 빼는 쪽을 택했지만, 그 근거가 `application.yml` 주석으로만
남아 있었다. 설계서와 코드가 어긋난 채로 굳은 상태이며, `CLAUDE.md` 는 이 경우 **설계서를 먼저 고치라**고
요구한다. 이 ADR이 그 절차다.

## 결정

**레디니스 = DB 마이그레이션 완료 + (fulfillment) GEO 적재 완료.** Kafka 브로커 연결은 넣지 않는다.

- 브로커 상태는 레디니스가 아니라 **outbox 지연 게이지와 consumer lag 알림**(§9.4)으로 감시한다.
- 라이브니스에도 넣지 않는다. 브로커 장애로 프로세스를 재시작해도 얻는 것이 없다.

## 근거

- **이 아키텍처가 outbox를 쓰는 이유 자체가 이것이다.** 쓰기 경로는 도메인 변경과 `outbox_events` INSERT를
  같은 DB 트랜잭션에서 끝낸다(§4.4). 브로커는 그 경로에 없다. 주문을 받는 데 브로커가 필요 없는데
  브로커가 없다고 주문을 거절하면, outbox로 산 비동기성을 프로브가 도로 반납하는 셈이다.
- **레디니스는 "이 인스턴스로 트래픽을 보내도 되는가"를 답한다.** 브로커 장애는 이 질문의 답을 바꾸지 않는다.
  트래픽을 끊어도 브로커가 낫지 않고, 다른 인스턴스도 똑같이 실패하므로 흘려보낼 곳도 없다.
- **장애의 영향 범위를 넓힌다.** 브로커 하나의 장애가 전 서비스 트래픽 차단으로 증폭된다.
  §8.2가 설계한 완충 지점("Kafka가 하류 처리 지연을 흡수")이 통째로 사라진다.
- **DB는 다르다.** DB가 없으면 주문을 받을 수 없다 — 쓰기 경로에 실제로 있기 때문이다.
  그래서 DB는 레디니스에 남는다. 이 비대칭이 정확히 outbox 설계의 내용이다.

## 고려한 대안과 기각 이유

**(a) 설계서 §8.6을 그대로 두고 코드에 Kafka 프로브를 추가한다**

- 장점: 문서와 코드가 일치한다. "브로커가 죽었는데 왜 healthy냐"는 질문이 안 나온다.
- 기각: §8.4와 모순되고, 무엇보다 **§8.2의 피크 완충 설계가 무너진다.**
  둘 중 하나를 고쳐야 한다면 고칠 것은 §8.6이다. §8.4·§8.2 쪽이 이 시스템의 핵심 성질이다.

**(b) 기동 시 1회만 검사하고 이후에는 무시(프로듀서 초기화 확인)**

- 장점: "프로듀서 초기화"라는 원문에 가장 가깝다.
- 기각: 기동 순서 의존성이 생긴다. Compose·k8s에서 브로커보다 먼저 뜨면 부팅에 실패하고,
  그건 브로커 장애 시 재기동이 막힌다는 뜻이다. 게다가 Kafka 프로듀서는 원래 지연 연결이라
  "초기화됨"이 브로커 도달 가능성을 보장하지도 않는다. 검사 비용만 있고 정보가 없다.

**(c) 별도 헬스 그룹(`/actuator/health/kafka`)으로 노출하되 레디니스에서는 뺀다**

- 장점: 진단용 정보가 엔드포인트로 남는다.
- 기각: 같은 사실을 이미 두 곳이 말한다 — `dawnline_outbox_lag_seconds` 와 consumer lag.
  세 번째 출처는 서로 어긋날 때 어느 쪽이 맞는지 정하는 비용만 만든다.
  진짜로 필요해지면 그때 추가한다(되돌리기 쉬운 방향).

## 결과

**장점**

- §8.4가 약속한 "브로커 다운 시 주문 API 정상"이 실제로 성립한다.
- 브로커 장애의 영향이 하류 지연으로 국한된다. 트래픽 차단으로 증폭되지 않는다.
- 브로커보다 먼저 떠도 서비스가 기동한다 — 기동 순서 의존성이 없다.

**비용**

- **브로커가 죽어도 프로브는 녹색이다.** 프로브만 보는 사람에게는 정상으로 보인다.
  그래서 outbox 지연 알림(§9.4, > 30s)이 이 장애의 **유일한** 탐지 경로다. 그 알림이 꺼져 있으면
  브로커 장애가 조용히 진행된다 — 알림 설정이 선택이 아니라 이 결정의 전제다.
- outbox 미발행이 계속 쌓인다. 장기 장애 시 `outbox_events` 가 커지고, 복구 직후 릴레이가
  밀린 분량을 한꺼번에 밀어낸다(§8.4 RB-01에서 확인).

**되돌리는 방법**

`application.yml` 의 `management.endpoint.health.group.readiness.include` 에 Kafka 헬스 인디케이터를
추가하면 된다. 서비스마다 한 줄이며, 되돌리면 §8.4·§8.2도 함께 수정해야 한다.
