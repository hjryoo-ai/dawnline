# ADR-007 — 헥사고날 아키텍처 + ArchUnit 강제, 도메인 모델과 JPA 엔티티 분리

## 맥락

서비스 5개가 같은 내부 레이아웃을 쓴다(§3.4).

```
com.dawnline.<service>
├── domain/            # 애그리거트·값 객체·도메인 서비스 (프레임워크 비의존)
├── application/       # 유스케이스, port/in, port/out, 트랜잭션 경계
├── adapter/in/web · in/messaging · out/persistence · out/messaging · out/redis
└── config/
```

여기에 이 프로젝트만의 강한 제약이 둘 있다.

1. **`dispatch-service` 의 `domain.optimizer` 는 순수 Java여야 한다.** `tools/benchmark` 가 Spring 컨텍스트 없이
   최적화 파이프라인을 그대로 실행해 전략을 비교하기 때문이다(§6.9, `CLAUDE.md` 규칙 5).
2. **상태 전이는 애그리거트 메서드로만 한다**(`order.markDispatched()`). 세터로 status를 바꾸지 않는다(규칙 6).

설계서 §3.4는 "JPA 어노테이션은 `adapter/out/persistence` 엔티티에만 두고 도메인 모델과 분리한다"를 기본값으로 두되,
서비스 규모가 작으므로 **도메인 = JPA 엔티티 통합을 허용할지**를 `[결정 필요]`로 남겨 두었다. 이 ADR이 그것을 확정한다.

## 결정

1. 헥사고날 레이아웃을 전 서비스에 적용하고 **ArchUnit으로 강제**한다(§13의 규칙 5개).
   - `domain` 은 `org.springframework`, `jakarta.persistence` 를 의존하지 않는다.
   - `application` 은 `adapter` 를 의존하지 않는다.
   - `com.dawnline.<svc>` 는 다른 `<svc>` 패키지를 참조하지 않는다.
   - Kafka 리스너 클래스는 `adapter.in.messaging` 에만 존재한다.
   - `@Transactional` 은 `application` 계층에만 붙는다.
2. **도메인 모델과 JPA 엔티티를 분리한다.** JPA 어노테이션은 `adapter/out/persistence` 의 `*Entity` 클래스에만 둔다.
   도메인 애그리거트는 순수 Java이며, 변환은 각 어댑터가 소유한 **손으로 쓴 매퍼**(정적 `toDomain` / `toEntity`)가 담당한다.
3. 매핑 라이브러리(MapStruct 등)는 도입하지 않는다. 의존성 최소화 원칙과, 애노테이션 프로세서가
   `-Werror -Xlint:all` 컴파일 설정과 상호작용하는 위험을 피한다.

## 근거

- **`optimizer` 순수성이 요구사항이다.** 도메인 = JPA 엔티티라면 `tools/benchmark` 모듈이 Hibernate를 끌고 온다.
  벤치마크가 "서비스에서 도는 것과 같은 코드"임을 주장할 수 있는 것은 도메인이 프레임워크에 묶여 있지 않기 때문이다.
- **JPA의 요구가 도메인 불변식과 충돌한다.** JPA는 무인자 생성자, non-final 클래스·필드(프록시),
  특정 컬렉션 타입을 요구하고 리플렉션으로 필드를 채운다. 즉 **"항상 유효한 객체"를 만들 수 없다.**
  규칙 6(세터 금지, 상태 머신 메서드로만 전이)과 정면으로 부딪힌다.
- **`record` 와 `sealed interface` 를 도메인에서 쓸 수 있다.** JPA 엔티티는 `record` 가 될 수 없다.
  값 객체(`GeoPoint`, `Money`, `TimeWindow`)와 룰 계층(`sealed interface DispatchRule`, §6.3)이 이 표현력에 의존한다.
- **영속성 사고를 유스케이스 경계 밖으로 민다.** 지연 로딩 프록시가 도메인 메서드 안에서 터지는 일
  (`LazyInitializationException`, 의도치 않은 N+1)이 구조적으로 불가능해진다. 어댑터가 필요한 것을 다 읽어서 도메인을 조립한다.
- **스키마와 모델이 독립적으로 진화한다.** Flyway로 컬럼을 나눠도 도메인은 그대로일 수 있고, 그 반대도 가능하다.
  운영 중 인덱스·정규화 변경이 도메인 규칙 리뷰를 강제하지 않는다.

## 고려한 대안과 기각 이유

**(a) 도메인 = JPA 엔티티 통합 (설계서가 남겨 둔 선택지)**

- 장점은 실제로 크다. 매퍼가 사라져 애그리거트당 코드가 30~40% 줄고, 더티 체킹 덕분에 저장 코드를 쓰지 않아도 되며,
  필드 추가가 한 곳 수정으로 끝난다. 서비스 규모(테이블 5~10개)를 보면 **합리적인 선택이었다.**
- 기각 이유는 위 근거 전부이며, 특히 `optimizer` 순수성(요구사항)과 규칙 6(세터 금지)이다.
  이 둘은 취향이 아니라 이 프로젝트가 증명하려는 것의 일부다.

**(b) 서비스별로 다르게 (작은 서비스는 통합, `dispatch` 만 분리)**

- 장점: 비용이 큰 곳에만 비용을 낸다.
- 기각: ArchUnit 규칙을 서비스별로 분기해야 하고("여기서는 `jakarta.persistence` 가 domain에 허용됨"),
  리뷰어와 미래의 나에게 "왜 여기만 다른가"를 매번 설명해야 한다. 일관성의 가치가 절약분보다 크다.

**(c) 계층형 아키텍처 (controller → service → repository)**

- 장점: 가장 익숙하고 파일이 적다.
- 기각: 포트가 없으므로 서비스 클래스가 리포지토리 구현·Kafka 템플릿·Redis 템플릿을 직접 참조하게 되고,
  경계가 점진적으로 침식된다. 이 침식은 리뷰로만 막을 수 있는데 리뷰어가 1명이다.
  헥사고날의 실질적 이득은 "경계를 자동으로 검사할 수 있는 형태"라는 데 있다.

**(d) 헥사고날 + 규칙을 문서로만 (ArchUnit 없음)**

- 기각: 문서로만 있는 규칙은 마감이 급할 때 가장 먼저 깨진다. 강제되지 않는 아키텍처는 주장일 뿐이다.

## 결과

**장점**

- 규칙 5(프레임워크 비의존 도메인)가 ArchUnit 규칙 1로 강제된다.
- 규칙 6(상태 머신 전이)은 **ArchUnit으로 강제되지 않는다.** 애그리거트에 세터를 두지 않는 것은
  현재 코드 리뷰와 PR 체크리스트로만 지켜진다. 도메인 애그리거트가 처음 생기는 Phase 1에서
  `..domain..` 의 `set*` 메서드를 금지하는 규칙을 추가한다.
- 도메인 단위 테스트가 컨테이너·컨텍스트 없이 밀리초 단위로 돈다. 룰 엔진·비용 모델·시퀀서 테스트가 여기 속한다.
- `tools/benchmark` 가 `dispatch-service` 의 도메인만 의존해 전략을 실행할 수 있다.

**비용 (정직하게)**

- **매퍼 보일러플레이트가 실재한다.** 애그리거트마다 `toDomain` / `toEntity` 두 메서드를 손으로 쓴다.
  필드 하나를 추가하면 **도메인·엔티티·매퍼 세 곳**을 고쳐야 하고, 매퍼에서 빠뜨려도 컴파일러가 잡아 주지 않는다.
  → **완화책: 애그리거트마다 왕복(round-trip) 매핑 테스트를 의무화한다.**
  도메인 → 엔티티 → 도메인이 동등해야 한다는 단일 테스트가 누락 필드를 잡는다. 이것이 없으면 이 결정은 위험하다.
- **더티 체킹을 쓸 수 없다.** 유스케이스가 명시적으로 `save()` 를 호출해야 하며, 호출을 잊으면 조용히 저장되지 않는다.
  → 통합 테스트에서 "변경 후 재조회" 어설션으로 방어한다.
- **낙관적 락 `version` 을 도메인이 들고 다녀야 한다.** 순수 도메인에 영속성 개념이 새어 들어오는 지점이며,
  이 결정의 가장 불편한 타협이다. 값 객체로 감싸 의미를 명시한다.
- **초기 코드량 증가.** Phase 1~3의 구현 속도가 느려진다. 이것은 실제 비용이고, 위 이득과 맞바꾼 것이다.

**되돌리는 방법**

통합으로 되돌리려면 엔티티 클래스에 도메인 메서드를 옮기고 매퍼를 삭제한 뒤 ArchUnit 규칙 1을 완화하면 되며,
**서비스 단위로 점진 적용이 가능하다**(`dispatch-service` 는 제외). 반대로 이 결정을 유지하는 한
`tools/benchmark` 는 `dispatch-service` 의 `domain` 패키지만 의존한다 — 이 의존 관계가 결정의 준수 여부를 알려주는
카나리아 역할을 한다. 벤치마크 모듈이 Hibernate를 필요로 하기 시작하면 경계가 깨진 것이다.
