## 맥락

§9.1 표는 39행이고, 대시보드와 알림(§9.4)은 그 표의 이름을 쓴다. 표와 코드를 잇는 것은 셋이었다 — 그리고 셋 다
표를 **읽지 않았다**.

- **`DawnlineMetrics`** 는 「§9.1 표 전체」라고 적힌 11개 상수였고 **어느 서비스도 쓰지 않았다.**
  `DawnlineMetricsTest` 는 같은 11개를 손으로 옮긴 목록과 비교했다(7-0 A30). 근거: 관측(재현됨) — 표에 행을 하나 더해도 초록이었다.
- 실제 이름은 여덟 곳의 점 표기 상수(`DispatchMetrics` · `MessagingMetrics` · `OrderMetrics` · `TrackingMetrics` ·
  `FulfillmentMetrics` · `OnTimeRatioGauges`(지금 `KpiGauges`) · `InternalToken` · 정리기 셋)에 흩어져 있었고, 서비스마다 `Counter.builder` ·
  `Gauge.builder` · `registry.gauge` 를 직접 불렀다(45곳).
- **라벨**은 표의 넷째 칸에 산문으로만 있었다.

대조가 없는 동안 갈라진 것이 다섯이다. 넷은 이 ADR 의 검사가 처음 돌 때 빨갛게 나왔고, 하나는 대시보드를 그리려고 서비스를 긁다가 나왔다(근거는 각 줄).

1. **히스토그램이 켜져 있지 않았다.** `management.metrics.distribution.percentiles-histogram` 의 키가 Prometheus 이름
   (`dawnline_plan_duration_seconds`)이었는데, Spring 의 `PropertiesMeterFilter` 는 **미터 이름**(`dawnline.plan.duration`)의
   접두사로 맞춘다. 근거: 관측(재현됨) — 같은 타이머를 두 키로 등록해 긁었더니 앞의 키에서는 `_bucket` 이 없고 뒤의 키에서는
   있었다. §9.4 의 「계획 시간 p95 > 45s」 알림이 읽을 버킷이 없었다. `ObservabilityResourcesTest` 는 YAML 에 그 **문자열이
   있는가**를 봤다.
2. **§9.1 이 닫힌 라벨의 값을 모른다 — 다섯 자리.** 근거는 둘로 갈린다.
   - 카탈로그 ↔ §9.1 대조가 빨갛게 냈다(근거: 관측(재현됨)).
     - `dawnline_ops_commands_total{action}` 의 표는 넷을 적었는데 코드는 여섯이다(`CLOSE_WAVE` · `REQUEUE_OUTBOX` — ADR-054 와
       ADR-015 후속 정정이 더했다).
     - `dawnline_promise_revised_total{cause}` 는 표에 둘이 있고, 코드는 불변식이 깨졌을 때 셋째 값 `unknown` 을 낸다.
   - 카탈로그를 처음 쓸 때 표의 산문만 보고 적은 값이 틀렸고, **등록 헬퍼의 값 검사가 테스트에서 실패해** 드러났다
     (근거: 관측(재현됨)). 대조가 막으려던 바로 그 갈라짐을 이번에는 사람이 만들었고, 헬퍼가 잡았다.
     - fulfillment 의 `ServiceTier` 에는 `NEXT_DAY` 가 있다.
     - `dawnline_geo_lookups_total{index}` 는 GEO 둘이 아니라 `fc` · `zone`(권역 캐시) · `wave_lock`(웨이브 락)이다 — 이름과
       달리 fulfillment 의 Redis 폴백 셋이 함께 쓰는 카운터다.
3. **라벨이 열린 카운터에 건 알림이 부재를 다루지 않았다.** `dawnline_event_processed_total{outcome="dlq"}`(§9.4 「DLQ 신규
   > 0」)는 `consumer`·`eventType` 이 열린 집합이라 미리 등록할 수 없다. §9.1 「짝」이 적은 `cancel_too_late{camp}` 와 같은
   모양인데, 그 문단은 하나만 알고 있었다. 근거: 추정 — 규칙 식이 아직 없었으므로 틀린 식이 돈 적은 없다. 결정 3 의 검사가
   이 모양을 **라벨 칸에서** 찾아낸다.
4. **상태 게이지가 GC 에 사라졌다.** Micrometer 는 게이지의 상태 객체를 **약한 참조**로 든다. 7-0c 의 IT 에서 정리기가 GC 된
   뒤 `dawnline_route_plans_stuck` 이 `NaN` 을 냈다. 근거: 관측(재현됨). 그 PR 은 테스트가 정리기를 필드로 잡아 두게 했다 —
   **테스트의 우회**다. 운영에서도 같은 결함이 가능하다. 스프링 빈은 컨텍스트가 강하게 잡지만, 람다나 임시 객체를 대상으로
   등록한 게이지는 GC 뒤 조용히 `NaN` 이 된다. fulfillment · ops-api 의 같은 모양 테스트는 「세기 전에는 `NaN`」을 검사하는데,
   그 `NaN` 은 정리기가 GC 돼도 나오는 값이다. 대상이 사라져도 검사가 통과한다(§13 축 10 의 변종).
5. **HTTP 버킷도 없었다.** §9.4 의 Order Intake 는 주문 API p99 를 그리는데, 서비스를 긁어 보니 `http_server_requests_seconds`
   에 `_bucket` 이 없었다(근거: 관측(재현됨) — order-service 컨텍스트의 `/actuator/prometheus`). 맥락 1 과 같은 부류다 —
   그리는 쪽이 읽을 것이 있는지를 아무도 긁어 보지 않았다. 카탈로그 밖의 Spring 미터라서 헬퍼가 켤 수 없고, 속성 파일에서
   **미터 이름**(`http.server.requests`)으로 켠다. 버킷이 실제로 있는지는 Compose 스모크(`make obs-check`)가 본다.
6. **§9.4 가 그리라고 적은 것에 §9.1 의 행이 없었다** (2026-09-25 추가). Delivery 의 「실패 · 라우트 진행」이다. 대시보드
   대조는 「패널이 쓰는 이름은 §9.1 에 있다」를 보므로, 이름이 없는 항목은 텍스트 패널로만 남을 수 있었다 — 첫 판이 그렇게
   했고, 그것은 **꺼 둔 검증의 패널판**이다. 근거: 관측(재현됨) — 패널을 그리며 §9.4 의 항목을 §9.1 과 맞대 보다 드러났다.
   두 행을 더했다: `dawnline_kpi_delivery{camp, outcome}`(정시율과 같은 스냅숏의 결과 수)와 `dawnline_routes{camp, status}`
   (`rm_routes` 의 진행 집계 — 라우트 단위가 아니다, `routeId` 는 열린 라벨이다). 둘 다 표 → 카탈로그 → 헬퍼를 지나고,
   나머지(등록 · 라벨 값 · 패널)는 대조 검사가 요구했다.

맥락 1 과 5 는 한 모양이다 — **알림과 패널이 존재하지 않는 시계열을 보고 있었다**(§13 축 12). 맥락 2 는 카탈로그가 라벨
집합을 넷째 칸으로 드는 이유가 첫 실행에서 증명된 사례다.

## 결정

### 1. 이름은 카탈로그 한 곳이다 — 항목의 칸은 넷

`libs/observability` 의 `DawnlineMetrics` 가 §9.1 의 **행마다** `DawnlineMetric` 하나를 든다.

| 칸 | 뜻 | 대조 |
|---|---|---|
| Prometheus 이름 | §9.1 의 첫 열 그대로 | 표 ↔ 카탈로그 **양방향**, 빼는 방식. `docs/DESIGN.md` 는 `test` 의 입력이다 |
| 타입 | `counter` · `gauge` · `histogram` | 표의 둘째 열 |
| Micrometer 이름 | 코드가 등록하는 이름(점 표기가 대부분이다 — 바꾸지 않는다) | `PrometheusNamingConvention` 에 **통과시킨 결과**가 첫 칸과 같다. 이름 대응을 주석이 아니라 레지스트리가 말한다 |
| 라벨 집합 | 키마다 **닫힘**(값 목록이 있다) 또는 **열림** | 표의 넷째 열 — §9.1 「라벨 칸의 문법」대로 읽는다 |

**라벨 칸이 넷째인 이유**: 열린 라벨과 닫힌 라벨을 카탈로그가 구별해야, 알림이 걸린 카운터마다 **「미리 등록하는가 /
알림 식이 부재를 다루는가」**를 코드가 판정한다(결정 3). 맥락 3 의 DLQ 알림을 사람이 눈으로 찾은 것은 그 칸이 없어서였다.

서비스의 메트릭 상수(`DispatchMetrics.REPLAN` 등)는 없앤다. 부르는 자리는 카탈로그 항목을 직접 쓴다. 라벨 **값**의 상수(`OUTCOME_DLQ`
등)는 남는다 — 그것은 이름이 아니라 도메인의 어휘다.

### 2. 등록은 헬퍼 한 곳이다 — `DawnlineMeters`, 상태 게이지는 강한 참조

`DawnlineMeters` 가 `counter` · `timer` · `gauge` 셋을 내고, 등록 때 카탈로그와 대조한다.

- **타입**이 항목과 다르면 실패한다(카운터 항목을 게이지로 등록할 수 없다).
- **라벨 키 집합**이 항목과 다르면 실패한다. Prometheus 레지스트리도 같은 이름의 키 집합이 다르면 거부하지만(ADR-022),
  그것은 **둘째** 등록에서다. 헬퍼는 첫 등록에서 실패한다.
- **닫힌 라벨의 값**이 목록 밖이면 실패한다. 「닫혔다」는 「코드가 값을 전부 안다」는 주장이고, 그 주장이 틀린 자리는 등록이다.
  값이 enum 에서 오는 라벨은 **그 enum 과 카탈로그의 값 목록을 대조하는 테스트**를 짝으로 둔다. 그래야 enum 에 값이 느는 날
  운영의 첫 등록이 아니라 빌드가 실패한다.
- **`histogram` 항목은 `publishPercentileHistogram()`** 으로 등록한다. 타입 칸이 곧 버킷이다 — 속성 파일의 키가 이름과
  맞는지에 기대지 않는다(맥락 1). 속성 파일의 `percentiles-histogram` · `percentiles` 는 지운다.
- **게이지는 `strongReference(true)`** 로 등록한다. 상태 객체의 수명을 레지스트리가 잡는다. 대가는 레지스트리가 사는 동안
  그 객체가 남는 것이고, 등록하는 쪽이 전부 싱글턴이라 새는 것이 없다. `registry.gauge(…)` 형태는 쓰지 않는다 —
  그 API 에는 강한 참조를 거는 칸이 없다.

**우회는 ArchUnit 규칙 11 이 막는다.** 헬퍼(`com.dawnline.observability..`) 밖에서 Micrometer 의 `*.builder` ·
`MeterRegistry.counter/timer/gauge/summary/…` 를 부르지 않는다. 대상은 다섯 서비스와 `libs/messaging` · `libs/web` 이다. 위반
표본은 `libs/common` 의 `archunit/samples/bad` 에 둔다.

**의존 방향.** `libs/messaging` · `libs/web` 이 `libs/observability` 를 참조하게 된다. `libs/observability` 가 웹·OTel
스타터를 끌고 오면 `tools/sim-runner`(웹이 아닌 CLI)가 그것을 받는다. 그래서 둘을 옮긴다.
- OTel 스타터는 `dawnline.spring-service` 규약으로 옮긴다. 다섯 서비스가 그대로 받는다.
- 웹 스타터는 `compileOnly` 로 바꾼다. `MdcFilter` 의 자동 설정은 이미 `@ConditionalOnWebApplication` 이다.

### 3. 알림이 걸린 카운터 — 닫혔으면 미리 등록하고, 열렸으면 식이 부재를 다룬다

§9.1 「짝 — 없는 시계열은 0 으로 보인다」를 카탈로그의 라벨 칸으로 판정한다.

- **닫힌 라벨만 가진 카운터**에 알림이 걸리면 기동 때 값의 조합 전부를 0 으로 등록한다. `DawnlineMeters.preregister` 가 그
  조합을 카탈로그에서 뽑는다. 이미 손으로 하던 셋이 여기로 온다: 레이트 리밋 · 내부 토큰 · 운영자 커맨드. 검사는 서비스의
  IT 가 한다 — 기동한 레지스트리에, §9.1 「emit 주체」가 그 서비스인 **알림 걸린 닫힌 카운터**의 조합이 전부 있는가.
- **열린 라벨이 하나라도 있는 카운터**에 걸린 알림은 식이 새 시계열의 첫 표본을 증가로 읽는다:

  ```
  increase(x[w]) > 0
    or
  (x unless x offset w)
  ```

  뒤의 절은 **창 w 전에는 없던 시계열**이다 — 1 로 태어난 시계열의 첫 증가를 `increase()` 가 읽지 못하는 자리를 덮는다.
  재기동으로 같은 라벨이 다시 태어나면 w 전의 표본이 있어 뒤의 절이 빠지고, 앞의 절이 카운터 리셋을 증가로 센다.
  `AlertRulesConsistencyTest` 가 규칙 파일의 식을 읽어 확인한다. 열린 카운터를 참조하는 알림은 이 모양이어야 하고, 예외는
  이유와 함께 적는다.
- 게이지에는 이 구별이 없다 — 게이지는 기동 때 등록하거나(`*_stuck` · 나이 · 파티션) 값이 생길 때 나타나는 것이 뜻이다
  (`plan_cost` · `wave_orders`).

`increase()` 가 1 로 태어난 시계열의 첫 증가를 못 읽는다는 것은 이 결정의 전제다. 근거: 관측(재현됨) — `PrometheusRulesIT`
가 실제 Prometheus 컨테이너로 Micrometer 레지스트리를 긁는다. 미리 등록한 카운터와 처음 셀 때 만든 카운터를 같은 순간
올리면, `increase()` 는 앞의 것만 읽는다. 같은 실행에서 규칙 파일의 `DawnlineCancelTooLate` 는 뒤의 것에 울린다.

## 고려한 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| 게이지만 헬퍼로 (처음 제안의 범위) | 카운터 이름이 대조 밖에 남고 다음 갈라짐이 거기서 난다. A30 의 대조가 「표 → 카탈로그 → 헬퍼」로 끝까지 이어지려면 **모든** `dawnline_*` 미터가 그 길을 지나야 한다 |
| 소스의 문자열 리터럴을 긁어 표와 대조 | 이름은 점 표기라 표의 이름과 다르다. 토픽 이름 · 설정 접두사(`dawnline.dispatch…`)와도 섞인다. 타입과 라벨은 소스에서 보이지 않는다 |
| 기동한 서비스의 `/actuator/prometheus` 를 긁어 대조 | 열린 라벨의 카운터는 사건 전에는 없다 — 대조가 「지금 있는 것」만 본다. 결정 3 의 IT 는 **알림 걸린 닫힌 카운터**에만 이 방식을 쓴다. 그 부분집합에서는 「기동 때 있어야 한다」가 규칙이기 때문이다 |
| 테스트가 대상 객체를 필드로 잡는다 (7-0c) | 테스트의 우회다. 운영의 같은 결함이 남고, 다른 테스트의 `NaN` 검사는 계속 대상 없이 통과한다 |
| `MeterFilter` 가 카탈로그 밖의 이름을 거부 | 스프링 컨텍스트가 있는 곳에서만 돈다 — 단위 테스트의 `SimpleMeterRegistry` 는 지나간다. 운영에서 예외를 내는 필터는 미터를 조용히 버리거나 유스케이스를 깨뜨리는데, 둘 다 원인에서 멀다 |
| 대시보드 JSON 을 파일째 비교(스냅숏) | Grafana 가 저장할 때 키를 재정렬하고 id 를 붙인다 — diff 가 뜻 없이 커진다. 대조는 JSON 을 파싱해 **메트릭 이름 집합**으로 한다. 커밋된 파일은 프로비저닝 전용이다(UI 에서 저장하지 않는다 — `deploy/compose/README.md`) |

## 결과

**장점**

- §9.1 이 처음으로 코드의 입력이 된다. 표에 행을 더하면 카탈로그 · 등록 · 대시보드 · 규칙 중 빠진 곳이 빨갛다.
- `histogram` 이 타입 칸에서 온다. p95 알림이 읽을 버킷이 생긴다.
- 게이지의 `NaN` 이 다시 「모름」 하나만 뜻한다.
- 열린 카운터에 걸린 알림이 첫 사건을 놓치지 않는다. 그 판정이 사람의 눈이 아니라 라벨 칸에서 나온다.

**비용**

- 45곳을 기계적으로 옮긴다.
- 닫힌 라벨의 값 목록이 카탈로그 · §9.1 · enum 세 곳에 있다. 셋은 대조되지만, 값 하나를 더하는 PR 은 세 곳을 같이 고쳐야
  초록이 된다. 의도한 마찰이다.
- 닫힌 라벨에 목록 밖의 값이 오면 **등록이 실패한다** — 운영에서는 그 유스케이스가 예외를 낸다. enum 대조 테스트가 빌드에서
  먼저 막는 것이 전제다. enum 이 아닌 문자열로 값을 만드는 자리(`result.name()` 등)는 그 대조가 없으면 이 비용을 그대로 진다.

**재검토 지점**

- 서비스가 인스턴스 여럿으로 뜨면(7-0 A16) 열린 카운터의 `unless … offset` 은 인스턴스 라벨마다 따로 판정한다. 한
  인스턴스가 새로 뜬 것도 「새 시계열」이다. 그 인스턴스가 사건을 하나 세면 울리는 것이 맞지만, 식이 인스턴스 합으로 바뀌면
  (`sum by`) 이 절을 다시 본다.

**되돌리는 방법**

카탈로그와 헬퍼는 되돌리지 않는다 — 되돌리면 표와 코드가 다시 서로를 보지 않는다. 값 검증(결정 2 셋째)은 헬퍼 한 곳에서
끌 수 있고, 끄면 닫힌 라벨은 「주장」이 아니라 「설명」이 된다.
