## 맥락

§4.4 는 릴레이를 이렇게 적었다: 폴링 100ms, 배치 500, `FOR UPDATE SKIP LOCKED`. 그리고 **한 문장을
전제로 달아 두었다** — "릴레이는 서비스당 단일 활성 인스턴스를 전제로 한다. 현 단계는 인스턴스
1개로 이 전제가 자동 충족되며, 스케일아웃 전에 리더 락을 도입한다."

그 전제는 지금까지 **아무것도 강제하지 않은 채로** 성립하고 있었다. 인스턴스가 하나라서다.

### `SKIP LOCKED` 가 막는 것과 막지 못하는 것

`SELECT … FOR UPDATE SKIP LOCKED` 는 두 인스턴스가 **같은 행**을 집는 것을 막는다. 그래서 중복
발행은 일어나지 않는다.

막지 못하는 것은 **키 단위 순서**다. 두 인스턴스가 각각 다른 행을 집으면, 같은
`partition_key` 를 가진 두 행이 서로 다른 프로세스에서 서로 다른 시점에 `send` 된다. Kafka 가
보장하는 것은 *한 프로듀서가 한 파티션에 보낸 순서*이므로, 프로듀서가 둘이면 그 보장 밖이다.
§4.5 가 "같은 `orderId` 의 이벤트는 순서대로 온다" 고 적어 둔 것이 바로 그 지점에서 깨진다.

깨지면 무엇이 나쁜가. §4.5 의 순서 보장은 소비자 쪽 여러 결정의 전제다. ADR-017 이 주문 상태
머신에 순서 뒤바뀜 흡수를 넣은 것은 **토픽이 다른 이벤트들 사이**의 순서를 포기한 것이지, 같은
토픽·같은 키 안의 순서까지 포기한 것이 아니다. 그 안까지 흔들리면 흡수 규칙이 무엇을 흡수하는지
정의되지 않는다.

### 그래서 이것은 스케일아웃 전에 들어가야 한다

인스턴스를 2개로 올리는 사람은 `docker compose up --scale` 을 치는 사람이고, 그 사람은 §4.4 의
전제 문장을 읽지 않는다. **읽지 않아도 안전한 상태**로 만들어 두는 것이 이 ADR 의 목적이다.

## 결정

### 1. 릴레이는 배치 전에 매번 리더십을 확인한다 (Redis `SET NX` + 갱신)

키는 `lock:relay:{service}`(§7.2), 값은 인스턴스 토큰(UUIDv7), TTL 기본 30초. 획득과 갱신을
**한 번의 왕복**으로 한다:

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
  redis.call('PEXPIRE', KEYS[1], ARGV[2])
  return 1
end
if redis.call('SET', KEYS[1], ARGV[1], 'NX', 'PX', ARGV[2]) then
  return 1
end
return 0
```

`GET` 으로 확인한 뒤 `PEXPIRE` 하면 그 사이에 TTL 이 만료되고 다른 인스턴스가 키를 잡을 수 있고,
그러면 이쪽의 `PEXPIRE` 가 **남의 리더십 시계를 늘린다.** 100ms 마다 도는 호출이라 그 창은 이론이
아니다. 해제도 같은 이유로 Lua 다(비교 후 삭제) — `RedisWaveLock` 과 같은 판단이다.

**폴링이 곧 갱신이다.** 별도의 갱신 스케줄을 두지 않는다. 릴레이는 100ms 마다 도는데 TTL 이
30초이므로 갱신 여유가 300배이고, 갱신 작업을 따로 두면 "폴링은 도는데 갱신이 죽은" 상태가
새로 생긴다. 상태를 하나 줄이는 쪽을 골랐다.

**TTL 은 전송 타임아웃보다 길어야 한다.** 리더십은 배치 *전에* 확인하고 배치 *중에는* 확인하지
않으므로, TTL 이 한 배치의 최대 소요보다 짧으면 배치 도중 리더가 바뀔 수 있다 — 락을 켠 채로
두 인스턴스가 동시에 발행하는 상태다. 기본값 30초 대 10초이고, 그 관계는 설정 바인딩이 기동 시
검증한다(`Outbox` 레코드의 compact constructor).

TTL 30초를 고른 두 번째 이유: **리더가 죽었을 때 교체까지 걸리는 시간의 상한**이 그 값이고,
§9.4 의 "outbox 지연 > 30s" 알림과 **같은 눈금**이다. 교체가 제때 되면 알림이 울리지 않고,
울린다면 교체도 안 된 것이다. 알림을 새로 만들지 않아도 되는 이유가 여기 있다.

**정상 종료는 리더십을 내려놓는다.** `OutboxRelay` 가 `AutoCloseable` 이고 스프링이 빈 소멸 시
부른다. 그러면 배포 중 발행 공백이 TTL(30초)이 아니라 다음 폴링(100ms)이 된다.

### 2. 락이 거는 것은 **발행뿐**이다

메트릭 갱신과 오래된 행 정리는 리더가 아니어도 돈다. 이 락이 지키는 것은 <em>순서</em>이고,
순서를 가진 것은 발행밖에 없다. 게이지는 인스턴스마다 자기 값을 내야 하고(팔로워의 지연도
보여야 한다), 정리는 어느 인스턴스가 해도 결과가 같다.

### 3. 판정 불가는 팔로워가 아니라 **세 번째 상태**다

`Leadership` 은 `LEADER` / `FOLLOWER` / `UNKNOWN` 셋이다. 발행을 멈추는 <em>결정</em>은 뒤의 둘이
같지만 **봐야 할 곳이 정반대다** — `FOLLOWER` 는 정상(다른 인스턴스가 일하는 중)이고 `UNKNOWN` 은
Redis 장애다. 하나로 접으면 대시보드에서도 로그에서도 그 둘을 구별할 수 없다.

게이지 `dawnline_outbox_leader{service}` 가 `1 / 0 / -1` 로 그대로 노출한다(§9.1). 로그는
**상태가 바뀔 때만** 남긴다 — 100ms 마다 "리더가 아닙니다" 를 찍으면 로그가 사라진다.

### 4. **Redis 장애는 fail-closed 다** — `RedisWaveLock` 과 반대다

이 저장소에는 이미 Redis 락이 하나 있고 그것은 fail-**open** 이다(`lock:wave`, §7.2). 같은
자료구조인데 반대로 정한 이유는, **실패했을 때 잃는 것이 다르기 때문이다.**

| | `lock:wave` (fail-open) | `lock:relay` (fail-closed) |
|---|---|---|
| 락 없이 진행하면 잃는 것 | 중복 마감 시도 | **키 단위 순서(§4.5)** |
| 그것을 DB 가 막아 주는가 | **그렇다** — `FOR UPDATE` + 상태 전이 | **아니다** — `SKIP LOCKED` 는 중복만 막는다 |
| 멈추면 잃는 것 | **컷오프 시각** — 지나가면 돌아오지 않는다 | **지연뿐** — 행은 남고 복구되면 이어서 나간다 |
| 그래서 | 진행한다 | 멈춘다 |

불변규칙 7 은 "Redis 가 사라져도 DB 로 정확성이 회복되게 하라" 이다. 웨이브 락에서는 그 회복
경로가 실제로 있어서 fail-open 이 규칙을 지키는 형태였다. 여기에는 **회복 경로가 없다.** 그런
자리에서 규칙이 요구하는 것은 없는 폴백을 지어내는 것이 아니라 **멈추는 것**이다 — 폴백이 있는
척하는 코드는 규칙을 지키는 것이 아니라 규칙이 무엇을 지키려 했는지를 지운다.

멈춤은 보이지 않게 두지 않는다. `dawnline_outbox_lag_seconds` 가 오르고 §9.4 의 알림이 그대로
잡는다. 그리고 **되돌릴 수 없는 손실(순서)과 되돌아오는 손실(지연)** 중에서 후자를 고른 것이다.

### 5. 락을 켠 채로 Redis 가 없으면 **기동에서 실패한다**

`StringRedisTemplate` 이 없는데 `leader.enabled=true` 면 애플리케이션이 뜨지 않는다. 조용히
"항상 리더" 로 떨어뜨리지 않는 이유: **없는 락을 있다고 믿는 것이 락이 없는 것보다 나쁘다.**
스케일아웃한 날 아무 신호 없이 §4.5 가 깨지고, 그때 깨진 것은 로그가 아니라 이벤트 순서다.
5c 리뷰에서 나온 문장이 정확히 이것이었다 — "켜져 있다고 믿는 게이트는 없는 게이트보다 나쁘다."

끄는 길은 열려 있다. `dawnline.messaging.outbox.leader.enabled=false` 는 **"이 배포는 인스턴스가
하나다" 라는 선언**이고, 설정 파일에 적힌 문장이라 grep 된다. ops-api 가 그 값을 쓴다 — 이벤트를
발행하지 않는 서비스라(§3.2) 릴레이가 지킬 순서가 없고 Redis 도 붙이지 않기 때문이다. 그 서비스의
`application.yml` 주석은 "인스턴스가 하나다" 가 아니라 **"발행하지 않는다"** 라고 적는다. 이유가
다르면 없어지는 조건도 다르다.

## 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| **그대로 둔다** (인스턴스 1개 전제) | 전제를 지키는 것이 배포자의 기억뿐이다. 스케일아웃하는 사람은 §4.4 를 읽지 않고, 깨져도 예외가 나지 않는다 — 순서만 조용히 틀어진다 |
| **Redis 장애에 fail-open** | 그 순간 <em>모든</em> 인스턴스가 동시에 판정 불가가 되므로, 락이 가장 필요한 순간에 락이 사라진다. 그리고 순서 손실은 되돌릴 수 없다 |
| **락 없이 `partition_key` 해시로 인스턴스를 나눈다** | 인스턴스 수가 바뀌는 순간(배포·스케일) 같은 키가 다른 인스턴스로 옮겨 가고, 그 전환 구간에 정확히 같은 문제가 생긴다. 그것을 막으려면 결국 조정자가 필요하다 |
| **DB advisory lock** (`pg_advisory_lock`) | Redis 를 안 늘려도 된다는 장점은 있으나, 세션 수명에 묶인 락이라 커넥션 풀과 상호작용이 미묘하다(반납된 커넥션이 락을 들고 있다). 그리고 §7.2 는 이미 조정(coordination)을 Redis 의 역할로 정해 두었다 |
| **Kafka 트랜잭션/EOS** | ADR-006 이 이 프로젝트에서 쓰지 않기로 정했다. 게다가 EOS 는 중복을 없앨 뿐 <em>두 프로듀서의 순서</em>를 정해 주지 않는다 |
| **리더 선출 라이브러리**(Curator·Spring Integration `LockRegistry` 등) | 의존을 하나 더 늘린다. 여기서 필요한 것은 `SET NX` + Lua 두 줄이고, 이미 같은 형태의 락이 저장소에 있다(`RedisWaveLock`) |
| **갱신 전용 스케줄 작업** | "폴링은 도는데 갱신이 죽은" 상태가 새로 생긴다. 폴링(100ms)이 TTL(30s)보다 300배 잦아 폴링 자체가 갱신으로 충분하다 |

## 결과

**좋아지는 것**

- 인스턴스를 늘려도 §4.5 가 유지된다. 릴레이는 한 번에 하나만 발행한다.
- 발행이 멈춘 이유가 값으로 보인다(`dawnline_outbox_leader` 1/0/-1).
- 배포 중 발행 공백이 TTL 이 아니라 폴링 주기다(정상 종료의 `stepDown`).

**나빠지는 것 — 적어 둔다**

- **발행 경로가 Redis 에 의존하게 됐다.** Redis 가 죽으면 이벤트가 나가지 않는다. 이것은 부작용이
  아니라 결정 4 그 자체이고, 값은 지연으로 지불된다. Compose 의 Redis 가 단일 인스턴스라 그
  가용성이 곧 발행 가용성의 상한이 됐다는 뜻이기도 하다.
- **테스트가 Redis 를 요구한다.** 발행이 브로커까지 가는 것을 보는 IT 들(`OutboxRelayIT`,
  `OrderPublishIT`, `PlanExecutionIT`)이 이제 Redis 컨테이너를 띄운다. `OrderPublishIT` 에는
  "Redis 는 있으나 없으나 발행 경로는 같다" 는 주석이 있었고 **이 ADR 이 그 문장을 거짓으로
  만들었다** — 주석을 고치는 대신 락을 끄는 선택지도 있었지만, 락을 끄고 통과하는 발행 테스트는
  운영 경로를 테스트하지 않는다.
- **리더 전환 구간에 `SKIP LOCKED` 가 다시 안전망이 된다.** TTL 만료와 새 리더의 획득 사이에는
  이전 리더가 아직 배치 중일 수 있다. 그 구간에서 중복 발행을 막는 것은 여전히 `SKIP LOCKED` 이고,
  순서는 그 짧은 구간에 한해 보장되지 않는다. 완전한 배제는 fencing token 을 소비자까지 들고
  가야 가능한데, at-least-once + 멱등 소비(ADR-006) 위에서 그 비용을 낼 자리가 아니다.

**재검토 지점**

- 인스턴스를 실제로 2개 이상으로 올리는 시점(Phase 7 `peak-day`). 그때 `dawnline_outbox_leader`
  의 전 인스턴스 합이 **항상 1** 인지 본다. 2 가 관측되면 TTL 과 배치 소요의 관계가 깨진 것이다.
- Redis 장애 카오스 시나리오(`make chaos-redis`, Phase 7)에서 **지연은 오르되 유실·중복은 0** 인지.
  이 ADR 이 지연으로 지불하기로 한 값이 실제로 지연에서 그치는지를 그때 확인한다.

## [후속 정정 — Phase 4 착수] 락을 PostgreSQL advisory lock 으로 옮긴다

| 항목 | 내용 |
|---|---|
| 정정일 | 2026-09-05 (원 결정과 같은 날, 리뷰에서) |
| 무엇이 바뀌나 | **조정자만** — Redis `SET NX` → `pg_try_advisory_lock` |
| 무엇이 그대로인가 | 결정 1(배치 전 매번 확인)·2(락이 거는 것은 발행뿐)·3(세 상태) |
| 사라지는 것 | 결정 4 의 fail-open/fail-closed 딜레마, 결정 5 의 기동 실패, TTL·갱신·`leader.enabled` |

### 무엇이 틀렸나

위 결정 4 는 **Redis 에 두는 한** 옳다. 락 없이 진행하면 키 단위 순서를 잃고 DB 에는 그 폴백이
없으므로, 멈추는 것이 맞다. 틀린 것은 그 앞 단계다 — **락을 Redis 에 둔 것.**

릴레이 리더 선출은 **서비스 내부** 조정이다. 조정에 참여하는 것은 한 서비스의 릴레이
인스턴스들뿐이고, 그들은 정의상 **같은 DB** 를 공유한다(불변규칙 3: 서비스는 자기 DB 만 쓴다).
그 DB 는 다른 아무 DB 가 아니라 **자기가 비우고 있는 outbox 가 들어 있는 바로 그 DB** 다.

그러면 `pg_try_advisory_lock` 이 정확한 도구다.

- **TTL 이 없다.** 갱신도, 갱신이 죽은 상태도, TTL 과 배치 소요의 대소 관계도 없다. 위 결정 1 의
  마지막 세 문단과 설정 검증 하나가 통째로 사라진다.
- **시계가 없다.** 임차 기반 락(lease)은 두 시계가 같은 속도로 간다는 가정 위에 서는데,
  advisory lock 은 임차가 아니라 **세션의 존재** 자체다.
- **세션이 죽으면 락이 즉시 풀린다.** TTL 30초를 기다리지 않는다. 리더 교체가 TTL 상한이 아니라
  TCP 가 끊기는 속도로 일어난다.
- **fail-closed 딜레마가 사라진다.** DB 가 죽으면 리더십을 판정할 수 없지만, **그때는 발행할
  행도 읽을 수 없다.** 두 사건이 하나이므로 "멈출 것인가 진행할 것인가" 라는 질문이 성립하지
  않는다. Redis 에 두면 성립했다 — 조정자만 죽고 저장소는 살아 있는 상태가 존재했기 때문이다.

### 이것은 불변규칙 7 의 예외가 아니라 위반이었다

원 결정은 §13 매핑표 7번에 "명시적 예외 하나" 를 만들었다. 그 서술은 **회복 경로가 없는 자리**를
전제로 하는데, 회복 경로가 없었던 이유가 락을 그 자리에 둔 선택 그 자체였다. 즉 예외의 근거가
예외를 만든 결정에서 나왔다. 결과적으로 **Redis 단일 인스턴스의 가용성이 다섯 서비스 전체의
이벤트 발행 가용성의 상한**이 됐고(원 결정의 "나빠지는 것" 첫 줄이 그것을 정확히 적고 있다),
그것은 Redis 를 진실·필수 경로에서 뺀다는 규칙이 막으려던 바로 그 상태다.

**규칙이 예외를 요구하는 것처럼 보이면, 먼저 그 자리가 맞는지 의심한다.** 여기서는 자리가
틀렸다. 옮기고 나니 §7.2 의 모든 행이 다시 폴백 칸을 갖는다.

### ADR-005 의 기각 사유에 붙이는 각주

§16 의 ADR-005 행은 advisory lock 을 "서비스별 DB 분리 시 범위 한계" 로 기각했다. **그 사유는
서비스 <em>간</em> 락에만 해당한다** — 두 서비스가 같은 자원을 두고 다투면 각자의 DB 에 잡은 락은
서로를 보지 못한다. 맞는 말이다.

그런데 **이 시스템에는 서비스 간 락이 하나도 없다.** `lock:wave` 는 fulfillment 안, `lock:relay`
는 각 서비스 안, `route:{id}:atrisk:cooldown` 은 tracking 안이다(§7.2). 그래서 저 기각 사유는
현재 존재하는 어떤 락에도 적용되지 않는다. 일반 원칙으로 적힌 문장이 개별 사례에 자동으로
적용된다고 읽은 것이 이 정정의 원인이다.

`lock:wave` 를 함께 옮기지 않는 이유는 다르다. 저쪽은 **fail-open 이 맞는 락**이고(컷오프 시각은
지나가면 돌아오지 않는다), 정확성의 최종 보루가 이미 DB 의 `FOR UPDATE` + 상태 머신에 있다.
바꿀 이유가 없다.

### 구현 조건 넷

1. **전용 장수 세션.** 세션 수준 락이므로 커넥션을 풀에 반납하면 락이 **반납된 커넥션에 남는다** —
   그 커넥션을 다음에 빌리는 트랜잭션이 락을 들고 다니고, 아무도 그것을 풀지 않는다. 그래서
   커넥션 하나를 열어 **계속 들고 있는다.** 풀 슬롯 하나를 영구히 차지하며, 그 비용은 아래
   「결과」에 적었다.
2. **리더 여부는 매 사이클 DB 에서 도출한다.** 메모리 플래그를 두지 않는다 — 플래그와 실제 락
   상태가 어긋나는 창이 곧 §4.5 가 깨지는 창이다. 매 폴링마다 `pg_locks` 에 "이 백엔드가 그 키를
   쥐고 있는가" 를 묻고, 아니면 획득을 시도한다. **획득 시도를 먼저 하면 안 된다**:
   `pg_try_advisory_lock` 은 재진입 가능이라 이미 쥔 세션이 다시 부르면 **참조 수가 쌓이고**
   같은 수만큼 unlock 해야 풀린다.
3. **세션이 끊기면 재연결 후 재획득.** 판정 쿼리가 예외로 끝나면 그 사이클은 `UNKNOWN` 이고,
   커넥션을 버린 뒤 다음 사이클에 새로 연다. 버릴 때는 **닫기 전에 `pg_advisory_unlock_all()` 을
   시도한다** — 커넥션이 살아 있는 채로 풀에 돌아가면 락도 함께 돌아가기 때문이다. 세션이 이미
   죽었으면 그 호출도 실패하지만, 그때는 서버가 이미 락을 풀었다.
4. **`SKIP LOCKED` 는 그대로 인수인계 안전망이다.** 이전 리더의 세션이 끊기는 순간과 새 리더가
   획득하는 순간 사이에 이전 리더의 배치가 아직 전송 중일 수 있다. 그 구간의 중복을 막는 것은
   여전히 `SKIP LOCKED` 다. 원 결정의 「결과」 마지막 줄이 그대로 유효하다.

### 세 상태는 그대로다

`LEADER`/`FOLLOWER`/`UNKNOWN`. `UNKNOWN` 의 의미만 "Redis 장애" 에서 **"DB 세션 장애"** 로
바뀐다. 게이지 `dawnline_outbox_leader` 의 1/0/-1 도 그대로다. 값이 -1 이면 이제
`dawnline_outbox_unpublished` 도 함께 낡아 있을 것이다 — 같은 DB 를 읽지 못하니까. **그 동행이
곧 이 정정이 만든 성질**이고, 둘이 따로 노는 조합(리더 판정 불가인데 게이지는 신선함)은 더 이상
나오지 않는다.

### 사라지는 설정

`dawnline.messaging.outbox.leader.enabled` 와 `leader.ttl` 을 **없앤다.** 전자는 "Redis 가 없는
배포" 를 위한 탈출구였는데, 이제 조정자는 릴레이가 이미 쓰고 있는 DataSource 라 **없을 수가
없다**. 없는 조건을 위한 탈출구는 남겨 두면 다른 이유로 쓰이게 된다 — 그리고 이 저장소는 같은 날
"켜져 있다고 믿는 게이트" 를 하나 발견했다.

ops-api 의 `application.yml` 에서 그 블록을 지운다. ops-api 는 이벤트를 발행하지 않지만(§3.2)
릴레이가 도는 것 자체는 해롭지 않다(빈 테이블을 폴링한다). **그 서비스가 발행하지 않는다는
사실은 설정이 아니라 코드가 말한다** — `OutboxAppender` 를 부르는 곳이 없다.

### 결과 (정정 후)

**좋아지는 것 — 원 결정에 더해**

- 이벤트 발행 가용성이 Redis 에서 풀렸다. §8.4 의 "Redis 다운 → 성능 저하, 락 폴백" 이 다시
  맞는 말이 된다. **원 결정은 그 행을 고치지 않았다** — 발행이 멈추는 장애 모드를 새로 만들면서
  장애 모드 표를 갱신하지 않은 것이고, 이 정정이 그 어긋남도 함께 닫는다.
- 리더 교체 상한이 TTL(30초)에서 **세션 종료 감지 시간**으로 내려간다.
- `libs/messaging` 이 Redis 를 아예 참조하지 않는다. `compileOnly` 의존과 Lua 두 개, 자동설정의
  중첩 조건 클래스가 사라진다.
- **테스트가 Redis 를 요구하지 않는다.** 원 결정의 "나빠지는 것" 둘째 줄이 되돌아간다 —
  `OutboxRelayIT`·`OrderPublishIT`·`PlanExecutionIT` 가 컨테이너를 하나씩 덜 띄운다.

**나빠지는 것 — 적어 둔다**

- **커넥션 풀 슬롯 하나를 영구히 쓴다.** 릴레이를 켜는 서비스는 풀 크기에 +1 이 필요하다.
  Hikari 의 `maxLifetime` 은 **사용 중인** 커넥션을 회수하지 않으므로 이 세션은 은퇴하지 않는다.
- **트랜잭션 풀러(PgBouncer transaction mode)와 함께 쓸 수 없다.** 세션 수준 락은 세션이 고정될
  때만 의미가 있다. 이 저장소는 풀러를 쓰지 않지만, 넣는 날 이 락은 `session` 모드나 별도 접속을
  요구한다. 되돌리는 비용이 여기 있다.
- **판정에 왕복이 하나 는다.** 리더는 폴링마다 `pg_locks` 조회 1회(팔로워는 2회)를 추가로 낸다.
  `pg_locks` 는 메모리 뷰이고 100ms 주기라 부하로 보이지 않지만, 공짜는 아니다.

**재검토 지점**

- 인스턴스를 실제로 2개 이상으로 올리는 시점(Phase 7 `peak-day`). `dawnline_outbox_leader` 의 전
  인스턴스 합이 **항상 1** 인지 본다. 원 결정의 재검토 지점과 같지만 이제 2 가 관측될 경로는
  TTL 이 아니라 **커넥션 풀러를 끼워 넣었을 때**뿐이다.
- `make chaos-redis`(Phase 7)에서 **발행이 멈추지 않는지**. 원 결정에서는 이 시나리오가 "지연은
  오르되 유실·중복 0" 을 확인하는 것이었는데, 정정 후에는 **지연도 오르지 않아야 한다.**
