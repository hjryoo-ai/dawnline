# ADR-021 — 권역 시드는 order-service 지오코더의 출력 집합에서 파생한다 (권역 91개)

## 맥락

fulfillment-service 는 주소의 geohash5 로 `zones` 를 찾아 캠프를 정한다(§5.2 4단계).
찾지 못하면 그 주문은 `UNSERVICEABLE`(`NO_ZONE_MATCH`)이 되어 배차되지 않는다.

그 주소 좌표를 만드는 것은 order-service 의 `PostalPrefixGeocoder` 스텁이다(§5.1).
우편번호 앞 2자리 앵커 19개 × 세 번째 자리 10단계(각 0.008°) × 주소 문자열 해시로 만든
지터(±0.004°)를 더한다.

**부록 A 는 권역을 60개(캠프당 6)로 적어 두었다. 그런데 그 지오코더가 실제로 만들어 낼 수 있는
geohash5 셀을 세어 보면 91개다.**

```
좌표 범위: 위도 37.1600–37.7800 · 경도 126.6100–127.2200
geohash5 셀 91개 (접두어당 4~8개)
```

60개를 손으로 고르면 최소 31개 셀이 어느 권역에도 걸리지 않는다. 그 셀에 떨어진 주소로 들어온
주문은 **전부** `UNSERVICEABLE` 이 되고, Phase 2 의 DoD("주문 200건이 자동으로 웨이브에 편입")는
바로 거기서 깨진다.

이것은 스텁 두 개가 서로를 향하고 있어서 생기는 결합이다. 그러나 **데모 전체를 조용히 무너뜨릴 수
있는 결합**이고, 무너지는 방식이 예외가 아니라 "정상적인 UNSERVICEABLE" 이라 더 나쁘다 —
설계된 실패 경로와 구별되지 않는다.

## 결정

### 1. 권역 목록을 손으로 고르지 않고 지오코더의 출력 집합에서 파생한다

권역 = `PostalPrefixGeocoder` 가 만들어 낼 수 있는 geohash5 셀 전체. **91개다.**
부록 A 의 60은 어림수였고, 실제 값으로 고친다.

### 2. 셀 → 캠프는 최근접 캠프, 캠프 → FC 도 최근접 FC

캠프 10개는 지오코더 앵커의 분포를 덮도록 배치하고, 91개 셀을 각각 가장 가까운 캠프에 붙인다.
결과는 캠프당 6~13개다. FC 3개에 붙는 캠프 수는 **2 / 5 / 3** 이 된다 — 부록 A 가 적어 둔
"FC당 3~4" 와 다른데, 수도권 우편번호 19개 접두어 중 8개가 서울이라 캠프도 서울에 몰리기
때문이다. 균형을 맞추려고 서울 캠프를 먼 FC 에 붙이는 것은 숫자를 위해 지리를 버리는 일이다.

FC 후보가 하나뿐이면 §5.2 5단계의 `GEOSEARCH` 가 발화하지 않는다. 그 단계는 **캠프의 FC 가
1~3단계 필터(티어·냉장·재고)에서 떨어졌을 때의 대체 선택**으로 읽는다 — 그렇게 읽어야 `geo:fc`
적재와 5단계가 죽은 코드가 되지 않는다.

### 3. 이 결합을 두 서비스 각각의 테스트로 고정한다

지오코더의 출력 집합을 `contracts/seed/order-service-geohash5.txt` 에 생성물로 커밋한다.

- **order-service**: 자기 지오코더의 출력 집합이 그 파일과 **정확히 같은지** 검사한다.
  앵커 표를 고치면 여기서 깨지고, 메시지가 fulfillment 시드를 함께 고치라고 말한다.
- **fulfillment-service**: 시드된 `zones` 가 그 파일의 모든 셀을 **덮는지** 검사한다.

`contracts/openapi/order-service.yaml` 과 같은 취급이다 — 생성물이지만 커밋하고, 코드와 어긋나면
테스트가 깨진다. 어느 한쪽만 고치는 변경이 조용히 통과하지 못하게 하는 것이 목적이다.

### 4. `UNSERVICEABLE` 경로는 `NO_ZONE_MATCH` 가 아닌 곳에서 태운다

권역이 전부 덮이면 `NO_ZONE_MATCH` 는 사실상 발생하지 않는다. 그렇다고 그 경로가 검증되지 않으면
안 되므로, 시드를 `OUT_OF_STOCK` 이 실제로 나오도록 구성하고(품절 SKU) 나머지 사유는 통합 테스트가
직접 상태를 만들어 태운다. 구체는 Phase 2 의 시드·FC 선택 구현에서 정한다.

## 고려한 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| **권역 60개를 손으로 고르고 나머지는 `UNSERVICEABLE` 로 둔다** | DoD 가 부분적으로만 만족된다. 더 나쁜 것은 "설계된 실패" 와 "시드가 모자란 것" 이 같은 값(`NO_ZONE_MATCH`)으로 나와 **구별할 수 없게** 된다는 점이다 |
| **지오코더의 지터·스텝을 줄여 셀 수를 60 이하로 만든다** | 이미 머지·테스트된 order-service 의 동작을 시드 편의를 위해 바꾸는 것이다. 게다가 주소가 좁은 곳에 뭉쳐 Phase 3 의 stop 통합·경로 최적화가 비현실적으로 쉬워진다 — 최적화 품질 비교가 무의미해진다 |
| **권역 키를 geohash4 로 넓힌다** | 셀이 커져 수는 줄지만 §5.2 DDL(`CHAR(5)`)·부록 C(권역 = geohash5)를 함께 바꿔야 하고, 권역 하나가 약 20 km 가 되어 캠프 단위 병렬성(§6.7)의 기반이 무너진다 |
| **권역을 요청 시 자동 생성** | `zones` 는 fulfillment 가 소유하는 **참조 데이터**다. 요청이 참조 데이터를 만들면 "이 권역은 왜 생겼나" 를 추적할 수 없고, 시드와 런타임 데이터가 섞인다 |
| **양쪽에 셀 목록을 각자 적어 둔다** | 같은 목록이 두 곳에 있으면 한쪽만 고치는 날이 온다. 그것이 정확히 이 ADR 이 막으려는 사건이다 |

## 결과

**장점**

- 데모의 주문 200건이 전부 웨이브에 편입된다. Phase 2 DoD 가 그대로 성립한다.
- 어느 한쪽을 고치면 그 자리에서 테스트가 깨진다. 결합이 문서에만 적혀 있지 않고 **실행된다**.

**비용**

- 권역이 60 → 91 로 늘었다. 부록 A 를 고쳤고, FC 당 캠프 수도 "3~4" 가 아니라 2/5/3 이다.
- `contracts/` 에 이벤트·OpenAPI 가 아닌 세 번째 종류의 생성물이 생긴다(§12 저장소 구조 갱신).
- 이 파일의 존재가 **스텁 두 개가 서로를 향하고 있다**는 사실을 드러낸다. 실제 서비스라면
  지오코딩은 외부 서비스이고 권역은 운영 데이터라 이런 파일이 필요 없다. 감추지 않고 남겨 둔다 —
  포트폴리오에서 이 결합을 설명할 수 있는 것이 감춘 것보다 낫다.

**되돌리는 방법**

`zones` 가 진짜 권역 데이터로 바뀌는 시점(지오코딩을 외부 서비스로 교체하는 때)에 이 파일과
두 테스트를 지운다. 지우면 드리프트가 조용해지므로, 지우는 조건은 "권역이 더 이상 지오코더의
출력에 의존하지 않을 때" 하나뿐이다.
