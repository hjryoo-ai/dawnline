## 맥락

표의 제목은 「가상 스레드(I/O) + ForkJoin(CPU) 분리」였다. 두 축은 다른 질문이다.

- **CPU 축 — 계획 안의 병렬.** ADR-035 가 병렬 단위를 정했다(클러스터가 아니라 배정의 차량 후보 · 개선의 라우트 쌍). 그리고 게이트를 먼저 걸었다:
  **`peak` 에서 예산이 물리고 잘림의 대가 ≥ 1% 이면 만든다.** 잰 값은 **+0.83%** 였다(근거: 관측 — `phase4-peak-gate.md`). 이월했다.
- **I/O 축 — 가상 스레드.** 소비는 리스너 동시성 3(파티션 수와 맞춘다), 계획의 계산은 트랜잭션 밖이고(ADR-064) 쓰기는 커넥션 풀이 상한이다.
  I/O 에서 **스레드가 모자란 순간을 본 적이 없다** — 주문 API 의 꼬리는 풀 대기와 콜드 스타트였다(Phase 1 · A2).

## 결정

1. **계획 안의 병렬은 만들지 않는다.** 7-4 의 창 시나리오 다섯에서 80 계획이 전부 `FULL` 이었고 가장 긴 계산이 16.6초(예산 30초)였다 —
   A12 의 조건(잘림의 대가 ≥ 1%)이 켜지지 않았다(근거: 관측).
2. **가상 스레드는 켜지 않는다**(`spring.threads.virtual.enabled` 없음). 켜서 줄 것이 없다 — 병목은 스레드가 아니라 커넥션 풀이고,
   가상 스레드는 풀 대기를 더 많은 동시 대기로 바꿀 뿐이다(근거: 추정 — 켜고 재지 않았다). 도구 셋(Redis 선연결 · sim-runner 의 기사 · 운전)은
   가상 스레드를 쓴다 — 블로킹 대기가 수천 개인 자리이고, 결정 2 는 서비스의 요청 · 소비 경로에 관한 것이다.
3. **병렬의 단위는 캠프다.** `wave.closed` 의 키가 캠프라 캠프 간 계획은 파티션별로 자연 병렬이고, 한 캠프의 계획은 차례다 — ADR-075 의
   파티션 논거가 이 성질에 기댄다.

## 대안

| 안 | 기각 사유 |
|---|---|
| 클러스터 단위 병렬 | 클러스터는 독립이 아니다 — 재삽입과 라우트 간 개선이 클러스터를 가로지른다(ADR-035) |
| 라우트 쌍 병렬(ADR-035 의 단위) | 게이트 아래(+0.83%) — 만들 값이 측정으로 없다 |
| 서비스 전체 가상 스레드 | 병목이 풀이다. 켜면 `ThreadLocal`(MDC · 트랜잭션 동기화)과 핀닝을 검증할 일이 생기고 얻는 것이 보이지 않는다 |

## 재검토 지점 (포트폴리오 범위 밖 — 다시 여는 조건)

- **FAST 전환이 생기거나 예산에 잘리는 계획이 1% 이상의 대가를 낼 때**(A12 · B10 과 같은 수) — 그때 ADR-035 의 단위로 만든다.
- **스레드 풀 고갈이 관측될 때**(톰캣 · 리스너 스레드가 모두 대기인데 풀은 비어 있다) — 그때 가상 스레드를 켜고 핀닝을 잰다.
