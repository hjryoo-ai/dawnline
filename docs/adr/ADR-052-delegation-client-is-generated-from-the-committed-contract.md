## 맥락

ops-api 는 운영자 커맨드를 코어 서비스 REST 로 위임한다(§5.5, 불변규칙 4 — 동기 REST 는 ops-api →
코어 방향만). 이번 묶음이 붙이는 것은 엔드포인트가 이미 있는 셋이다.

| 커맨드 | 코어 | 계약 문서 |
|---|---|---|
| 재계획 | dispatch `POST /api/v1/plans/{waveId}/run` | `contracts/openapi/dispatch-service.yaml` (Phase 6-0) |
| stop 재배정 | dispatch `POST /api/v1/routes/{routeId}/stops/{orderId}/reassign` | 같은 문서 |
| 주문 취소 | order `POST /api/v1/orders/{orderId}/cancel` | `contracts/openapi/order-service.yaml` |

Phase 6-0 이 dispatch 의 문서를 만든 이유가 이 클라이언트다 — 작업 1 을 먼저 했으면 위임 클라이언트는
컨트롤러 소스를 읽고 만들어졌고, 그 순간 §11 의 「문서가 계약이다」가 dispatch 에만 성립하지 않았다.
**ops-api 는 그 문장의 첫 소비자다.** 소비자가 문서를 읽고 만든 코드가 문서가 바뀌었을 때 깨지면, 그
문장은 검사가 된다.

## 결정

### 1. 생성을 시도한다 — 채택 기준은 시도 **전에** 여기 적는다

기준을 시도 뒤에 적으면 결과를 보고 기준을 고르게 된다. 그래서 이 절은 첫 생성보다 먼저 커밋한다.

**후보는 하나다**: openapi-generator 의 `spring` 생성기, `library=spring-http-interface`. 생성물이
`@HttpExchange` 인터페이스와 모델이고, 호출은 Spring Framework 7 의 `HttpServiceProxyFactory` 와
Boot 가 구성한 `RestClient` 가 한다 — HTTP 계층과 직렬화기를 생성물이 들고 오지 않는다. 같은 도구의
`java` 생성기(`library=restclient`)는 자기 `ApiClient` 와 Jackson `ObjectMapper` 를 생성물 안에 가져와
Boot 4 의 Jackson 3 과 둘째 직렬화기가 생긴다 — 후보로 삼지 않는다(**근거: 추정** — 생성해 보지 않았다).

**채택한다** — 아래가 전부 참일 때:

1. **표준 템플릿.** `templateDir` 를 쓰지 않고, 생성 뒤 파일을 고치는 후처리가 없다.
2. **설정은 생성기가 문서화한 옵션만.** `configOptions` 의 공개 키는 쓴다. `typeMappings`·`importMappings`
   로 생성물의 타입을 **이 저장소의 클래스로 바꿔 끼우는 것은 심(shim)으로 친다**.
3. **생성물이 그대로 컴파일된다.** 생성물에 이 저장소의 린트(`-Xlint:all … -Werror`)를 걸지는 않는다 —
   그것은 우리가 쓴 코드의 규약이지 호환의 기준이 아니다. 생성물은 **자기 컴파일 단계**를 가지고, 그
   단계가 경고를 내면 그 수를 이 ADR 에 적는다. 오류는 기각이다.
4. **Jackson 3 왕복이 통과한다.** 앱이 쓰는 `JsonMapper`(Boot 4 자동 구성)로 — 요청 모델은 직렬화한
   JSON 의 키가 계약 스키마의 속성 이름과 같고, 응답 모델은 계약 스키마대로 적은 JSON 을 역직렬화해 값을
   잃지 않는다. 호출 경로(`RestClient` + 프록시)를 한 번 거쳐서 본다.
5. **새 런타임 의존이 없다.** 생성물이 요구하는 라이브러리가 ops-api 의 클래스패스에 이미 있어야 한다
   (예: `jackson-databind-nullable` 이 필요하면 그것은 Jackson 2 모듈이라 호환 심이다 — 기각).

**기각한다** — 하나라도 거짓이면. 손댄 템플릿이나 심은 생성기 버전을 올릴 때마다 다시 깨지는 **두 번째
계약**이고, 그때는 손으로 쓴 인터페이스 + YAML 대조 테스트가 더 정직한 가드다. 그 대조 테스트는 §13
「서로를 비추는 목록에는 대조 검사를 둔다」의 한 자리가 된다 — 경로·메서드·파라미터·스키마 속성을
**YAML 에서 전부 읽고** 인터페이스의 것과 맞춘다(열거하지 않는다).

**채택하면 조건 셋**:

- 입력은 살아 있는 엔드포인트가 아니라 **커밋된 `contracts/openapi/*.yaml`** 이다. 생성 태스크는 그
  파일을 입력으로 선언한다 — 문서만 바뀐 빌드에서도 생성과 컴파일이 다시 돈다.
- 생성기 버전은 `gradle/libs.versions.toml` 에 고정한다.
- 생성물은 커밋하지 않는다 — `build/` 아래의 빌드 산출물이다.

### 2. 토큰은 스크립트가 찍고 ops-api 는 검증만 한다

설계에 사용자 저장소가 없다. 로그인 엔드포인트는 없는 것을 새로 만드는 것이고, 개발 프로필에서만 켜도
「프로필이 꺼져 있다」는 조용한 전제가 하나 는다. 그래서:

- 발급은 `make token ROLE=…` — 로컬 시크릿(환경변수)으로 HS256 토큰을 찍는다. **만료 12시간**: 데모
  토큰이 저장소나 스크린샷에 남았을 때의 반경이다.
- ops-api 는 서명·만료·역할 클레임만 본다. 시크릿이 없거나 짧으면(HS256 은 256비트) **기동하지 않는다** —
  열린 채로 뜨는 것보다 뜨지 않는 것이 낫다.
- ops-web 은 토큰을 붙여 넣는 설정 화면 하나로 충분하다. 그것이 「이 화면에는 인증이 있지만 사용자
  관리는 범위 밖」이라는 문장의 UI 판이다.

### 3. 감사 행은 위임 **전에** 쓰고, 결과를 모르면 `UNKNOWN` 이다

- 위임 전에 별도 트랜잭션으로 `PENDING` 행을 커밋한다. 순서가 반대면 위임과 기록 사이에 죽었을 때
  **기록이 사라진다** — 코어는 적용했는데 누가 했는지 아무도 모른다. 먼저 쓰면 적어도 `PENDING` 이 남는다.
- 결과는 넷이다: `SUCCEEDED`(2xx) · `REJECTED`(코어가 4xx 로 거절 — 적용되지 않았다) ·
  `FAILED`(**연결이 맺어지지 않았다** — 요청이 코어에 닿지 않은 것이 확실한 유일한 경우) · **`UNKNOWN`**(그
  밖의 전부 — 응답 전 타임아웃, 응답 도중 끊김, 코어의 5xx). **모름을 값으로 접지 않는다** — 타임아웃을
  `FAILED` 로 적으면 적용된 커맨드를 「안 됐다」고 말하게 된다.
  (구현하며 정정: 처음 적은 판은 코어의 5xx 를 `FAILED` 에 넣었다. 5xx 는 「무언가 깨졌다」이지 「아무 일도
  없었다」가 아니다 — 커밋 뒤 응답 직렬화에서 난 예외도 500 이다. **근거: 추정** — 그 경로를 재현하지는 않았다.
  그래서 `FAILED` 를 「닿지 않은 것이 확실한 경우」 하나로 좁혔다.) 그러면 결과 셋이 **서로 배타적인 사실**이
  된다: 안 닿았다(`FAILED`) / 닿았고 거절됐다(`REJECTED`) / 닿았는데 결과를 모른다(`UNKNOWN`). 대가는 코어
  버그의 500 도 사람이 해소해야 한다는 것이고, 그것은 맞게 감수하는 대가다 — 그 500 을 `FAILED` 로 접으면 실제로
  적용된 재계획을 「안 됐다」고 적는 감사 기록이 생기고, **그것은 기록이 없는 것보다 나쁘다.**
- 감사 행의 id 를 코어 호출에 상관 헤더(`X-Dawnline-Audit-Id`)로 싣고, 코어는 그것을 로그 MDC 의
  `auditId` 로 남긴다. 사람이 `UNKNOWN` 행을 해소할 때 **어디를 볼지가 그 id 로 정해진다**.

## 시도 결과 — 채택 (2026-09-24)

openapi-generator **7.25.0**(Gradle 플러그인, 카탈로그 고정). 기준마다 무엇을 보았는지:

| 기준 | 결과 | 근거 |
|---|---|---|
| 1. 표준 템플릿 | ✅ | `templateDir` 없음, 후처리 없음 |
| 2. 문서화된 옵션만 | ✅ | `useSpringBoot4`·`useJackson3`·`useJspecify`·`openApiNullable=false`·`useBeanValidation=false`·`annotationLibrary=none`·`documentationProvider=none` 등 전부 [생성기 문서](https://openapi-generator.tech/docs/generators/spring)의 공개 키. `typeMappings`·`importMappings` 없음 |
| 3. 그대로 컴파일 | ✅ | 자기 소스셋(`coreClients`)에서 `-Xlint:all` 로 **오류 0 · 경고 0**(dispatch 모델 19 · API 3, order 모델 12 · API 1) |
| 4. Jackson 3 왕복 | ✅ | `CoreClientsRoundTripTest` 32개 — 두 계약의 스키마 **전부**를 스키마대로 채워 읽고 다시 써서 같은 트리, 그리고 위임하는 세 연산을 `RestClient` + 프록시로 거쳐 요청 키 = 계약 속성 이름 · 응답 무손실 |
| 5. 새 런타임 의존 없음 | ✅ | 생성물의 import 는 `spring-web`·`jakarta.validation`·`jakarta.annotation`·`org.jspecify`·`com.fasterxml.jackson.annotation` 뿐 — 전부 ops-api 에 이미 있다. 마지막 것은 Jackson 3 도 그대로 쓰는 어노테이션 패키지이고, Jackson 2 의 `databind` 는 import 하지 않는다 |

**첫 시도는 실패했고, 그것은 기준 2 안에서 풀렸다.** 기본값(`useSpringBoot3`)으로 생성하자 51개 오류와
100개 경고가 났다 — `jakarta.validation` 이 생성물 소스셋에 없었고(ops-api 에는 있다), 경고는 전부 Spring 7
에서 폐기된 `org.springframework.lang.Nullable` 이었다. 생성기 문서에 `useSpringBoot4`·`useJackson3`·
`useJspecify` 가 있었고, 그 셋과 소스셋에 main 이 이미 가진 validation 을 거는 것으로 오류와 경고가 함께
0 이 됐다. 템플릿이나 심은 쓰지 않았다.

**왕복 검사의 음성 표본**: 생성 옵션에 `dateLibrary=legacy`(`java.util.Date`)를 넣자 32개 중 **8개가 빨갛다**
— 날짜 칸이 있는 모델 7개와 그것을 응답으로 받는 취소 연산이다. 날짜 칸이 없는 모델은 그대로 초록이다.
검사가 「Jackson 3 가 이 타입을 계약대로 쓰는가」를 실제로 본다.

**드러난 계약 문서의 거짓 하나 — 같은 PR 에서 고쳤다.** 두 문서의 `ProblemDetail` 스키마는 확장 멤버를
`properties` 라는 **중첩 객체**로 적었는데, 실제 본문은 Spring 의 `ProblemDetail` 믹스인이 그것을 **최상위**로
펼친다(`"code": "…"` 가 `type` 옆에 온다 — **근거: 관측(재현됨)**, tracking 의 `ScanApiIT` 가
`jsonPath("$.code")` 로 본다). 생성 모델은 문서대로 만들어졌으므로 실제 오류 본문을 읽으면 `code` 를 잃었다.

처음에는 「범위 밖」으로 적었다가 고쳤다. 이것은 **부재가 아니라 발행된 문서가 틀린 경우**이고, 「거짓은 아는
순간 고친다」가 Phase 5 에서 세운 규칙이다 — 그 규칙이 처음 적용된 사례가 정확히 「문서를 보고 만든 클라이언트가
오류를 파싱하지 못한다」였고, 첫 소비자가 지금 여기 있다. springdoc 이 맵을 중첩으로 그리는 것은 생성기의
오류이므로 **생성기 쪽에서** 고쳤다: `libs/web` 의 `ProblemDetailSchema`(`OpenApiCustomizer`, springdoc 을 쓰는
서비스 전부에 자동 구성 — 경로의 `/api/1` 을 되돌린 것과 같은 자리의 일)가 중첩 칸을 지우고 `code` 를 최상위에
두고 추가 칸을 허용한다. 세 서비스의 `OpenApiContractIT` 가 「확장 칸은 최상위」를 문서 쪽에서 대조하고,
customizer 등록을 빼면 그 검사와 「커밋된 문서가 코드와 같다」가 함께 빨갛다(음성 표본). 다시 생성한 모델은
`code` 칸과 `@JsonAnySetter` 로 나머지 확장 멤버를 받고, 왕복 검사는 이제 선언되지 않은 칸까지 본다.

**그래도 ops-api 는 거절 본문을 바이트 그대로 전달한다** — 이유가 바뀌었다. 처음 적은 이유는 「문서가 틀렸다」
였고 지금은 **프록시로서 옳다**이다: 운영자는 코어가 말한 것을 그대로 보고, 코어가 확장 멤버를 더해도 ops-api
에서 잘리지 않는다. 문서가 참이어야 한다는 것과 클라이언트가 그것으로 파싱해야 한다는 것은 다른 문장이다.

## 고려한 대안과 기각 이유

- **생성 없이 처음부터 손으로 쓴 인터페이스 + 대조 테스트** — 결정 1 의 기각 분기다. 처음부터 고르지
  않은 이유는 가드의 세기다: 대조 테스트는 *테스트가 보는 것*만 지키고, 생성은 *컴파일이 보는 것*을
  지킨다. 계약이 바뀌면 컴파일이 깨지는 것이 이 저장소가 가진 가드 중 가장 센 형태다.
- **살아 있는 엔드포인트(`/v3/api-docs`)에서 생성** — 빌드가 코어의 기동에 매이고, 무엇을 입력으로
  썼는지가 커밋에 남지 않는다. 커밋된 문서가 계약이다.
- **생성물 커밋** — 문서와 생성물이 서로를 비추는 두 목록이 되고, 대조 검사가 하나 더 필요해진다.
- **ops-api 의 개발 전용 `POST /auth/token`** — 결정 2.
- **위임 뒤 한 번만 기록** — 결정 3.

## 결과

**장점**
- 계약이 바뀌면 **컴파일이 깨진다.** 어댑터가 쓰는 연산·칸의 이름이 문서에서 바뀌면 `compileJava` 가
  실패한다 — 테스트가 보는 것만 지키는 대조 검사보다 센 가드다.
- 생성 태스크가 `contracts/openapi/*.yaml` 을 입력으로 가지므로 문서만 바꾼 빌드에서도 생성·컴파일이 다시 돈다.
- HTTP 계층은 Boot 4 의 HTTP Service Client(`@ImportHttpServices`, `spring.http.serviceclient.<그룹>`)가
  맡는다 — 관측(트레이스 전파)이 붙은 `RestClient` 를 쓰고, 프록시를 손으로 만들지 않는다.

**비용**
- 빌드 플러그인 하나(openapi-generator)와 소스셋 하나가 는다. 생성기를 올리면 생성물이 바뀔 수 있다 —
  그때 지키는 것이 왕복 검사와 위의 기준 표다. **기준 표를 다시 채우지 못하면 올리지 않는다.**
- 생성물은 `build/` 에만 있으므로 IDE 에서 처음 열면 빨갛다 — `./gradlew :services:ops-api:compileCoreClientsJava` 한 번.

**되돌리는 방법**: 결정 1 의 기각 분기다 — 쓰고 있는 세 연산의 인터페이스를 손으로 옮기고, YAML 에서 경로·
메서드·파라미터·스키마 속성을 전부 읽어 대조하는 테스트를 둔다. 어댑터는 인터페이스만 보므로 바뀌지 않는다.

## 재검토 지점

1. **생성기 버전을 올릴 때** — 기준 표(위)를 다시 채운다. 하나라도 거짓이면 올리지 않는다.
2. ~~**`ProblemDetail` 스키마가 실제 본문과 맞춰지면**~~ — **닫았다**(2026-09-24, 같은 PR). 문서는 이제 참이다.
   거절 본문은 그래도 바이트 그대로 전달한다 — 이유는 문서가 아니라 프록시라는 자리다(위 「시도 결과」).
3. **위임 커맨드가 는다면**(웨이브 조기 마감 — fulfillment 의 첫 운영 엔드포인트와 그 OpenAPI 문서) — 같은
   경로로 붙인다. 문서가 먼저이고, 생성 태스크의 `coreContracts` 에 한 줄이 는다.
4. **`UNKNOWN` 의 자동 해소 — `UNKNOWN` 이 실제로 쌓이면.** 위임 대상 셋은 전부 코어에서 상태를 다시 읽을 수
   있다: 재계획은 `waveId` 로 계획의 상태(`GET /plans/{planId}` — 웨이브에서 계획을 찾는 길이 필요하다), 재배정은
   두 라우트의 `revision`(`GET /routes/{routeId}`), 취소는 주문의 상태(`GET /orders/{orderId}`). 감사 id 로 코어
   로그를 사람이 뒤지기 전에 ops-api 가 코어 상태를 한 번 더 읽어 `UNKNOWN` 을 `SUCCEEDED`·`FAILED` 로 닫는
   경로가 있고, 그것은 **RB-07 이 하는 일을 코드로 옮기는 것**이다. 지금 만들지 않는 이유: `UNKNOWN` 은 타임아웃과
   코어의 5xx 에서만 나오고 둘 다 아직 관측된 적이 없다 — 없는 부하를 위한 경로는 그 자체가 검사할 것이 는다.
   **조건**: `dawnline_ops_commands_total{result="UNKNOWN"}` 가 운영(또는 Phase 7 peak-day)에서 사람이 따라가기
   어려운 빈도로 나타나면 다시 연다. 그때도 읽은 상태가 「이 커맨드의 결과」임을 가려야 한다 — 재배정의 `revision`
   이 오른 것이 이 커맨드 때문인지 다른 재계획 때문인지는 revision 만으로 알 수 없다.
   **첫 사례**(2026-09-24): DLQ 재처리([ADR-053](ADR-053-dlq-replay-is-addressed-to-the-failed-group.md)). 그 `UNKNOWN` 은 무엇을 다시
   읽을 필요도 없다 — 재처리 커맨드는 **멱등**이라(대상 그룹의 `processed_events` 가 두 번째를 막는다) 해소 방법이
   「다시 누르기」다. 위임 셋에서 이 지점이 여전히 열려 있는 이유가 그 대비로 보인다 — 재계획을 다시 누르면
   계획을 **다시** 세운다. 다시 누르기가 해소가 되려면 커맨드가 멱등이어야 한다.
