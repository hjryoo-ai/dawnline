## 맥락

두 번째 `peak-day`(2026-09-27, `dawnline-sim`)가 비활성화 409 로 끝났다 — `peak-sim` 차량 4대에 끝나지 않은 stop 이 남았다.
두 서비스의 사실을 대조하면(검증 표 V8 의 식, 아래 결정 5) **tracking 에서 `COMPLETED` 인 주문 20건이 dispatch 의 `PLANNED` stop
위에 있었다** — 라우트 3개, 전부 at-risk 재계획이 옮겨 온 자리다. 그 라우트의 기사는 같은 주문을 다시 찍었고 tracking 은 이미 끝난
주문이라 STALE 로 답했다(16건). 새 상태 이벤트는 나오지 않으므로 그 stop 은 영원히 `PLANNED` 다.

한 주문의 순서(유효 시각): tracking 이 `ARRIVED` · `COMPLETED` 를 14:59:45.23 · 45.73 에 적고 45.93 에 발행 → 재계획이 원 라우트의
쿨다운을 45.96 에 집음 → dispatch 가 두 상태를 46.00 · 46.08 에 처리 → 주문은 다른 라우트의 `PLANNED` stop 에 있다.

1. **기전 — 재계획의 쓰기는 옮길 stop 의 상태를 보지 않았고, 옮긴 뒤 원래 행을 지웠다.** `JdbcRouteMutations.moveOrder` 는 주문의
   연결(`route_stop_orders.stop_id`)을 대상 라우트의 새 stop(또는 같은 좌표의 stop)으로 옮기고 **비워진 원래 stop 행을 지운다**.
   앞선 보고에서 이것을 「라우트의 stop 행을 지우고 다시 넣는다」로 적었는데 **추정이었고 절반만 맞았다** — 다시 넣는 것이 아니라
   지우는 것이다. 경합은 두 순서로 일어나고, 둘 다 정정 전 코드에서 재현됐다. **근거: 관측(재현됨)** — `ReplanRaceIT` 를 먼저 쓰고
   정정 전 코드에서 돌렸다.
   - (가) **계산하는 동안 끝난 배송.** 재계획이 `PLANNED` 로 읽은 stop 이 쓰기 전에 `COMPLETED` 로 커밋된다. 쓰기는 상태를 보지 않고
     옮기고, 사실은 지워진 행과 함께 사라지며 새 자리는 `PLANNED` 다. IT: 남은 stop 을 계산 중에 끝내자 주문 2건이 `PLANNED` 에 남았다.
   - (나) **쓰기가 잡은 stop 에 도착한 배송.** 상태 반영이 옛 stop 을 읽은 뒤 쓰기의 락을 기다린다. 쓰기가 그 행을 지우고 커밋하면
     반영의 `UPDATE … WHERE id = ?` 는 **0 행을 고치고 조용히 끝난다**. IT: 쓰기 트랜잭션 안에서 멈춘 동안 반영을 스레드마다 보내자
     락 대기가 생겼고, 풀어 준 뒤 주문 2건이 `PLANNED` 에 남았다.
2. **같은 문장의 둘째 결함 — 합쳐진 stop 을 옮기면 주문마다 흩어진다.** `moveOrder` 는 새 stop 을 **후보의 좌표**로 만든다. §6.5 1단계는
   geohash7(약 153 m) 안의 주문을 한 stop 으로 합치므로 합쳐진 stop 의 주문들은 좌표가 서로 다르다 — 옮기면 한 stop 이 주문 수만큼의
   행이 된다. 뒤따르는 다시 쓰기(`rewrite`)는 **좌표로** 행을 찾으므로 대표 좌표와 같은 행 하나만 순번 · 시각을 받고 나머지는
   `createStop` 의 자리표시 시각과 `max(seq) + 1` 순번으로 남는다. **근거: 관측** — 같은 실행의 라우트 하나에 한 이동(`gainKrw` 1,824
   · `searchTruncated`)이 옮긴 주문 8건이 행 8개로 있고, 그중 7개의 `planned_arrival` 이 자리표시(재계획 시각)다. 기전은 코드 읽기.
   **합쳐진 stop 을 둘 이상 옮기면 커밋이 깨진다** — 다시 쓰기가 받지 못한 행의 `max(seq) + 1` 순번이 다시 매긴 순번과 겹쳐
   지연 UNIQUE `(route_id, seq)` 가 커밋에서 터지고, 재계획은 롤백 · 재전달을 되풀이한다. **근거: 관측(재현됨)** — `ReplanIT` 의
   짝 픽스처(지점마다 주문 둘)를 정정 전 코드에서 돌리자 「부분 재계획을 반영했다」가 90초 동안 20번 찍히고 매번 오프셋 0 으로
   되감겼다. 라우트는 그대로였다.
3. **재계획의 계산이 트랜잭션 안에 있다** — 7-0 B13, ADR-064 재검토 지점 1. 1 의 (가) 창이 계산 시간만큼 열려 있고, 그동안 커넥션 하나를
   쥔다. **근거: 관측(재현됨)** — `ReplanRaceIT` 가 계산 안에서 멈춘 동안 `idle in transaction` 백엔드 1개를 봤다.

셋은 뿌리가 같다 — **쓰기가 계산의 전제를 다시 보지 않고, 행의 정체성을 지키지 않는다.**

## 결정

### 1. 재계획도 읽기 · 계산 · 쓰기 셋이다 — ADR-064 와 같은 구조

- **읽기**(읽기 전용 트랜잭션): 쿨다운(비교만) · 라우트 머리 · 계획 · 닿은 stop · 원 라우트와 후보 라우트의 stop · 차량 · 룰 ·
  **계획의 라우트마다 `revision`**. 아무것도 쓰지 않는다.
- **계산**(트랜잭션 없음): `RelocateSearch`. 커넥션을 쥐지 않는다.
- **쓰기**(트랜잭션 하나, 멱등 게이트가 감싼다): 결정 2 의 재검증 → 쿨다운 집기 → 옮기기 → 두 라우트 다시 쓰기 · 개정 발행 · 설명.

유스케이스가 게이트(`WriteGate`)를 받는다 — `RunPlanUseCase` 와 같은 형태이고, 그래서 그 타입을 `port.in` 의 독립 타입으로 옮긴다.
`at-risk` 리스너는 `IdempotentConsumer.runOnce` 를 넘긴다. 카운터(`dawnline_replan_total` · `dawnline_at_risk_deviation_mismatch_total`)는
게이트가 돌아온 뒤, 곧 커밋 뒤에 센다 — 편차 대조는 읽기 단계에서 하지만 **세는 것은 쓰기가 커밋된 뒤다**(같은 `eventId` 의 재전달이
두 번 세지 않는다).

### 2. 쓰기는 옮길 stop 을 잠그고 다시 본다 — 바뀌었으면 버리고 `stale` 로 센다

쓰기 트랜잭션의 첫 일:

1. 옮길 stop 을 **주문으로** 찾아 `FOR UPDATE` 로 잡는다(`lockStopOf` — 운영자 재배정이 이미 쓰는 문장). 상태가 `PLANNED` 가 아니거나,
   주문이 더는 원 라우트에 없거나, 주문이 취소됐으면 버린다. **ADR-026 결정 2 의 넷째 분기(「`ARRIVED` 이후는 거부」)를 개정에 넓힌
   것이다** — 취소가 끝난 배송을 되돌리지 않듯 재계획도 끝난 배송을 옮기지 않는다.
2. 계산이 본 라우트(원 · 대상)의 행을 `FOR UPDATE` 로 잡고 `revision` 이 읽기 때와 같은지 본다. 다르면 버린다 — 그 사이 취소 · 재배정 ·
   다른 재계획이 순서나 소속을 바꿨고, 계산한 순서는 지금 라우트의 것이 아니다.

버린 결과는 `dawnline_replan_total{outcome="stale"}` 로 센다(일곱째 갈래 — 합이 트리거 수라는 성질은 그대로다). **쿨다운은 집지 않는다**
— 계산의 전제가 바뀐 것이지 재계획을 한 것이 아니고, 집으면 그 라우트는 10분 동안 다시 풀 수 없다. 다음 at-risk 가 새 사실로 다시 푼다.

잠그는 순서는 stop → 라우트다. 상태 반영은 stop 하나만 잡고, 취소 · 재배정도 stop 을 먼저 잡고 라우트를 뒤에 고친다 — 같은 순서다.

### 3. 옮기는 것은 행이다 — `route_id` · `seq` 를 고치고 stop id 를 지킨다

재계획은 stop 단위로 옮긴다(`RelocateSearch.Move` 는 그 stop 의 주문 전부). 그래서 쓰기는 주문을 새 stop 으로 옮기지 않고 **stop 행의
`route_id` 를 대상 라우트로 바꾼다**. 순번은 다시 쓰기가 매긴다(`(route_id, seq)` UNIQUE 는 지연 제약 — V3). 행의 좌표 · 약속창 ·
작업 시간 · 상태 · `actual_at` · 주문 연결이 그대로 따라간다.

- 결정 2 의 락을 기다리던 상태 반영은 커밋 뒤 **같은 id 의 행**을 고친다 — 사실은 옮겨 간 행에 적힌다(1 의 (나)가 닫힌다).
- 합쳐진 stop 은 한 행 그대로 옮겨 간다(맥락 2 가 닫힌다).
- 같은 좌표의 stop 이 대상에 있어도 합치지 않는다. 옛 `moveOrder` 는 합쳤고 — 약속창이 다른 두 stop 이 한 약속창이 되는 자리였다.
  그래서 다시 쓰기는 **좌표가 아니라 주문으로** 행을 찾는다(라우트 안에서 주문은 한 행에만 있다). 취소의 시각 재계산(`retime`)도 같은
  방법으로 바꾼다 — 같은 좌표의 두 행이 한 라우트에 있을 수 있게 된 뒤에는 좌표 열쇠가 둘 중 하나를 놓친다.

**셋을 함께 하는 이유.** 결정 2 만이면 (나)가 남는다 — 잠그고 `PLANNED` 를 확인해도 그 뒤 락을 기다린 반영은 지워진 행을 고친다.
결정 3 만이면 (가)가 남는다 — 계산 뒤에 끝난 stop 을 그대로 옮긴다. 「상태 반영이 0 행이면 새 자리를 찾아 다시 쓴다」만이면 (가)의
사실은 되살릴 수 없다 — 이미 커밋된 행이 지워졌고 그 이벤트는 소비가 끝났다. **결정 3 이 이 부류를 구조적으로 없앤다** — 사실이 어느
행에 적히든 그 행이 살아 있다.

### 4. 쿨다운 — 읽기는 비교만, 쓰기는 한 문장으로 비교 · 갱신

ADR-046 결정 3 의 성질(두 at-risk 가 같은 창에서 둘 다 재계획하지 않는다)은 쓰기의 `tryStartReplan` 한 문장이 그대로 지킨다. 읽기
단계의 비교는 **계산을 아끼는 것**뿐이다 — 쿨다운 안이면 계산하지 않고 게이트만 지나 `cooldown` 으로 끝난다. 읽기에서 비었는데 쓰기에서
집지 못하면(그 사이 다른 at-risk 가 집었다) 계산을 버리고 `cooldown` 이다. `no-anchor` · `no-candidate` · `no-gain` · `truncated` 도
쓰기에서 쿨다운을 집는다 — 지금과 같다(「아무것도 안 했더라도 다시 시도할 값은 없다」, `ReplanIT`).

순서: 재검증(결정 2) → 쿨다운 집기 → 옮기기. 재검증이 먼저인 이유는 결정 2 의 「`stale` 은 쿨다운을 집지 않는다」다.

### 5. 검증 표 V8 — dispatch 의 `PLANNED` stop 중 tracking 에서 `COMPLETED` 인 주문 = 0

서비스 둘의 사실을 대조하는 첫 검증이다. dispatch 에서 주문마다 지금의 stop(가장 나중 stop id — `findAssignedStop` 과 같은 규칙)의 상태가
`PLANNED` 인 주문 집합, tracking 에서 `shipments.status = 'COMPLETED'` 인 주문 집합을 뽑아 교집합을 센다(서비스 사이 JOIN 없이 — V1 과
같은 방법). 범위는 T0 이후 주문(V1 의 주문 집합). 상태 이벤트는 비동기라 V1 · V7 처럼 `--wait` 동안 다시 잰다.

두 번째 `peak-day` 에 이 식을 대면 **20 — 첫 ✗** 다(맥락).

| 대안 | 기각 이유 |
|---|---|

| 상태 반영이 0 행을 고치면 새 자리를 찾아 다시 쓴다 | (가)의 사실은 되살릴 수 없다 — 커밋된 행이 지워졌고 그 이벤트의 소비는 끝났다 |
| 계산은 트랜잭션 안에 두고 옮길 stop 부터 잠근다 | 무엇을 옮길지는 계산이 정한다 — 먼저 잠그려면 남은 stop 전부를 계산 내내 잡아야 하고, 그동안 그 라우트의 상태 반영이 전부 선다(peak 에서 라우트당 수십 stop · 계산 수 초 — B13) |
| `SERIALIZABLE` 격리 | 직렬화 실패가 재계획 전체(계산 포함)의 재시도가 되고, 이 서비스의 다른 트랜잭션과 격리 수준이 갈린다. 필요한 것은 행 몇 개의 재검증이다 |
| `stale` 을 따로 두지 않고 `no-gain` 으로 접는다 | 「옮겨도 이득 없음」과 「계산의 전제가 바뀌었다」는 다른 말이다 — `truncated` 를 따로 둔 이유(§13 축 14)와 같다 |

## 결과

**좋아지는 것**

- 재계획과 동시에 도착한 배송이 사라지지 않는다 — `ReplanRaceIT` 의 두 순서가 정정 전 빨강 · 정정 후 초록.
- 합쳐진 stop 이 흩어지지 않고, 옮긴 행이 자리표시 시각으로 남지 않는다.
- 재계획의 계산이 커넥션을 쥐지 않는다(B13 이 닫힌다) — 같은 IT 가 계산 중 `idle in transaction` 0 을 본다.
- 검증 표가 서비스 둘의 사실을 처음으로 대조한다(V8).

**대가**

- 계산이 `stale` 로 버려질 수 있다 — 상한은 한 번의 계산(평가 2,000회)이다. 그 빈도가 `stale` 라벨이다.
- 한 라우트에 같은 좌표의 stop 이 둘 있을 수 있다 — 기사가 같은 건물을 두 번 들른다. 약속창이 다른 두 stop 이면 그것이 맞고, 같으면
  비용이 탐색에 이미 반영됐다(두 stop 사이 이동 0).
- `ReplanRouteUseCase` 의 모양이 바뀐다(게이트를 받고, 게이트가 건너뛰면 결과가 없다).

## 재검토 지점

1. **운영자 재배정(§5.3)의 `moveOrder` 는 여전히 비워진 stop 을 지운다.** 그쪽은 주문 하나를 옮기는 조작이라(stop 을 가를 수 있다) 결정 3 을
   그대로 쓰지 못하고, 잠그고 `PLANNED` 를 확인하지만(재배정 가드 — IMPLEMENTATION_PLAN 7-4 ④ 앞) 그 트랜잭션 동안 락을 기다린 상태 반영은 (나)와 같이 0 행을 고친다.
   **근거: 추정** — 코드 읽기, 재현하지 않았다. 창은 운영자 커맨드 하나의 트랜잭션이다. 같은 좌표 합치기도 그쪽에 남아 있다.
2. **`stale` 이 `applied` 에 견줄 만큼 잦으면** 재검증의 범위(라우트 `revision` 전체)가 너무 넓은 것이다 — 옮기는 stop 과 삽입 자리만 보는
   좁은 재검증을 본다.
3. **끝난 라우트가 재계획의 대상이 된다.** 후보 라우트는 「같은 계획의 다른 라우트 전부」이고 끝났다는 개념이 없다 — 두 번째 `peak-day` 에서
   모든 stop 을 끝낸 라우트 둘이 stop 을 받았다(근거: 관측 — 그 두 라우트의 앞 stop 은 tracking 에서 전부 `COMPLETED`, 받은 stop 은 스캔되지
   않았다). §6.8 2단계의 「진행 중 라우트 · 미출발 차량」에 「끝난 라우트」가 없다 — 이 ADR 의 범위 밖이고 7-0 표에 행으로 남긴다.
