# ADR-066 — 시뮬레이션은 스케줄이 아니라 시계를 옮긴다

## 맥락

`peak-day` 는 **컷오프 직전 버스트**다(부록 A). 컷오프는 코드의 상수다 — `TierSchedule` 이 DAWN 00:00 · SAME_DAY 10:00 · 14:00
(Asia/Seoul)을 적고, 설정할 자리가 없다. 그래서 7-4a 의 첫 계획은 셋 중 하나를 골라야 한다고 적었다:

- (a) **실제 컷오프 앞에서만 돈다** — 23:00–24:00 KST. 가짜 장치는 없지만 하루에 한 번만 돌 수 있다.
- (b) **컷오프 스케줄을 설정으로 연다** — 시뮬레이션만을 위한 스위치가 도메인에 생긴다.
- (c) **조기 마감으로 컷오프를 흉내 낸다** — 모든 마감이 `cause=manual` 이 되어 ADR-054 의 판정 데이터가 오염된다.

셋 다 한 가지를 전제했다: 「컷오프 직전은 **실제 시각**에만 온다」. 그 문장은 시계가 벽시계일 때만 참이다. 이 저장소는 불변규칙 12 로
시계를 **주입**한다 — 서비스 다섯과 sim-runner 가 `libs/messaging` 의 `dawnlineClock` 빈 하나에서 시각을 받는다. `PhaseThreeDoDIT`
가 09:00 KST 에 세운 시계가 이미 그 이음매를 쓴다.

## 결정

### 1. 옮기는 것은 시계다 — 스케줄 · 도메인 · 파이프라인은 그대로

`dawnline.clock.offset`(ISO-8601 기간, 기본 `PT0S`)이 `dawnlineClock` 에 더해진다 — `Clock.tick(Clock.offset(systemUTC, offset), 1µs)`.
컷오프 상수도, 웨이브 마감 스케줄러도, 계획도 **바꾸지 않는다**. 오프셋을 「실행 시작이 22:40 KST」가 되게 고르면 컷오프 직전 버스트가
**아무 때나** 돈다. (b) 의 설계 변경도, (a) 의 「하루 한 번」도 없다.

### 2. 한 값, 한 자리 — 그리고 서로를 비춘다

- 값은 compose 의 `x-service-env` 앵커에 있는 환경변수 **하나**(`DAWNLINE_CLOCK_OFFSET`)다. 다섯 서비스(와 sim-runner)가 같은 앵커를
  읽는다. 서비스마다 다른 오프셋은 「주문은 23:00 에 들어왔는데 웨이브는 22:00 에 닫혔다」 같은, 어느 서비스의 결함으로도 보이는 모순을 만든다.
- 기동 로그에 **유효 시각 한 줄**: `시계: 유효 시각 2026-09-26T13:40:00Z (2026-09-26T22:40+09:00) — 오프셋 PT7H12M, 시뮬레이션 프로필(ADR-066)`. 오프셋이 0 이어도 남긴다
  — 「이 로그는 어떤 시각에 있었는가」가 로그의 첫 질문이다.
- 게이지 `dawnline_clock_offset_seconds{service}`(§9.1). `make obs-check` 가 **서비스 다섯이 모두 이 게이지를 내고 값이 하나인지** 대조한다.
  같은 앵커에서 읽으니 같을 것이라는 문장은 적어 둔 문장일 뿐이다(CLAUDE.md 「서로를 비추는 목록에는 대조 검사를 둔다」).

### 3. 시뮬레이션 프로필 밖에서는 기동을 거부한다

오프셋이 0 이 아니면 Spring 프로필 `sim` 이 켜져 있어야 한다. 아니면 기동 실패다. 이 저장소에는 「운영 프로필」이 따로 없다 — 그래서
「운영이면 거부」가 아니라 **「시뮬레이션이라고 말한 곳에서만 허용」**으로 적는다. 앞의 것은 누군가 운영 프로필의 이름을 기억해야 지켜지고,
뒤의 것은 아무도 기억하지 않아도 지켜진다.

### 4. 시계는 하나다 — SQL 의 `now()` 를 걷어낸다

오프셋은 **JVM 의 시계**에만 닿는다. SQL 의 `now()` 는 DB 의 벽시계라, 그것과 주입 시계로 적은 값을 비교하면 오프셋만큼 어긋난다.
운영 코드에 셋이 남아 있었다:

| 자리 | 무엇이 틀렸나 | 근거 |
|---|---|---|
| `JpaOutboxRepository` 의 미발행 나이(`now() - min(created_at)`) | 오프셋만큼 **음수**가 된다 — `dawnline_outbox_lag_seconds` 가 음수면 `DawnlineOutboxLag` 가 영원히 조용하고, 7-3 카오스의 검증 표가 「지연 없음」으로 읽는다 | 관측(재현됨) — `OutboxLagIT` 를 옛 SQL 에 먼저 돌려 −28,799.95초(오프셋 8시간) |
| `JdbcRouteMutations.createStop` 의 `planned_arrival` · `planned_departure = now()` | 같은 트랜잭션의 `rewrite` 가 덮는 자리표시자다 — 값이 남지는 않지만, 남지 않는다는 것을 코드를 읽어야 안다 | 추정(코드 읽기) |
| `JdbcReferenceAdmin.updateRule` 의 `updated_at = now()` | 룰 이력의 시각이 다른 행들과 다른 시계에서 온다 | 추정(코드 읽기) |

셋 다 주입 시계의 값을 파라미터로 받는다. **KPI 뷰 · 보존 정리 · 예외 목록**은 이미 그랬다 — 「현재」를 `?` 로 받는다(확인: 운영 코드의
`now()` · `CURRENT_TIMESTAMP` · `CURRENT_DATE` 는 위 셋이 전부였다). 마이그레이션의 `now()` · `CURRENT_DATE` 는 이 규칙 밖이다 — 기동 때 한 번
도는 채우기이고, `DEFAULT now()` 가 붙은 칸 셋(`rm_waves.updated_at` · `rm_routes.updated_at` · `shipments.updated_at`)은 어댑터가 언제나
값을 적는다(기본값이 쓰이는 삽입이 없다). 재발은 `SqlUsesInjectedClockTest` 가 막는다 — 운영 소스의 SQL 에서 DB 시계 함수를 **빼는 방식**으로 찾고,
마이그레이션 제외는 그 이유와 함께 테스트에 있다.

### 5. 벽시계로 남는 것 — 사실은 주입 시계, 인프라는 벽시계

오프셋이 닿지 않는 것들이다. 고치지 않는다 — 이것들은 **사실의 시각**이 아니라 **인프라의 시간**이다. 경계가 문서에 있어야 한다:

| 벽시계 | 오프셋 아래에서 보이는 것 |
|---|---|
| JWT `iat` · `exp` (`tools/ops-token` 이 `date +%s` 로 찍고, ops-api 의 검증기도 벽시계) | 토큰 12시간은 실제 12시간이다. **검증기는 주입 시계를 쓰고 있었다**(`JwtTimestampValidator.setClock(clock)`) — 발급은 벽시계인데 검증이 오프셋 시계면 토큰이 오프셋만큼 일찍 만료되고, 오프셋이 12시간을 넘으면 방금 찍은 토큰이 이미 만료다(근거: 추정 — 코드 읽기). 빈이 벽시계를 넘기게 고쳤고 `OpsTokenScriptTest` 가 빈 메서드에 `Clock` 파라미터가 없음을 본다 |
| Redis TTL (at-risk 쿨다운 · 웨이브 락 임대 · GEO 적재 표식) | 쿨다운 5분은 실제 5분이다(ADR-046 과 같은 문장) |
| Kafka 레코드 타임스탬프 · 보존 | 브로커는 오프셋을 모른다 — 레코드 시각과 봉투의 `occurredAt` 이 오프셋만큼 다르다 |
| Prometheus 수집 시각 · 알림 `for` · Grafana 시간축 · Tempo 스팬 · 로그 타임스탬프 | 그래프의 x 축은 **실제 시각**이다. 「23:00 버스트」는 그래프에서 실제 시각에 찍힌다 — 유효 시각 = 실제 + `dawnline_clock_offset_seconds` |
| `Ids.newId()`(정적)의 UUIDv7 시간 성분 | id 정렬은 벽시계 순서다. 사실의 순서는 시각 칸이 말한다 |
| `@Scheduled` 의 간격 · HTTP · 커넥션 타임아웃 | 기간이지 시각이 아니다 — 오프셋과 무관하다 |

### 6. 시간은 뒤로 가지 않는다 — 시뮬레이션은 자기 볼륨에서 돈다

오프셋을 켜고 쓴 사실은 벽시계보다 **미래**다. 같은 볼륨으로 오프셋 0 에 돌아오면 시간이 뒤로 간다 — 유효 시각으로 컷오프가 지나 `CLOSED`
인 웨이브가 벽시계로는 아직 오지 않은 컷오프를 들고 있고, 그 컷오프로 들어오는 다음 실제 주문은 닫힌 웨이브를 만난다. 어느 서비스의 결함으로도
보이는 모순이다. 그래서:

- `make peak` 은 **자기 compose 프로젝트**(`COMPOSE_PROJECT_NAME=dawnline-sim`, 볼륨 `dawnline-sim_*`)에서 돈다. 개발 볼륨(`dawnline_*`)은
  오프셋을 한 번도 보지 않는다.
- 같은 시뮬레이션 프로젝트에서 연달아 돌 때(`normal-day` 뒤 `peak-day`) 오프셋은 **이미 적힌 가장 늦은 사실보다 뒤**의 22:40 KST 로 고른다 —
  다음 실행이 앞 실행의 컷오프를 다시 만나지 않는다.

## 대안

| 대안 | 기각 이유 |
|---|---|
| (a) 실제 23:00 KST 에만 돈다 | 반복 비용 — 하루 한 번, 로컬에서는 밤 11시. 측정은 여러 번 돌아야 읽힌다 |
| (b) 컷오프 스케줄을 설정으로 | 시뮬레이션만을 위한 스위치가 도메인(`TierSchedule`)에 생긴다 — 운영에서 켜질 수 있는 자리다 |
| (c) 조기 마감으로 컷오프를 흉내 | 모든 마감이 `cause=manual` — ADR-054 재검토 지점 1 의 데이터가 오염된다 |
| 시계를 빠르게(배속) | 계획 시간 · 소비자 랙 · 커넥션 대기는 실제 시간이다 — 배속한 시계 위에서 잰 p99 는 무엇의 p99 인지 말할 수 없다. 옮기기만 한다 |
| DB 의 시계도 옮긴다(`SET timezone` · faketime) | DB 는 공유 인프라다 — 옮길 수 있어도 결정 4 의 「시계는 하나」가 JVM 쪽 하나로 서는 편이 검사할 수 있다 |
| 개발 볼륨에서 그대로 | 결정 6 — 오프셋 0 으로 돌아오면 시간이 뒤로 간다 |

## 결과

- `peak-day` · `normal-day` 를 아무 때나, 연달아 돌린다. 스케줄 · 도메인 코드는 바뀌지 않는다.
- 새 설정 키 하나(`dawnline.clock.offset`), 새 게이지 하나(`dawnline_clock_offset_seconds`), 새 프로필 이름 하나(`sim`).
- 대시보드의 x 축은 실제 시각이다 — 7-4 리포트는 헤더에 오프셋을 적고 표의 시각을 **유효 시각**으로 적는다.
- `make peak` 은 개발 스택을 내린 뒤(`make down`, 볼륨 유지) 시뮬레이션 프로젝트를 올린다 — 컨테이너 이름이 고정이라 둘은 함께 뜨지 않는다.

## 재검토 지점

1. **벽시계 경계가 사실을 건드릴 때** — 결정 5 의 목록 중 하나가 사실의 판정에 들어오면(예: TTL 이 「언제 끝났다」를 결정하는 경로) 그 자리는
   주입 시계로 옮기거나 이 ADR 에 예외로 적는다.
2. **인스턴스가 둘 이상일 때** — 오프셋은 앵커 하나라 인스턴스를 늘려도 같지만, obs-check 의 「값이 하나」 대조가 인스턴스 라벨로도 모이는지 본다.
