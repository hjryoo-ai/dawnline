# ADR-009 — API 버전은 URL 경로 세그먼트

| 항목 | 내용 |
|---|---|
| 상태 | Accepted |

| 관련 문서 | `docs/DESIGN.md` §5.1 · §4.7 |

## 맥락

§5.1은 "API 버전은 URL 세그먼트 `v1` 기본. Spring Framework 7의 API Versioning 기능을 쓰되 URL
방식으로 통일한다" 라고만 적어 두었다. Phase 1에서 첫 컨트롤러를 만들며 그 문장을 코드로 옮겼고,
옮기는 과정에서 **문장만으로는 정해지지 않는 것 두 가지**가 드러났다.

1. 경로에 이미 `v1` 이 박혀 있는데 Spring 의 버저닝 기능을 켜서 무엇을 얻는가.
2. 버전 세그먼트를 <em>어디서부터</em> 세는가. 이 서비스에는 `/api/...` 말고 `/actuator/...` 도 있다.

## 결정

### 1. 버전은 경로 세그먼트다 — 헤더가 아니다

`POST /api/v1/orders`. 이유는 이 프로젝트의 성격에 있다. 헤더 버저닝은 브라우저 주소창·`curl`·
k6 스크립트·Swagger UI 어디서도 눈에 보이지 않는다. 데모와 면접에서 "지금 무엇을 부르고 있는가" 가
한눈에 보이는 편이 낫고, 그 가치가 헤더 버저닝의 장점(URL 이 리소스만 가리킨다)보다 크다.

### 2. 매핑 경로에 `v1` 을 박지 않고 `{version}` 자리표시자를 쓴다

```java
@RequestMapping(path = "/api/{version}/orders", version = "1")
```

리터럴 `v1` 로 두면 `/api/v2/orders` 가 **경로 매칭에서 먼저 떨어져 404** 가 된다. 실제로 그렇게
구현했다가 통합 테스트에서 확인했다 — 응답 본문은 `No static resource api/v2/orders` 였다.
그러나 사실은 "그런 리소스가 없다" 가 아니라 **"그 리소스는 있는데 그 버전은 지원하지 않는다"** 다.
자리표시자로 두면 버전 조건까지 도달해 400 으로 답한다. 클라이언트가 오타와 버전 불일치를
구분할 수 있어야 한다.

곁가지 하나: Spring 의 `SemanticApiVersionParser` 는 앞의 숫자가 아닌 문자를 버리므로
(`skipNonDigits`) 경로의 `v1` 과 `version = "1"` 이 그대로 맞아떨어진다. `v` 를 벗기는 코드를
우리가 쓸 필요가 없다.

### 3. 버전을 찾는 범위를 `/api/` 로 한정한다

```java
configurer.usePathSegment(1, path -> path.value().startsWith("/api/"))
```

술어가 없으면 **모든** 요청의 두 번째 세그먼트를 버전으로 읽으려 든다. `/actuator/health` 의 두 번째
세그먼트는 `health` 이고, 그것을 버전으로 파싱하려 들면 헬스 체크가 깨진다. 레디니스 프로브가
실패하면 배포가 멈춘다(§8.6). 이 결함은 통합 테스트 없이는 눈에 띄지 않으므로,
`OrderApiIT` 가 `/actuator/health/readiness` 를 직접 호출해 확인한다.

### 4. v2 가 생기면 두 매핑을 함께 둔다

같은 컨트롤러에 `version = "2"` 메서드를 더하거나 `OrderV2Controller` 를 만든다. 두 버전이 공존하는
동안은 `addSupportedVersions("1", "2")` 다. 이벤트 계약의 major 규칙(§4.7)과 방향이 같다 —
**추가로 살고, 삭제로 죽인다.**

## 고려한 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| **헤더 버저닝**(`X-API-Version`) | URL 이 리소스만 가리킨다는 이론적 장점이 있지만, 이 프로젝트에서는 보이지 않는 것이 곧 비용이다. curl·k6·Swagger·로그 어디에서도 버전이 안 보이면 "어느 버전을 부르는지" 를 매번 추적해야 한다 |
| **미디어 타입 파라미터**(`Accept: application/json;version=1`) | 헤더 방식의 단점을 그대로 갖고 캐시 키·프록시 설정까지 복잡해진다 |
| **경로에 `v1` 을 리터럴로 두고 Spring 버저닝은 끄기** | 가장 단순하다. 그러나 지원하지 않는 버전이 404 가 되어, 오타와 버전 불일치가 구분되지 않는다. 버전 목록이 코드 어디에도 없게 되는 것도 문제다 |
| **버전 없이 시작하고 필요할 때 붙이기** | 나중에 붙이면 이미 나간 URL 이 전부 바뀐다. k6 스크립트·sim-runner·통합 테스트를 소급 수정해야 하는 것은 API 키 결정(§17-2)에서 이미 겪은 종류의 비용이다 |

## 결과

**좋아지는 것**

- 지원하지 않는 버전이 400 이고, 응답 본문이 Problem Details 로 그 사실을 말한다.
- 지원 버전 목록이 `WebConfig` 한 곳에 있다.
- 데모·부하 테스트·문서 어디서나 호출 중인 버전이 URL 에 그대로 보인다.

**비용**

- 매핑 경로에 쓰이지 않는 `{version}` 자리표시자가 남는다. 그 이유를 모르면 지우고 싶어지는
  코드이고, 지우면 v2 요청이 조용히 404 로 돌아간다. 그래서 컨트롤러 Javadoc 과 이 ADR 에 적었고
  `OrderApiIT` 가 그 동작을 고정한다.
- 버전 해석 범위를 술어로 한정해야 한다. `/api/` 밖에 새 경로군을 만들 때 이 술어를 다시 봐야 한다.
- URL 에 버전이 들어가므로 `Location` 헤더·문서·클라이언트 코드가 모두 버전을 포함한다.
  v2 로 넘어갈 때 고칠 곳이 헤더 방식보다 많다.
