# ADR-019 — 멱등 기록은 7일 보존하고, 만료된 키는 새 요청이다

| 항목 | 내용 |
|---|---|

| 결정일 | 2026-09-03 |

## 맥락

ADR-018 이후 `idempotency_keys` 에는 **완료된 요청만** 남는다. 행이 있다는 것은 곧 "그 요청은
끝났고 응답은 이것" 이다. 그러면 두 가지가 따라 나온다.

첫째, `status` 컬럼은 값이 하나뿐인 컬럼이 된다. 읽기 경로에 남겨 둔 `IN_PROGRESS` 분기는
**아무도 만들지 않는 상태를 처리하는 코드**다. ADR-018 은 그것을 "언젠가 쓸 자리" 로 남겨 두었지만,
쓰이지 않는 분기는 테스트로만 살아 있고 리팩터링 때마다 판단을 요구한다.

둘째, 이 테이블은 **아무것도 지우지 않으면 무한히 자란다.** §8.1 피크 150,000 주문/일이면
하루 150,000 행이고, 한 달이면 450만 행이다. `expires_at` 컬럼은 §5.1 DDL 에 처음부터 있었지만
그것을 보고 지우는 것이 없었다.

## 결정

### 1. `status` 컬럼을 없앤다

§5.1 DDL 에서 빼고, 응답 두 컬럼(`response_code`·`response_body`)을 `NOT NULL` 로 올린다.
행의 존재가 곧 완료이므로 응답이 없는 행은 있을 수 없다. `V1__orders.sql` 은 아직 머지되지 않은
브랜치의 마이그레이션이므로 새 버전을 쌓지 않고 V1 자체를 고친다.

### 2. 업서트를 `ON CONFLICT DO NOTHING` 으로 단순화한다

`status` 가 없으면 `DO UPDATE … WHERE status = 'IN_PROGRESS'` 도 근거를 잃는다.
같은 의미인지 **측정해서** 확인했다. 두 연결로 같은 키를 넣어 보면,

```
B: starting insert at 10:40:44.282
INSERT 0 0
Time: 1972.115 ms          ← A 가 커밋할 때까지 기다렸다
B: insert returned at 10:40:46.254
최종 내용: key-1 | aaa | {"n": 1}    ← A 의 행이 그대로 남았다
```

`DO NOTHING` 은 충돌 상대가 아직 커밋되지 않았으면 **그 트랜잭션이 끝날 때까지 기다렸다가**
0행을 돌려준다. 필요한 성질 셋(충돌 시 0행 · 동시 트랜잭션 대기 · 기존 행 보존)이 모두 같으므로
더 단순한 쪽을 쓴다.

### 3. 보존은 7일이고, 그것은 클라이언트와의 계약이다

`expires_at = created_at + 7일`. 만료된 행은 정리 배치가 지운다. 그러므로
**7일이 지난 멱등 키로 같은 요청을 보내면 재생이 아니라 새 주문이 된다.** 이 문장을 §5.1 에
계약으로 적는다 — 숨겨 두면 "왜 어떤 재시도는 200이고 어떤 재시도는 201인가" 가 미스터리가 된다.

Redis 키 TTL 24h 는 그대로다. 두 값이 다른 것은 역할이 다르기 때문이다 — 24시간은 DB 를 읽지 않고
중복을 걸러 내는 구간이고, 그 뒤 7일까지는 DB 가 답한다.

### 4. 정리 배치는 `ProcessedEventCleaner` 와 같은 패턴이다

`ctid` 를 거친 `LIMIT` 삭제, 배치마다 커밋, 한 실행의 배치 수 상한. 다른 것은 보존 기간과
설정 접두사(`dawnline.order.idempotency.*`)뿐이다.

### 5. `expires_at` 인덱스를 추가한다 (불변규칙 11)

100만 행(피크 기준 정상 상태) 기준 측정이다.

| | 배치 하나 (LIMIT 1000) | 하루치(233,332행) 전량 |
|---|---|---|
| 인덱스 없음 | 78.2 ms, 38,210 버퍼, Seq Scan + top-N heapsort | 13.47 s |
| 인덱스 있음 | 1.2 ms, 2,314 버퍼, Index Scan | **0.47 s** |

인덱스는 7 MB — 337 MB 테이블의 2.1% 다. 전문은 근거 자료 문서에 있다.

## 근거

**7일인 이유는 `processed_events` 와 방향이 반대라서다.** §4.4 의 보존 14일은 "재전달 창(토픽 보존
7일)의 2배" 로 잡았고, 잘못 지웠을 때의 결과는 *같은 이벤트를 한 번 더 처리하는 것*이다.
멱등 기록은 다르다. 잘못 지운 뒤 같은 키가 오면 **새 주문이 만들어진다** — 고객에게 소포가 두 번
가고, 되돌리려면 사람이 개입해야 한다. 대가가 비대칭이므로 여유를 크게 잡는다.

클라이언트의 재시도 창은 보통 수 초에서 수 분이다. 7일은 그보다 세 자릿수 크고, "어제 실패한 주문을
오늘 같은 키로 다시 보내는" 수동 재시도까지 덮는다. 그 이상은 테이블만 키운다.

## 고려한 대안과 기각 이유

| 대안 | 기각 이유 |
|---|---|
| **`status` 를 남겨 둔다**(ADR-018 §4의 원안) | 값이 하나뿐인 컬럼과 도달하지 않는 분기가 남는다. 언젠가 결제 같은 경로가 생기면 그때 컬럼을 추가하는 마이그레이션 한 줄이면 된다 — 쓰지 않는 상태를 미리 들고 있는 것보다 싸다 |
| **정리하지 않는다**(무한 보존) | 재생은 영원히 되지만 테이블이 한 달에 450만 행씩 자란다. PK 조회는 버티지만 백업·복제·`VACUUM` 이 그렇지 않다 |
| **보존 24시간**(Redis TTL 과 동일) | 두 경로가 같은 기간이면 DB 가 있을 이유가 절반 사라진다. Redis 가 죽은 동안의 재시도를 DB 가 받아 주는 구간이 곧 이 차이다 |
| **보존 30일**(DLQ 와 동일) | 관계없는 숫자를 빌려 오는 것이다. DLQ 30일은 사람이 조사할 시간이고, 여기는 클라이언트 재시도 창이다 |
| **`expires_at` 대신 `created_at` 으로 지운다** | 인덱스를 하나 아끼지만 보존 기간이 코드에만 있게 된다. 행 자체가 "언제까지 유효한가" 를 들고 있는 편이 운영자가 읽기 쉽다 |

## 결과

**좋아지는 것**

- 테이블이 일정한 크기(약 100만 행)에서 멈춘다.
- 컬럼 하나와 분기 하나가 사라진다. `IdempotencyRecord` 는 "지문 + 응답" 두 가지만 남는다.
- 업서트 SQL 이 짧아지고, 그 의미가 측정으로 확인됐다.

**비용**

- **7일이 지난 멱등 키는 더 이상 보호하지 않는다.** 그 창 밖의 재시도는 새 주문이 된다.
  이것은 숨겨진 동작이 아니라 문서화된 계약이지만, 계약인 이상 클라이언트가 읽어야 한다.
- 스케줄러가 하나 늘어난다(order-service 의 4번째 `@Scheduled`). 실행 주기·배치 크기·한 실행
  상한을 잘못 잡으면 정리가 못 따라잡을 수 있고, 그때는 테이블이 조용히 자란다 — 그래서 한 실행이
  상한에 걸리면 `warn` 을 남긴다(`ProcessedEventCleaner` 와 같다).
- 인덱스 7 MB 와 그만큼의 쓰기 비용. `expires_at` 이 단조 증가에 가까워 인덱스 오른쪽 끝에만
  붙는 것이 그나마 다행이다.
