## 맥락

5,000건 계획의 왕복은 26.8초인데 그중 **20.2초(75%)가 라우트·설명 저장**이었다. §6.7 의 예산
30초는 *알고리즘* 예산인데, 그 예산의 3/4 을 영속화가 쓰고 있었다는 뜻이다. 그래서 "계획이 예산
안에 끝났다" 는 통과가 최적화에 대해 말해 주는 것이 거의 없었다.

원인은 DB 가 느린 것이 아니었다. `JdbcPlannedRouteRepository` 는 행마다
`entityManager.createNativeQuery(...).executeUpdate()` 를 돌리고, Hibernate 는 네이티브 질의
실행 전마다 영속성 컨텍스트를 **auto-flush** 한다 — 어느 테이블을 건드리는지 알 수 없으므로
전부 flush 하는 것이 기본값이다. 그런데 그 시점 세션에는 `findPlannableInWave` 가 올려 둔
**관리 엔티티 5,000개**가 떠 있다. 계측값이 그대로 말한다: flush **10,652회** × 엔티티
**5,001개** ≈ 5,300만 회의 더티 체크.

통제 실험이 원인을 못박았다. 같은 5,000행 네이티브 INSERT 를, 같은 트랜잭션·같은 DB 에서,
세션에 관리 엔티티가 있을 때와 없을 때 돌렸다 — 유일한 차이가 그것이다.

| 세션 상태 | 5,000행 INSERT |
|---|---:|
| 빈 세션 | **635 ms** |
| 후보 5,000개를 올린 세션 | **13,877 ms** |
| | **21.9배** |

## 결정

**최적화기의 I/O 경로 — 입력 적재와 결과 저장 — 는 영속성 컨텍스트를 지나지 않는다.**

원인은 "쓰기가 느리다" 가 아니라 **읽지 않아도 되는 엔티티 5,000개를 세션에 올려 둔 것**이다.
그러므로 고칠 곳도 둘이다.

### 1. 후보는 읽기 전용 프로젝션으로 읽는다

최적화기의 입력은 순수 값이다(불변규칙 5 — `domain.optimizer` 는 프레임워크 비의존). 관리
엔티티일 이유가 없고, 계획 트랜잭션은 후보 행을 한 건씩 바꾸지도 않는다.
`findPlannableInWave` 는 `JdbcTemplate` 로 읽어 `DispatchCandidate` 를 직접 만든다.

상태 반영도 한 건씩이 아니라 **결과별 집합**으로 한다.

```sql
UPDATE dispatch_candidates
   SET status = ?, updated_at = ?, version = version + 1
 WHERE order_id = ANY(?) AND status = 'PENDING'
```

### 2. 라우트·stop·설명은 JDBC 배치 INSERT

이 세 테이블은 **쓰는 시점에 도메인 동작이 없는 대량 결과물**이다. 계획이 이미 끝난 뒤의
산출물이라 상태 머신도, 낙관적 잠금도, 더티 체크도 필요 없다. ORM 을 지날 이유가 없다.
`reWriteBatchedInserts=true` 로 드라이버가 다중 VALUES 로 다시 쓰게 한다.

### 원칙

이 결정을 §7.1 에 한 줄로 남긴다: **최적화기 I/O 경로(입력 적재·결과 저장)는 ORM 이 아니라
벌크.** 다음에 같은 자리에서 같은 질문이 나오면 이 줄이 답한다.

### 관측

`dawnline_plan_persist_seconds`(histogram) 를 §9.1 에 추가한다. **알고리즘 시간과 영속화
시간이 운영에서 따로 보여야** 한다 — 이 ADR 이 필요했던 이유가 정확히 둘이 한 수치에 섞여
있었기 때문이다. `dawnline_plan_duration_seconds` 와 짝이다.

목표는 **5,000건 영속화 ≤ 3초**다. 빈 세션 실측 635 ms 가 한 테이블 5,000행이므로 라우트·stop·
설명 세 테이블에 배치까지 얹으면 그 근처가 된다는 추정이고, 구현 후 재측정해 확정한다.

## 대안과 기각 이유

### A. `HibernateFlushMode.COMMIT` 로 auto-flush 를 끈다 — **기각**

가장 작은 변경이고 flush 횟수를 10,652 에서 1 로 만든다. 그런데도 기각하는 이유가 둘이다.

1. **증상을 숨길 뿐 원인은 그대로다.** 세션에 5,001개가 떠 있는 사실은 변하지 않는다. flush
   비용이 커밋 시점 한 번으로 옮겨갈 뿐이고(더티 체크 자체는 그때 5,001개를 다 훑는다),
   무엇보다 **관리 엔티티가 필요 없는 자리에 관리 엔티티를 두는 설계**가 남는다. 다음에 계획
   경로에 테이블이 하나 더 붙으면 같은 문제가 같은 모양으로 돌아온다.
2. **read-your-writes 위험을 설정 한 줄로 전역에 들인다.** `FlushMode.COMMIT` 은 같은
   트랜잭션 안의 네이티브 질의가 아직 flush 되지 않은 변경을 **못 보게** 만든다. 이 저장소는
   네이티브 질의를 많이 쓴다(`ON CONFLICT`, 인덱스 리터럴, EXPLAIN 테스트). 그 조합은 조용히
   틀린 답을 내는 종류의 결함이고, 터지는 자리가 설정을 넣은 자리와 멀다.

### B. 그대로 둔다 — **기각**

26.8초는 30초 예산 안이다. 다만 여유가 **12%** 뿐이고, 5,000건은 §8.1 피크의 한 웨이브
크기다. 후보 6,000건에서 넘는다. 그리고 다음 작업(Phase 4-1 `LocalSearchImprover`)은
**계획 시간을 늘리는 작업**이라, 예산의 75% 를 ORM 이 쓰는 상태에서 시작하면 LS 의 측정이
의미를 잃는다.

## 결과

**좋아지는 것**

- 영속화 20.2초 → 목표 3초 이하. §6.7 의 30초가 다시 알고리즘 예산이 된다.
- `dawnline_plan_persist_seconds` 로 둘이 운영에서 갈라진다.
- 후보를 값으로 읽으므로 최적화기 입력 경로가 불변규칙 5 와 형태가 맞는다.

**나빠지는 것 · 지불하는 값**

- **벌크 UPDATE 가 상태 전이를 SQL 로 옮긴다.** 불변규칙 6 은 "상태 전이는 상태 머신
  메서드로만" 이다. `WHERE status = 'PENDING'` 은 `recordPlanResult` 의
  `!status.hasProgressedPast(target)` 를 옮겨 적은 것이며(PLANNED·UNASSIGNED 는 progress 1,
  PENDING 만 0), **두 곳이 같은 규칙을 두 번 적는다.** 어긋나면 조용하다. 그래서 둘을 함께
  묶는 테스트를 둔다 — 취소된 후보가 벌크 UPDATE 로 뒤집히지 않는다는 것을 `recordPlanResult`
  가 거짓을 돌려주는 것과 나란히 확인한다(ADR-026 이 지키려는 성질이다).
- `JdbcTemplate` 경로는 Hibernate 의 미반영 변경을 보지 못한다. 계획 경로에서는 `route_plans`
  행이 `insertIfAbsent`(네이티브 INSERT)로 이미 DB 에 있어 FK 가 성립하지만, **이 가정이
  깨지는 변경은 FK 위반으로 즉시 터진다** — 조용하지 않다는 점이 A 와 다르다.
- 어댑터 하나가 `EntityManager` 에서 떨어져 나가 영속화 경로가 두 갈래가 된다. §7.1 의 원칙
  한 줄이 그 갈림길에 서 있는 표지판이다.

## 재검토 지점

- Phase 4-1 `LocalSearchImprover` 이후 — 알고리즘 시간이 늘면 30초 예산의 배분이 달라진다.
- Phase 5 재계획(§6.8)이 부분 저장을 하게 되면 배치 단위가 라우트 단위로 잘게 쪼개진다.
- 후보가 10,000건을 넘으면 프로젝션 읽기 자체(`ORDER BY order_id` 정렬 포함)를 다시 잰다.
