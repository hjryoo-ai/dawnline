**평일은 비어 있고 과부하는 과부하다.** `normal-day` 와 `cold-heavy` 는 함대 그대로 미배정 0 이다 — 좌석 예약이 수요 쪽에서 눌리는 유일한 시나리오
(`cold-heavy`)도 760 개의 배정을 좌석 순서로 밀었을 뿐 아무것도 떨어뜨리지 않았다. `overload-day` 는 같은 물량의 `peak-day` 가 더한 304대 없이 62%를
떨어뜨린다 — 계산 부족분이 캠프마다 `peak-day` 의 증차와 **한 대도 다르지 않다**(같은 seed · 같은 물량이니 같아야 하고, 같다). **어떤 실행에서도
계획의 열화 사다리가 켜지지 않았다** — 가장 큰 웨이브(후보 3,490)의 계산이 16.6초로 예산 30초 아래다.

새로 드러난 것이 셋이다(§3): 창이 열리는 순간 Redis 첫 연결이 명령 타임아웃 50 ms 에 걸려 **매 실행 page 알림**이 났고(A2), tracking 의 스캔 재시도가
**교착을 겹침으로 보지 않아** 500 을 냈고, `shipments` 는 HOT 갱신이 **0** 인 채 배송 하나당 37–94 번 고쳐진다(B11).

## 1. 측정 범위 — 시나리오마다 다르다

- **`peak-day` 는 DAWN 이다**(phase7-peak-day §7): 운영자가 23:58 에 DAWN 웨이브만 조기 마감하고, 실행은 NEXT_DAY 의 스케줄 마감(00:01:50) 전에 끝난다.
- **`as-is` 셋은 DAWN + NEXT_DAY 다.** 조기 마감이 없어 두 무리가 **같은 스케줄 마감(00:01:50)** 에 닫히고 함께 계획된다. 기사는 계획이 낸 DAWN 라우트
  수를 기다리지만 그 사이 받은 NEXT_DAY 라우트도 돈다(`77 / 57 기대` 가 그 모양이다). 그래서 기사 · V8 · 원장 행은 두 무리 합이고, 함대 · 미배정
  행은 DAWN 이다(함대 단계가 창의 DAWN 웨이브만 센다).
- 시각은 모두 유효 시각이다. `cold-heavy` 는 오프셋이 약 23시간이다 — `sim-up` 은 「지금 뒤의 첫 22:40」을 고르고 그 실행은 23:27 에 떴다. 창의 모양은
  같다.

## 3. 새로 드러난 것

### 3.1 창이 열리는 순간 Redis 첫 연결이 50 ms 에 걸린다 (A2 · 매 실행 page)

`overload-day` 의 order-service 로그(근거: 관측): 창 시작(유효 22:58) 4초 뒤 `RedisConnectionFailureException` — `StacklessClosedChannelException`,
10초 뒤 「**Connection initialization timed out after 50 millisecond(s)**」, 33초 뒤 「Command timed out after 50 millisecond(s)」. 실패마다 outage gate 가
10초 동안 Redis 를 건너뛰고(§7.2 폴백 — 레이트 리밋은 허용, 멱등은 DB), 그동안의 주문이 전부 `bypassed` 로 센다. 우회 수가 네 실행 모두 **rps × 33–43초**
(83 · 111 · 412 · 535)이고, 그것이 `DawnlineRateLimitBypassed`(page)를 울렸다. fulfillment 의 `geo:fc` 조회도 같은 순간 50 ms 명령 타임아웃으로 DB 폴백에
갔다.

- 기제: Lettuce 연결은 첫 요청에 게으르게 열리고, **연결 초기화에도 명령 타임아웃(`dawnline.order.redis.command-timeout-ms` = 50)이 걸린다**. 17분을
  놀던 JVM 의 첫 초기화가 50 ms 를 넘는다. 정확성은 무너지지 않았다 — 폴백이 설계대로 돌았다(V1–V8 ✅). 무너진 것은 알림(오탐 page)과 창 첫 30초의
  남용 방지다.
- 이것이 A2 의 「첫 요청 3초」의 한 몫이다(최대 3.1–3.5초가 네 실행 모두 창 시작). 운영에서도 재기동 뒤 첫 트래픽이 같은 길을 간다(근거: 추정).

### 3.2 tracking 의 스캔 재시도는 교착을 겹침으로 보지 않는다 (`normal-day` 종료 코드 2)

`normal-day` 의 기사 리포트에 `unavailable` 1건 — tracking 스캔 엔드포인트의 500 한 건이다. 같은 실행의 tracking DB 가 `deadlocks` 1 · `xact_rollback` 1
이다(실행 전 0 · 0). `ContendedScanRetry` 는 `OptimisticLockingFailureException` 하나만 다시 한다(§5.4 「세 번 뒤 409 `shipment-contended`」) — 교착의 패자는
그 밖이라 예상하지 못한 예외(500)로 나갔고, 도구는 500 을 다시 보내지 않는다. 교착의 패자는 PostgreSQL 이 「다시 하라」고 말하는 부류다.
어느 두 쓰기였는지는 모른다 — 그 실행의 서비스 로그는 다음 `sim-reset` 이 지웠다(그 뒤로 스냅샷이 로그도 뜬다). 가장 가까운 설명은 스캔과 개정 반영이
한 라우트의 배송들을 서로 다른 순서로 잡는 것이다(근거: 추정). → 재현됐다(2026-09-28, [ADR-070](../adr/ADR-070-tracking-writes-lock-the-route-first.md)): 스캔은 stop 순, 개정 반영은 주문 id 순이었다. → 재현됐다(2026-09-28, ADR-070): 스캔은 stop 순, 개정 반영은 주문 id 순이었다. 사실은 잃지 않았다 — V8 0, 원장의 완료가 배정 전부.

| | `peak-day` | `overload-day` | `normal-day` | `cold-heavy` |
|---|---:|---:|---:|---:|
| `shipments` 행 · 갱신 · HOT | 31,461 · 1,174,386 · **0** | 17,332 · 1,539,940 · **0** | 6,286 · 552,692 · **0** | 6,323 · 595,966 · **0** |
| 행당 갱신 | 37 | 89 | 88 | 94 |
| `rm_orders` 행 · 갱신 · HOT | 45,000 · 182,519 · 0 | 45,000 · 146,454 · 0 | 9,000 · 36,934 · 0 | 9,000 · 36,848 · 0 |

7-0b 는 「채운 직후라 인덱스 없이도 HOT 0」이라 운영 모양을 추정으로 남겼다 — 운영 모양에서도 0 이다. 행당 갱신이 라우트 길이에 비례하는 모양
(평일의 긴 라우트에서 더 많다)은 스캔 하나가 뒤 stop 들의 ETA 를 미는 것으로 읽힌다(근거: 추정). tracking 풀 대기(최대 60–191)가 기사 스캔 구간에만
있는 것과 같은 자리다.

### 3.4 그 밖 — 조사하지 않은 것

- `overload-day` 에서 `DawnlineAgeNegative`(ticket) — fulfillment 의 `dawnline_outbox_lag_seconds` 가 한 번 음수였다. 게이지가 음수를 `NaN` 으로 바꿔 크기는
  남지 않았다. 「지금」을 잡은 뒤 커밋된 행이 몇 ms 앞선 경우로 보인다(근거: 추정).

## 4. 결정 항목

이 리포트가 켜 놓고 닫지 않은 것 — 모두 설계 변경이라 구현 전에 묻는다.

1. **Redis 첫 연결(A2 · §3.1)** — 기동 때 연결을 미리 연다 · 연결 초기화의 타임아웃을 명령 타임아웃과 가른다 · 알림에 `for` 를 준다. 셋은 배타가 아니다.
2. **tracking 의 교착 패자(§3.2)** — `ContendedScanRetry` 가 교착의 패자도 겹침으로 다시 한다(§5.4 의 「무엇을 다시 하는가」 를 넓힌다).
   → **결정(2026-09-28)**: 재시도는 안전망으로 넣고, 교착은 쓰기 계층으로 없앤다 — 라우트 행 → `shipments`. 짝은 ETA 전파가 아니라 개정 반영이었다(스캔은 stop 순 · 개정은 주문 id 순, `ScanRevisionRaceIT` 로 재현) — [ADR-070](../adr/ADR-070-tracking-writes-lock-the-route-first.md).
3. **`routes.status`(A31)** — 사건 시점에 쓰거나 칸을 지운다.
4. **`no-anchor`(B1)** — dispatch 가 `route-departed` 의 소비자가 되는가, 아니면 도구 부하를 낮춘 실행(B14 와 같은 조건)으로 먼저 가르는가.
5. **HOT 손실(B11)** — BRIN 재측정, 또는 ETA 를 미는 갱신의 모양부터.
   → **결정(2026-09-28)**: 모양부터 — 편차를 라우트 행에 한 번(`deviation_seconds`), ETA 는 planned + 편차로 계산. 판정은 갱신 수 · 풀 대기로(HOT 은 `ix_ship_updated` 가 막는다). BRIN 은 그 뒤에도 남을 때만 — [ADR-070](../adr/ADR-070-tracking-writes-lock-the-route-first.md).
6. **합쳐진 stop 을 가르는 동안의 배송(ADR-068 후속 C)** — ADR-047 의 「이벤트의 라우트에 있는 쪽 하나」를 두 stop 에 적도록 바꿀지.
