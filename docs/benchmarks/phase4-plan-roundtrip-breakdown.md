# 5,000건 왕복 25초 — 구간 분해

Phase 3 마감 리포트(`phase3-baseline.md` §7)는 계획 시간 **4,916 ms** 와 왕복 **25,311 ms** 를
나란히 적어 두고 "나머지 20초는 영속화" 라고만 했다. 그 20초를 숫자로 가르고, **원인까지**
확정한 기록이다. 리뷰의 요구가 이것이었다 — "이 20초가 어디인지 모르면 이 수치는 §8.1 의 어느
SLO 와도 짝이 안 맞는다."

> **결과 먼저**: 20.2초를 **800 ms** 로 줄였다(§6). 원인은 DB 가 아니라 Hibernate auto-flush 의
> 더티 체크였고, 고친 것은 쓰기 방식만이 아니라 **후보 5,000개를 관리 엔티티로 읽던 것**이다.

## 먼저: 그 25초는 리뷰가 지목한 두 구간을 **포함하지 않는다**

리뷰는 두 후보를 들었다. 둘 다 이 측정 안에 없다.

| 후보 | 25초 안에 있나 | 이유 |
|---|---|---|
| 후보 5,000건 적재(이벤트 소비) | **아니다** | `PhaseThreeDoDIT` 는 후보를 `seedCandidates` 로 DB 에 직접 넣는다. Kafka 를 지나지 않는다. |
| 계획 종료 → `route.assigned` 도착 | **아니다** | 그 클래스는 릴레이를 끈다(`dawnline.messaging.outbox.enabled=false`). outbox 행은 쌓이지만 발행되지 않는다. |

즉 25초는 **`RunPlanUseCase.run()` 한 번의 트랜잭션 안**에서 전부 일어난다. 두 구간은 따로
쟀고, 아래 §3·§4 에 있다.

## 측정 환경

| 항목 | 값 |
|---|---|
| 방법 | out 포트 4개(`DispatchCandidateRepository`·`PlannedRouteRepository`·`RoutePlanRepository`·`DispatchEvents`)를 `BeanPostProcessor` 로 동적 프록시 감싸 메서드별 호출 수와 누적 시간을 잼 |
| | 재현이 아니라 **실측**이다 — 실제 `runPlan.run()` 호출을 그대로 지난다 |
| 환경 | macOS 27.0 (aarch64) · OpenJDK 25.0.4.1 · 14코어 · Docker Desktop 29.1.3 |
| 저장소 | PostgreSQL 18.2 (Testcontainers) |
| 입력 | 캠프 1 · 후보 5,000 · 차량 20 · seed 20260905 · 계획 시각 09:00 KST 고정 |
| 결과 | 라우트 20 · 배정 3,810 · 미배정 1,190 (마감 리포트와 동일) |

계측 클래스는 측정 후 삭제했다. 남기면 CI 에 27초짜리 테스트가 하나 더 붙는데, 이 측정은
회귀 감시가 아니라 **한 번의 진단**이기 때문이다.

## 1. 구간 B — 계획 유스케이스 26,750 ms

| 구간 | 시간 | 비중 | 호출 수 |
|---|---:|---:|---:|
| **계획**(`planDurationMs`, 후보 조회+룰+최적화+검증) | 5,030 ms | 19% | 1 |
| **라우트 저장** `saveRoutes` | 10,351 ms | 39% | 1 (20 라우트 · 3,810 stop · stop_orders) |
| **설명 저장** `saveExplanations` | 9,844 ms | 37% | 1 (5,000행) |
| **outbox 기록** `routeAssigned` | 1,403 ms | 5% | 20 |
| `ordersDispatched` | 43 ms | 0.2% | 20 |
| **후보 상태 반영** `findById`+`update` | 18 ms | 0.07% | 5,000 + 5,000 |
| 커밋 · 기타 | 56 ms | 0.2% | — |

**여기서 예상이 하나 틀렸다.** 5,000건을 한 건씩 `findById` → `update` 하는 `markCandidates` 가
비쌀 것으로 봤는데 **18 ms** 다. 이미 `findPlannableInWave` 가 5,000개를 영속성 컨텍스트에
올려 둔 뒤라 `findById` 는 1차 캐시에서 답하고 `update` 는 더티 표시만 한다. 실제 SQL 은
나중에 한꺼번에 나간다.

비싼 것은 **라우트·설명 저장 20.2초**(75%)다.

## 2. 원인 — DB 가 느린 게 아니라 더티 체크다

`JdbcPlannedRouteRepository` 는 행마다 `entityManager.createNativeQuery(...).executeUpdate()`
로 넣는다. Hibernate 는 **네이티브 질의 실행 전마다 영속성 컨텍스트를 auto-flush** 한다 —
어느 테이블을 건드리는지 알 수 없으므로 전부 flush 하는 것이 기본값이다. 그런데 그 시점의
세션에는 `findPlannableInWave` 가 올려 둔 **관리 엔티티 5,000개**가 떠 있다.

측정된 값이 이것을 그대로 말한다.

| 계측 | 값 |
|---|---:|
| flush 횟수 | **10,652** |
| prepared statement | 19,492 |
| 세션에 적재된 엔티티 | 5,001 |

flush 10,652회 × 엔티티 5,001개 ≈ **5,300만 회의 더티 체크**다.

### 통제 실험

가설을 실험으로 갈랐다. **같은 5,000행 네이티브 INSERT 를, 같은 트랜잭션·같은 DB 에서,
세션에 관리 엔티티가 있을 때와 없을 때** 돌렸다. 유일한 차이가 그것이다.

| 세션 상태 | 5,000행 INSERT |
|---|---:|
| 빈 세션 | **635 ms** |
| 후보 5,000개를 올린 세션 | **13,877 ms** |
| | **21.9배** |

DB 는 같다. 문장도 같다. 21.9배는 전부 애플리케이션 쪽이다.

## 3. 구간 A — 후보 적재(소비자 처리량)

리뷰가 "초당 건수로 따로 내야 한다" 고 한 값이다. `fulfillment.planned` 5,000건을 토픽에
넣고 `dispatch_candidates` 에 5,000행이 보일 때까지 잰다.

| 항목 | 값 |
|---|---:|
| 이벤트 5,000건 발행 | 250 ms |
| 마지막 행이 보일 때까지 | 3,053 ms |
| **처리량** | **1,638 건/초** |

**§8.2 의 컷오프 직전 600 rps 를 2.7배 웃돈다.** 리뷰가 걸어 둔 판정 조건 — "fulfillment→dispatch
소비가 600 rps 보다 느리면 랙이 grace 90초를 밀어내 약속 개정이 몰린다" — 은 **지금은 걸리지
않는다**. 다만 이 값은 dispatch 인스턴스 하나·로컬 Testcontainers 의 값이고, 여유가 2.7배지
한 자릿수는 아니다. 소비 경로가 무거워지면(Phase 5-5 의 `delivery.status` 소비가 같은 서비스에
붙는다) 다시 재야 한다.

## 4. 구간 C — 계획 종료 → `route.assigned` 도착 (릴레이)

릴레이를 켜고(폴링 100 ms) 후보 500건으로 계획을 돌린 뒤, 커밋 시점부터 브로커에서 첫
`route.assigned` 를 받을 때까지 잰다.

| 항목 | 값 |
|---|---:|
| 계획 트랜잭션 커밋까지 | 1,897 ms |
| 첫 `route.assigned` 도착 | 2,008 ms |
| **커밋 이후 지연** | **111 ms** |

**폴링 주기 한 번**이다. outbox 릴레이는 이 그림에서 병목이 아니다.

## 5. 그래서 §8.1 의 어느 SLO 와 짝이 되나

| 구간 | 값 | 짝이 되는 SLO |
|---|---:|---|
| A 후보 적재 | 1,638 건/초 | §8.2 피크 600 rps — **여유 2.7배** |
| B 계획(`planDurationMs`) | 5.0초 | §6.7 계획 시간 p95 ≤ 30초 — **여유 6배** |
| B 영속화 | 20.2초 | **짝이 없다** — 아래 |
| C 릴레이 | 0.11초 | §4.4 폴링 주기 |

**20.2초에는 짝이 되는 SLO 가 없다.** 그리고 이것이 이 측정의 결론이다: 왕복 26.8초를 "계획
시간" 으로 읽으면 30초 예산의 89% 를 쓰고 있는 것처럼 보이지만, 예산이 겨냥한 최적화는 5.0초
(17%)이고 나머지는 최적화와 무관한 영속화다. **둘을 한 수치로 합쳐 보고하면 30초 예산이
알고리즘 예산이 아니라 ORM 예산이 된다.**

## 6. 고쳤다 — B, 그리고 그 절반만으로는 부족했다 (2026-09-08, ADR-029)

세 안 중 **B(JDBC 배치)** 로 결정됐고, 결정에 한 가지가 더 붙었다: 원인은 "쓰기가 느리다" 가
아니라 **읽지 않아도 되는 엔티티 5,000개를 세션에 올려 둔 것**이므로, 쓰기만 고치면 절반이다.
그래서 둘을 함께 했다.

1. **후보는 읽기 전용 프로젝션으로.** `findPlannableInWave` 가 `JdbcTemplate` 로 읽어
   `DispatchCandidate` 를 직접 만든다. 상태 반영도 한 건씩이 아니라 결과별 집합
   `UPDATE … WHERE order_id = ANY(?) AND status = 'PENDING'` 두 문장.
2. **라우트·stop·설명은 JDBC 배치 INSERT** (`reWriteBatchedInserts=true`).

A(`FlushMode.COMMIT`)를 기각한 이유는 [ADR-029](../adr/ADR-029-optimizer-io-is-bulk-not-orm.md)
에 있다 — 증상만 숨기고 원인(세션에 5,001개)은 그대로이며, read-your-writes 위험을 설정 한
줄로 전역에 들인다.

### 재측정

| 구간 | 이전 | 이후 | 배수 |
|---|---:|---:|---:|
| **왕복** | 26,750 ms | **5,572 ms** | 4.8× |
| 알고리즘 (`planDurationMs`) | 5,030 ms | 4,730 ms | — |
| **영속화** (`dawnline_plan_persist_seconds`) | ~20,400 ms | **800 ms** | **25×** |
| `saveRoutes` | 10,351 ms | 52 ms | 199× |
| `saveExplanations` | 9,844 ms | 67 ms | 147× |
| `routeAssigned` ×20 | 1,403 ms | 597 ms | 2.4× |
| 후보 상태 반영 | 18 ms (10,000회) | 23 ms (**2회**) | — |

원인이 사라진 것을 두 수치가 그대로 말한다.

| 계측 | 이전 | 이후 |
|---|---:|---:|
| flush 횟수 | 10,652 | **22** |
| 세션에 적재된 엔티티 | 5,001 | **1** |
| prepared statement | 19,492 | 3,863 |

**계획 결과는 한 자리도 바뀌지 않았다** — 라우트 20 · 배정 3,810 · 미배정 1,190 · 비용
39,102,032원. 같은 seed 에 같은 입력이므로 같아야 하고, 실제로 같다. 영속화 경로만 바꿨다는
것의 증거다.

### 목표 확정

**5,000건 영속화 ≤ 3초.** 실측 800 ms 이므로 여유 3.7배이고, 알고리즘 예산(30초 대 4.7초,
6.4배)과 비슷한 비율이다. 이 목표는 문서가 아니라 게이트다 —
`PhaseThreeDoDIT.오천건_계획이_예산_안에_끝난다` 가 `dawnline_plan_persist_seconds` 를 읽어
어설션한다. 깨지면 둘 중 하나이고(영속화가 다시 ORM 을 지나거나, 목표가 이 기계에서
비현실적이거나), **조용히 늘리지 않는다** — 재서 ADR-029 재검토 지점에 적는다.
