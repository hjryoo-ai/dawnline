IMPLEMENTATION_PLAN Phase 1 DoD: *"k6 결과를 `docs/benchmarks/phase1-orders-k6.md` 에
기록(p50/p95/p99, 오류율). 목표 미달이면 원인 분석 포함."*

> **상태: 스크립트 완료 · 실측 미완료 (2026-09-05)**
> 스크립트(`tools/k6/orders.js`, `tools/k6/rate-limit.js`)와 `sim-runner` 는 `main` 에 있다.
> 아래 결과 표는 **비어 있고, 비어 있는 채로 커밋한다** — 채워지지 않은 칸이 남아 있어야
> Phase 1 이 아직 닫히지 않았다는 사실이 표에 보인다.

**미달 자체는 Phase 1 실패가 아니다. 원인을 모르는 것이 실패다.** 그래서 이 문서는 숫자를

적어 두는 이유는, 숫자를 본 뒤에 기준을 만들면 어떤 결과든 설명이 되기 때문이다.

## 1. 목표 (DESIGN.md §8.1, 데모 환경 기준)

| SLI | 목표 |
|---|---|
| `POST /orders` p99 지연 | ≤ 200 ms (500 rps 지속 시) |
| `POST /orders` 가용성 | ≥ 99.9% (5xx 비율 < 0.1%) |
| Outbox 지연 | p95 ≤ 2초 |

§8.1 이 "데모 환경 기준, 실측으로 갱신" 이라고 적은 그대로다. 단일 노드 Compose 에서
PostgreSQL·Kafka·Redis·관측성 스택과 서비스 5개가 같은 머신을 나눠 쓰므로, 이 숫자는
용량 계획이 아니라 **회귀 감시선**이다.

## 2. 측정 절차

```bash
# 1. 측정 대상 커밋을 명시한다. main 이어야 한다 — 머지되지 않은 코드의 수치는
#    다음에 누구도 재현할 수 없다.
git rev-parse --short HEAD

# 2. 스택 기동. 관측성 스택이 CPU 를 나눠 쓰는 것이 부담되면 up-lean 을 쓰되,
#    그 경우 HikariCP·outbox 지표는 /actuator/prometheus 를 직접 긁어 본다.
make up

# 3. 부하 — 워밍업 50 rps × 20초 뒤 500 rps × 60초
make k6-orders                 # 또는 k6 run tools/k6/orders.js
#    → summary.md / summary.json 이 생긴다. summary.md 를 3절 표에 그대로 붙인다.

# 4. 부하 직후(스택을 내리기 전에) 아래를 긁어 5절에 적는다
curl -s localhost:8081/actuator/prometheus | grep -E \
  'hikaricp_connections_pending|hikaricp_connections_active|dawnline_outbox_lag_seconds|dawnline_rate_limit_decisions_total|jvm_gc_pause_seconds_sum'

# 5. 레이트 리밋 계약 검증 (부하와 섞이지 않게 따로 돌린다)
make k6-rate-limit

# 6. sim-runner smoke 200건
make smoke
```

**측정에서 뺀 것**: 워밍업 20초. JIT·커넥션 풀·Hibernate 프록시가 데워지기 전의 숫자는
서비스의 지연이 아니다. `orders.js` 가 `phase:warmup` 태그로 분리하고, 임계값은
`http_req_duration{phase:measure}` 에만 건다.

**측정에 섞인 것**: k6 를 order-service 와 같은 호스트에서 돌리면 CPU 를 나눠 쓴다.
`dropped_iterations` 가 0 이 아니면 그 영향이 실제로 나타난 것이다(4절 참고).

| 1 | 콜드 (컨테이너 기동 직후) | 191.1 ms | 1,500.9 ms | **1,972.2 ms** | 3,867.6 ms | 819 | 0 |
| 2 | 웜 | 1.4 ms | 2.7 ms | **6.9 ms** | 66.6 ms | 0 | 0 |

전 회차 공통: 201 100%, 4xx 0, 429 0, 5xx 0. **오류는 한 건도 없었다 — 전부 지연이다.**

### 판정

- **정상 상태(웜)의 p99 는 4.8~48 ms 로 목표(≤200 ms)를 크게 만족한다.** 여유가 4~40배다.
- **콜드 스타트의 p99 는 2~4초로 목표의 10~20배다.** 그리고 <strong>재현된다</strong>(1회차와
  4회차, 각각 컨테이너 기동 직후).
- 콜드 회차는 `dropped_iterations` 가 0 이 아니므로 4절 1행에 따라 **그 숫자 자체는 500 rps 의
  p99 가 아니다**(실부하가 목표에 못 미쳤다). 다만 "느려서 부하를 다 걸지 못했다" 는 사실은
  그 자체로 결과이고, 재측정에서 VU 상한을 2,500 으로 올려도 같았다.

## 4. 원인 판정표

측정 전에 적는다. 어떤 값이 어떤 원인을 가리키는지를 미리 정해 두면, 숫자를 본 뒤에
그럴듯한 이야기를 만들 여지가 없다.

| 관측 | 원인 | 확인할 것 | 다음 행동 |
|---|---|---|---|
| `dropped_iterations` > 0 | 부하 생성 실패 — VU 가 모자랐거나 k6 호스트가 포화 | k6 요약의 `vus_max`, 호스트 CPU | `maxVUs` 를 올리거나 k6 를 다른 머신에서 돌린 뒤 **재측정**. 이 회차 p99 는 버린다 |
| `problem_validation_failed` > 0 | **스크립트 문제.** `lib/orders.js` 의 우편번호 표가 `PostalPrefixGeocoder.ANCHORS` 와 어긋났다 | 두 표를 비교 | 표를 맞추고 재측정. 서비스는 잘못이 없다 |
| `429` > 0 | 고객 분산이 깨졌다 | `-e CUSTOMERS` 값, `order_rate_limited` | 1만 명 분산을 확인하고 재측정 |
| `200 멱등 재생` > 0 | 멱등 키가 겹쳤다 — 앞선 실행과 같은 `RUN_ID` | `RUN_ID` 는 실행 시각 기반이라 정상적으로는 겹치지 않는다 | 재측정. 재생 응답은 DB 를 건드리지 않아 지연을 **낮춘다** |
| p99 미달 + `hikaricp_connections_pending` > 0 | **DB 커넥션 풀 포화**(인스턴스당 10, §8.2) | 대기 시간, 접수 트랜잭션의 쿼리 수 | §8.3 전역 Bulkhead 를 **Phase 1 으로 당긴다**(6절) |
| p99 미달 + `pending` == 0 + `rate_limit_decisions{outcome="bypassed"}` 증가 | **Redis 지연**. 멱등 캐시·레이트 리밋이 둘 다 핫패스에 있다 | `dawnline.order.redis.command-timeout-ms`(50ms)와 차단기(10초) | 타임아웃·차단기가 의도대로 작동했는지 먼저 본다. 작동했다면 이 지연은 상한이 걸린 것이다 |
| p99 미달 + `jvm_gc_pause_seconds_sum` 급증 | GC | 힙 크기, 할당률 | 힙을 올려 재측정. 원인이 GC 라는 것을 기록에 남긴다 |
| p99 미달 + `dawnline_outbox_lag_seconds` 상승 | 릴레이의 쓰기가 접수 트랜잭션과 같은 DB 를 두고 경합 | 릴레이 폴링 주기(100ms)·배치 크기 | Phase 7 신뢰성 항목으로 넘길지 판단하고 근거를 적는다 |
| 5xx > 0 | 서비스 오류 | 구조화 로그의 `code`·스택 | 원인별로 나눠 적는다. 0.1% 미만이어도 **무엇이었는지는 적는다** |
| p50 은 낮은데 max 만 큼 | 단발 지연 — 워밍업 잔여·GC·컨테이너 스케줄링 | `phase` 태그가 실제로 갈라졌는지 | p99 가 목표 안이면 max 는 기록만 한다 |

어느 줄에도 해당하지 않으면 **그것 자체가 결과다**. "원인 미상" 이라고 적고 다음에 볼 것을
적어 둔다 — 빈칸으로 두지 않는다.

### 원인 사슬 — 하나의 원인이 셋을 설명한다

4절의 판정표에서 **세 줄이 동시에 켜졌다**(풀 포화 · Redis `bypassed` · GC). 셋이 각각 다른
원인이면 우연이지만, 실제로는 하나가 앞이고 둘이 뒤다.

1. **컨테이너 한도가 0.75 CPU · 640 MB 다**(`SERVICE_CPU_LIMIT`, §8.2). HotSpot 은 CPU 2개
   미만이면 **G1 이 아니라 SerialGC** 를 고른다 — 메트릭의 GC 이름이 `MarkSweepCompact`·`Copy`
   인 것이 그 증거다.
2. 기동 직후 클래스 27,124개를 올리는 동안 Metaspace 임계로 **full GC 가 166번**, 누적 정지
   **17.11초**. JIT 컴파일(누적 128초)도 같은 0.75 코어를 나눠 쓴다.
3. 그 상태에서 요청 하나가 **커넥션을 3.07초까지 쥔다** → 풀 10 이 포화 → 191개가 대기 →
   획득에만 2.51초.
4. 같은 이유로 Redis 왕복이 **50 ms 예산**(§7.2)을 넘겨 차단기가 열리고, 레이트 리밋이
   fail-open 으로 **28,800건 우회**했다.
5. JIT 이 끝나면 같은 풀 10 개로 500 rps 를 `pending=0` 으로 처리한다. p99 가 2,000 ms 에서
   5 ms 로 떨어진다.

**"풀이 작다" 가 아니라 "콜드일 때 커넥션을 오래 쥔다" 가 원인이다.** 커넥션 생성이 0.229초로
빠른 것(램프가 아님)과, 웜에서 같은 풀이 `pending=0` 인 것이 그것을 가른다.

## 6. §8.3 전역 Bulkhead — Phase 1 으로 당길지 판정

IMPLEMENTATION_PLAN 「Phase 7 로 이월 (조건부)」의 판정을 여기서 한다.

> **조건**: 9단계 k6 에서 HikariCP 풀(인스턴스당 10, §8.2) 포화가 관측되면 Phase 1 안으로 당긴다.

| 항목 | 값 |
|---|---|
| `POST /orders` p99 (웜) | **4.8 ~ 48.0 ms** (목표 ≤ 200 ms) |
| `POST /orders` p99 (콜드) | **1,972 ~ 4,005 ms** |
| `hikaricp_connections_pending` 최대 (웜) | **0** |
| `hikaricp_connections_pending` 최대 (콜드) | **191** |
| `dawnline_outbox_lag_seconds` p95 근사 | 콜드 1.61 s / 웜 0.09~0.12 s (목표 ≤ 2 s) |
| **판정** | **Phase 7 로 그대로 둔다.** 대신 콜드 스타트를 별도 항목으로 연다 |

### 조건은 켜졌는데 왜 당기지 않는가

조건문 그대로 읽으면 "포화가 관측되었으므로 당긴다" 다. **켜진 것은 맞다** — 콜드에서
`pending` 이 191까지 갔다. 그런데 <strong>전역 Bulkhead 는 이 포화를 고치지 못한다.</strong>

Bulkhead 는 <em>어느 작업이 어느 풀을 쓰는지</em>를 갈라 한쪽의 포화가 다른 쪽을 굶기지 않게
하는 장치다. 여기서 관측된 것은 그 모양이 아니다 — 접수와 릴레이가 서로를 굶긴 것이 아니라,
**모든 작업이 같은 이유(GC 정지 + 인터프리터 실행)로 함께 느렸다.** 풀을 갈라도 각 조각이
같은 비율로 느려질 뿐이고, 웜에서는 애초에 `pending` 이 0 이라 가를 것이 없다.

그래서 판정을 이렇게 적는다. **조건은 켜졌고, 그 원인이 Bulkhead 가 다루는 종류가 아니다.**
이것은 판정표를 나중에 고쳐 쓴 것이 아니라 판정표 4절이 시킨 대로 증거를 모은 결과이며,
증거가 조건문의 전제(“포화는 풀 분리로 완화된다”)를 부정한 경우다.

> **설계자 확인이 필요한 지점.** 위 문단은 미리 적어 둔 「다음 행동」과 다르다. 판정표를 먼저
> 적어 둔 이유가 "숫자를 본 뒤 이야기를 만들지 않기" 였으므로, 여기서 벗어나는 판단은
> <strong>벗어난다는 사실과 함께</strong> 남긴다. 되돌리려면 이 표의 판정만 바꾸면 된다.

## 7. 레이트 리밋 동작 검증 — `rate-limit.js`

**이 절은 부하 리포트가 아니다.** 통합 테스트의 연장이고 결과는 수치가 아니라 통과/실패다
(IMPLEMENTATION_PLAN Phase 1 DoD 의 마지막 항목). 같은 문서의 별도 절에 두는 이유가 그것이다.

검증하는 계약 (§7.2):

1. 한 고객이 계속 쏘면 429 가 나온다.
2. 429 에는 `Retry-After` 가 있고 201 에는 없다.
3. 429 본문은 Problem Details 이고 `code` 는 `rate-limited`, `type` 이 채워져 있다.
4. 버킷은 용량 60 · 초당 1 리필이다 — 40초 × 5 rps(200건) 중 통과는 100건 언저리다.
5. **멱등 재요청도 한도를 소모한다.** 이미 접수된 키를 다시 보내도 버킷이 비어 있으면 429 다.
   리필 뒤에는 같은 키가 200 재생으로 돌아온다 — 리밋은 거절이 아니라 지연이다.

| 항목 | 기대 | 실측 | 판정 |
|---|---|---|---|
| 보낸 요청 | 200 | 201 | ✅ |
| 통과(201) | 60 ~ 105 | **100** | ✅ (용량 60 + 40초 리필 40) |
| 차단(429) | 75 이상 | **101** | ✅ |
| 예상 밖 status | 0 | **0** | ✅ |
| 체크 통과율 | 100% | **100.00%** | ✅ |
| `bypassed` 증가분 | 0 | **0** | ✅ 이 회차는 레이트 리밋이 <em>켜진 채로</em> 측정됐다 |

> **첫 시도는 무효였다.** 콜드 스타트 직후에 돌렸더니 통과 150 / 차단 51 로 임계를 넘겼다
> (체크는 100% 통과). 원인은 레이트 리밋이 아니라 **fail-open** 이었다 — 그 회차에
> `bypassed` 가 28,800 이었고, 즉 한도를 재려는 측정이 <em>한도가 꺼진 상태</em>에서 이뤄졌다.
> 5절의 표에 `bypassed` 를 넣어 둔 이유가 정확히 이것이고, 그 칸이 없었다면 "레이트 리밋이
> 설계대로 동작하지 않는다" 는 잘못된 결론을 내렸을 것이다.

> 5번 조항이 없으면 한도를 우회하는 방법이 생긴다 — 키 하나를 계속 재전송하면 되기 때문이다.
> 무인증 API(§10)에서 레이트 리밋은 유일한 남용 방지 수단이므로, 이 조항은 성능이 아니라
> **보상 통제**의 문제다.

**정상 상태에서는 전 항목이 목표를 만족한다.** 미달은 콜드 스타트 창 하나뿐이고, 그 창은
재현된다.

### 4절 판정표의 어느 줄이었나

세 줄이 동시에 켜졌다 — 그리고 셋은 <strong>같은 원인의 세 얼굴</strong>이었다(5절 사슬).

| 켜진 줄 | 근거 수치 | 실제 원인 |
|---|---|---|
| `dropped_iterations` > 0 | 819 · 2,169 | 응답이 2~4초라 500 rps 에 1,000+ VU 가 필요했다. VU 상한을 2,500 으로 올려 재측정해도 콜드에서는 같았다 |
| p99 미달 + `pending` > 0 | pending 191, acquire 2.51 s | 풀이 작아서가 아니라 **커넥션을 3.07초까지 쥐어서** |
| p99 미달 + GC 급증 | major GC 166회 / 17.11초 | 0.75 CPU → SerialGC + Metaspace 임계 |

`bypassed` 줄(Redis 지연)도 켜졌고, 원인은 같다 — GC 정지가 50 ms 예산을 통째로 삼켰다.

### 다음 행동

1. **§8.3 전역 Bulkhead 는 Phase 7 로 둔다** (6절). 조건은 켜졌으나 원인이 Bulkhead 가 다루는
   종류가 아니다 — 설계자 확인이 필요한 지점으로 표시했다.
2. **콜드 스타트를 Phase 7 신뢰성 항목으로 연다** (6절 하단 표). 후보 대응을 적되 지금 고르지
   않는다. 롤링 배포 창의 문제라 §8.6 레디니스와 함께 봐야 한다.
3. **`bypassed` 알림(§9.4)은 이미 설계에 있다.** 이번 측정이 그 알림의 값을 보여 줬다 —
   무인증 API 의 유일한 보상 통제가 꺼진 것을 <em>알 수 있게</em> 한 것이 그 카운터다.
4. 회귀 감시선은 **웜 기준 p99 ≤ 200 ms** 로 둔다. 콜드는 별도 항목으로 추적하며, 같은 문서에
   두 값을 나란히 적는 것이 이 측정의 결론이다.
