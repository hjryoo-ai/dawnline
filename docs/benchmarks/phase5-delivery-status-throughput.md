# `delivery.status` 소비 처리량 — 측정 조건 (선기록)

> **이 문서는 측정 전에 쓴다.** 작성 시점(2026-09-22)에 dispatch 의 `delivery.status` 리스너는
> 한 줄도 없다. 채워야 할 칸은 §6 의 결과 표 하나이고 지금은 비어 있다.
>
> 기준을 결과 뒤에 쓰면 **어떤 수치든 「적절하다」가 된다.** `DatasetFeasibilityTest` 가 같은
> 이유로 기준을 먼저 적었고, Phase 1 의 원인 판정표도 그랬다. 여기서 한 가지가 더 걸린다 —
> 이번 측정은 *기존 기준선이 유지되는가* 를 묻는 것이라, 나중에 기준을 만들면 나온 값이
> 그대로 새 기준선이 되어 **회귀가 회귀로 보이지 않는다.**

## 1. 무엇을 재고 무엇을 안 재나

| | 재는가 | 이유 |
|---|---|---|
| 브로커의 `delivery.status` → `route_stops.status` 전이 완료 | **잰다** | 이번에 새로 붙는 경로. 이것이 §8.2 판정의 새 입력이다 |
| 같은 JVM 의 `fulfillment.planned` → `dispatch_candidates` | **다시 잰다** | 기준선 1,638 건/초([측정](phase4-plan-roundtrip-breakdown.md) §3)가 「리스너 하나」의 값이었다. 그 문서가 「소비 경로가 무거워지면 다시 재야 한다」고 적어 둔 조건이 지금 켜진다 |
| `route:{id}:progress` 기록 | 잰다(위에 포함) | 전이 트랜잭션 안에 있으므로 가를 수 없다. 가르는 방법은 §7 |
| tracking 의 발행 쪽 | **안 잰다** | 스캔 → outbox → 브로커는 5-1b 의 `TrackingPublishIT` 이 보고, 팬아웃 배율까지 못 박는다 |
| outbox 릴레이 | **안 잰다** | 이 경로는 발행하지 않는다. 릴레이 지연은 같은 문서 §4(111 ms) |
| 주문 API·계획 시간 | **안 잰다** | Phase 1·4 의 값이 유효하고 이번 변경이 닿지 않는다 |

## 2. 입력 환산 — 주문 rps 를 `delivery.status` 건/초로

§8.2 의 부하 모델은 **주문 rps** 로 적혀 있고, 이번에 재는 것은 **stop 단위 이벤트**다. 둘을 잇는
배율이 둘이고, **둘 다 문서가 아니라 코드가 정한다.**

**배율 ⓐ — stop 당 `delivery.status` 2건.** 도착 + 종결(`COMPLETED` 또는 `FAILED`)이고
`DEPARTED_CAMP` 는 브로커로 나가지 않는다(5-1b). `TrackingPublishIT.팬아웃은_스캔당_한_건이고_캠프_출발은_0_이다`
가 `2 × stop 수` 로 어설션한다.

**배율 ⓑ — 주문당 stop 수.** `StopMerger`(§6.5 1단계)가 정하고 **데이터셋마다 다르다** — 밀도가
높을수록 같은 건물·같은 창의 주문이 한 stop 으로 합쳐지기 때문이다. 아래 표는 실측이고,
`DeliveryStatusFanoutTest` 가 이 표를 읽어 코드와 대조한다.

| 데이터셋 | 주문 | 통합 후 stop | 주문/stop | `delivery.status` | 주문당 이벤트 |
|---|---:|---:|---:|---:|---:|
| `small` | 500 | 470 | 1.0638 | 940 | 1.8800 |
| `medium` | 2,000 | 1,708 | 1.1710 | 3,416 | 1.7080 |
| `large` | 5,000 | 3,657 | 1.3672 | 7,314 | 1.4628 |
| `peak` | 15,000 | 8,411 | 1.7834 | 16,822 | 1.1215 |
| `overload` | 15,000 | 8,411 | 1.7834 | 16,822 | 1.1215 |

실측 조건: **seed 20260905 · 계획 시각 2026-09-06T01:00:00Z** — `DatasetFeasibilityTest` 와 같은
값이다. **seed 가 바뀌면 배율도 바뀐다**(주소 분포가 달라져 통합되는 주문 수가 달라진다).

`peak` 을 쓴다. §8.2 의 피크는 **10캠프 × 15,000 주문/일**이고, `peak` 데이터셋이 정확히 그
**캠프 하루치 15,000** 이다. 다른 규모를 쓰면 밀도가 달라져 배율이 달라진다.

> **600 rps × 1.1215 = 673 건/초.** 이것이 §8.2 버스트의 배송단 환산값이다.

## 3. 그런데 673 건/초는 도착하지 않는다 — 그래서 기준을 둘 건다

주문 버스트는 **컷오프 직전 1시간**에 몰리지만(§8.2), 배송은 **약속창 전체**에 퍼진다(§2.2:
DAWN 00:00–07:00, SAME_DAY 컷오프 +6시간). 같은 하루치를 어느 창에 펴느냐로 나눈 값이다.

| | 하루 이벤트 | 창 | 평균 도착률 |
|---|---:|---|---:|
| 피크일(150,000 주문/일, 10캠프) | 168,220 | DAWN 7시간 | **6.7 건/초** |
| 〃 | 168,220 | SAME_DAY 6시간 | **7.8 건/초** |
| 평시(30,000 주문/일) | 33,644 | DAWN 7시간 | **1.3 건/초** |

**673 과 6.7 의 차이는 100배다.** 그러므로 이 측정에서 실제 위험은 「새 리스너가 673 을
못 낸다」가 아니라 **「새 리스너가 붙어서 기존 경로가 느려진다」**이다 — `fulfillment.planned`
소비는 컷오프에 실제로 몰리고, 그 랙이 §6.7 열화 모드의 입력이기 때문이다(ADR-043 의 랙 조건).
기준을 둘 거는 이유가 이것이다.

## 4. 판정 조건

| | 기준 A — 기존 경로 회귀 | 기준 B — 새 경로 절대값 |
|---|---|---|
| 대상 | `fulfillment.planned` → `dispatch_candidates` | `delivery.status` → `route_stops.status` |
| 입력 | 이벤트 5,000건 (기준선과 동일) | 이벤트 10,000건 = 라우트 50 × stop 100 × 2 |
| **통과** | ≥ **600 건/초** (§8.2 의 조건 자체) | ≥ **673 건/초** (§2 환산값) |
| **조사** | < **1,310 건/초** (기준선 1,638 의 80%) — 통과여도 원인을 적는다 | 통과해도 **여유 배수**를 §3 의 6.7 건/초와 나란히 적는다 |
| 근거 | 통과선은 SLO 이고 조사선은 *같은 기계·같은 방법*끼리의 비교다. 80% 를 고른 근거는 편차가 그보다 작다는 **가정**이고, 그래서 아래처럼 편차를 잰다 | 절대값이 통과해도 673 은 «일어나지 않는 상한» 이라 여유 배수 없이는 판정에 쓸 수 없다 |

**편차를 가정하지 않고 잰다** — 기준 A 와 B 를 각각 **3회** 돌려 최소·중앙·최대를 §6 에 적는다.
3회의 산포가 20% 를 넘으면 **조사선이 무의미하다는 사실을 먼저 적고** 조사선을 산포에 맞춰
다시 정한다(그 조정도 이 문서에 남긴다 — 결과를 보고 기준을 고치는 것이므로 숨기면 안 된다).

## 5. 측정 환경

| 항목 | 값 |
|---|---|
| 기계 | macOS 27.0 · aarch64 · 14코어 |
| JDK · Docker · PostgreSQL · Kafka | Temurin 25.0.4.1 (Gradle 툴체인) · Docker Desktop 29.1.3 · PostgreSQL 18.2 · Kafka 4.3.1 (둘 다 Testcontainers) · Redis 8.8.2 |
| 측정 커밋 | `bb32e93` + `ThroughputProbeIT`. 계측 클래스는 **측정 커밋에 남기고 다음 커밋에서 지운다** — 커밋 해시가 재현 경로다 |
| **JVM 하나에 리스너 몇 개** | 측정 시점 **4개** — `fulfillment.planned` · `wave.closed` · `order.cancelled` · `delivery.status`(신규). 5-3 의 `delivery.at-risk` 가 붙으면 5개가 되고 **그때 이 측정은 무효다** |
| 리스너 동시성 · 파티션 | `concurrency` 는 서비스 기본값 그대로, 로컬 파티션 12 (§8.3: 동시성 ≤ 파티션) |
| **라우트 수** | 기준 B 는 **50 라우트 × stop 100**. 한 라우트에 몰면 `route_stops` 행 잠금과 `route:{id}:progress` 키 하나가 처리량 상한이 되어 **경합을 재게 된다**. 50 은 `peak` 한 캠프(라우트 90)의 절반이고 stop 100 은 시드 룰 `max-stops` 120 바로 아래다 |
| 스캔 순서 | stop seq 오름차순, 라우트 간에는 섞는다 — 실제 기사들은 동시에 돈다 |
| **sim-runner 압축 배율** | **쓰지 않는다.** `TripPacer` 가 호출 간격을 배속으로 잡아 주는 것이 시뮬레이터의 목적이라, 그것으로 재면 소비자가 아니라 **페이서를 재게 된다.** 기준 A 의 방법과 같이 `KafkaProducer` 로 직접 밀어 넣는다 — 기준선과 방법이 달라지면 두 값을 비교할 수 없다 |
| 계측 지점 | 발행 완료 시각 → 마지막 `route_stops` 행의 상태가 보일 때까지(Awaitility 폴링). 기준 A 와 동일한 형태 |

## 6. 결과 (2026-09-22)

### 기준 A — `fulfillment.planned` → `dispatch_candidates`, 5,000건

| 실행 | 발행 | 마지막 행까지 | 처리량 |
|---|---:|---:|---:|
| 1 | 48 ms | 2,286 ms | 2,187 건/초 |
| 2 | 37 ms | 2,179 ms | 2,295 건/초 |
| 3 | 35 ms | 2,178 ms | 2,295 건/초 |
| | | **중앙값** | **2,295 건/초** (산포 4.7%) |

**통과.** 통과선 600 건/초의 **3.8배**이고 조사선 1,310 건/초도 넘는다. 리스너가 넷으로 늘었는데
**기준선 1,638 건/초보다 오히려 높다.**

> **그러니 「빨라졌다」고 읽지 않는다.** 두 값은 방법이 완전히 같지 않다.
> ① 기준선은 «마지막 행이 보일 때까지» 3,053 ms 만 나눈 값이고(발행 250 ms 제외), 이 측정은
> 발행부터 잰다 — 이쪽이 <em>불리한</em> 방향이라 차이를 설명하지 못한다.
> ② 기준선은 **한 번** 측정했고 이 측정은 세 번 돈다. 실행 1(2,187)과 2·3(2,295)의 차이가
> JIT 워밍이고, 기준선은 실행 1 에 해당한다. 그래도 2,187 > 1,638 이다.
> ③ 그 사이 [ADR-029](../adr/ADR-029-optimizer-io-is-bulk-not-orm.md)가 <em>영속화</em>를 벌크로
> 바꿨다. 후보 적재는 그 경로가 아니지만 같은 세션·같은 커넥션 풀을 쓴다.
>
> **이 측정으로 답할 수 있는 것은 「두 번째 리스너가 이 경로를 느리게 하지 않았다」까지다.**
> 셋 중 무엇이 차이를 만들었는지는 재지 않았다(근거: 추정). 그것을 가르려면 기준선 커밋에서
> 같은 방법으로 다시 재야 하고, 이 측정의 판정에는 필요하지 않다.

### 기준 B — `delivery.status` → `route_stops.status`, 10,000건 (라우트 50 × stop 100 × 2)

| 실행 | 발행 | 마지막 전이까지 | 처리량 |
|---|---:|---:|---:|
| 1 | 85 ms | 11,651 ms | 858 건/초 |
| 2 | 44 ms | 10,154 ms | 985 건/초 |
| 3 | 33 ms | 9,938 ms | 1,006 건/초 |
| | | **중앙값** | **985 건/초** (산포 15.0%) |

**통과.** 통과선 673 건/초를 최솟값(858)으로도 넘는다.

| 무엇과 견주나 | 값 | 여유 |
|---|---:|---:|
| §8.2 버스트 환산(§2) | 673 건/초 | **1.5배** |
| 실제 도착률, 피크일 DAWN(§3) | 6.7 건/초 | **147배** |

`route:{id}:progress` 키 **50개**가 채워졌다 — 라우트마다 하나다.

### 편차는 가정하지 않고 쟀다

문서 §4 가 「3회의 산포가 20% 를 넘으면 조사선이 무의미하다」고 적어 두었다. A 4.7% · B 15.0%
로 둘 다 20% 아래이므로 **조사선(기준선의 80%)은 그대로 유효하다.** B 의 15% 는 전부 실행 1 에
있고(11.7초 → 10.2초 → 9.9초) 이것은 JIT 워밍이다 — 실행 2·3 의 차이는 2%다.

### 기준 B 가 A 의 절반 속도인 이유는 재지 않았다

985 건/초는 A 의 43%다. 이벤트 하나가 하는 일이 더 많으므로(멱등 게이트 + stop 조회 + 상태
쓰기 + 진행 재집계 + Redis 왕복) 이상한 값이 아니고, **선기록한 판정 조건을 전부 통과했으므로
§7 의 원인 추적을 돌리지 않는다.** 그 절은 미달일 때의 절차다. 지금 그 차이를 가르면
「기준이 없는 최적화」가 된다 — 필요해지는 시점은 실제 도착률이 147배 여유를 갉아먹을 때이고,
그 조건은 §3 의 표에 적혀 있다.

## 7. 미달이면 — 원인까지가 완료 조건

Phase 1 9단계 규칙이다. 「느렸다」로 끝내지 않는다. 후보와 **가르는 방법**을 미리 적는다.

| 후보 | 가르는 방법 |
|---|---|
| `route:{id}:progress` 의 Redis 왕복 | Redis 를 내리고 다시 잰다. 불변규칙 7 의 폴백이 이미 있어야 하므로 **이 측정 자체가 폴백 경로의 실행이기도 하다** |
| `route_stops` UPDATE 의 행 잠금 경합 | 라우트 수를 50 → 1 로 줄여 다시 잰다. 1 에서 크게 떨어지면 경합이고, 같으면 아니다 |
| 두 리스너의 컨슈머 스레드 경합 | 기준 A 를 `delivery.status` 리스너만 끄고 다시 잰다. 1,638 로 돌아오면 경합이다 |
| 낙관적 락 재시도 | 재시도 카운터를 본다. 이건 추측 없이 값으로 나온다 |
| `processed_events` INSERT | **원인이 될 수 없다** — 기준 A 에도 같은 비용이 있었고 그 값이 1,638 이었다. 이 줄은 *지우지 않는다*: 다음 사람이 같은 후보를 다시 세우지 않도록 |

---

**이 문서가 무효가 되는 조건** — ⓐ `StopMerger` 의 통합 키가 바뀌어 §2 표의 배율이 달라질 때
(`DeliveryStatusFanoutTest` 가 잡는다), ⓑ `DEPARTED_CAMP` 가 브로커로 나가게 될 때
(`TrackingPublishIT` 가 잡는다), ⓒ dispatch 에 리스너가 더 붙을 때(5-3). 셋 다 §5 헤더에
적힌 값이고, **무효인 줄 모르고 인용하는 것**이 이 측정에서 가장 나쁜 결말이다.
